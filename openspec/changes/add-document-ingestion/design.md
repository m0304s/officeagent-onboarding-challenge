## Context

동기는 `proposal.md` — Why, 요구사항은 `specs/document-ingestion/spec.md` 참조.

앞선 change가 남긴 것은 실행되는 빈 서버다. 계층 디렉터리(`api`/`services`/`core`/`adapters`), 도메인 예외 기반 클래스와 오류 봉투, 설정 단일 창구, 요청 로깅, 테스트 하네스, 그리고 어댑터 프로토콜 **하나**(`HealthProbe`)가 있다. 넓은 `VectorStore`·`Embedder` 프로토콜은 "소비자가 생길 때 정의한다"는 이유로 의도적으로 비워 뒀다. 이 change가 그 소비자다.

설계를 좌우하는 제약은 넷이다.

1. **저장 결과의 모양이 이후 세 change를 구속한다.** 청크에 위치 정보가 없으면 출처를 만들 수 없고, 리비전 개념이 없으면 무효화 신호가 없다.
2. **CPU 바운드 작업이 처음 들어온다.** PDF 파싱과 임베딩 인코딩은 블로킹이다. 워커는 1개 프로세스로 고정돼 있어(임베디드 벡터 스토어의 파일 락) 이벤트 루프를 막으면 서비스 전체가 멈춘다.
3. **평가자는 한 줄로 띄우고 한 줄로 테스트한다.** 새 컨테이너를 늘리거나 수작업 준비 단계를 요구하면 실행 조건이 깨진다.
4. **샘플 문서가 한국어다.** 영어 전용 임베딩 모델은 검색이 사실상 동작하지 않는다.

## Goals / Non-Goals

**Goals**

- 청크 스키마를 확정한다 — 문서 식별자, 리비전, **색인 서명**, 위치 정보. 이후 change가 재협상하지 않는다.
- 저장된 벡터가 **어떤 구성으로 만들어졌는지**를 값으로 남긴다. 구성이 바뀌면 재색인이 강제되고, 구 구성 벡터가 검색에 섞이지 않는다.
- 재업로드 의미론을 **원자적으로** 구현한다. "지금 유효한 리비전"에 단일 답이 있고, 교체 도중 실패해도 이전 상태가 살아 있다.
- 파서·임베더·벡터 스토어·레지스트리를 프로토콜 뒤에 두어, 구현 교체가 상위 계층을 건드리지 않게 한다.
- 블로킹 작업을 이벤트 루프 밖으로 내보내고, 그 사실을 테스트로 고정한다.

**Non-Goals**

- **검색 질의**는 설계하지 않는다. `VectorStore` 프로토콜은 이 change가 실제로 쓰는 **쓰기·삭제·집계** 면만 정의한다. `query`는 retrieval change가 자기 요구를 알고 나서 붙인다. 지금 정하면 top-k·필터·거리 지표·재랭킹을 근거 없이 추측하게 된다.
- **LLM 호출·스트리밍·프롬프트**. 이 change는 LLM을 호출하지 않는다.
- **캐시 키 구성과 무효화 실행**. 이 change는 무효화의 *신호*(리비전)만 만들고, 그것을 소비하는 쪽은 캐싱 change다.
- **OCR**. 텍스트 레이어가 없는 PDF는 거부하고, 거부 사유에서 OCR을 하지 않는다는 사실을 밝힌다.
- **비동기 작업 큐, 문서 버전 히스토리 보관, 접근 제어**.

## Decisions

### 1. 수집은 요청 안에서 동기적으로 끝낸다

업로드 요청 하나가 파싱 → 청킹 → 임베딩 → 저장까지 마치고 최종 결과를 응답한다. 잡 큐와 폴링 엔드포인트를 두지 않는다.

작업 큐를 두면 큐·워커·잡 상태 저장소·상태 조회 엔드포인트가 따라오고, 테스트는 "완료될 때까지 폴링"이 되어 느려지고 불안정해진다. 얻는 것은 큰 문서에서의 응답 시간뿐인데, 이 서비스가 다루는 문서는 업로드 크기 상한(기본 20 MiB)으로 묶여 있다.

대신 두 가지로 상한을 건다: **업로드 크기 상한**과 **스레드풀 오프로드**(결정 9). 큐가 필요해지는 지점은 명확하다 — 수집 시간이 HTTP 타임아웃을 넘기 시작할 때다. 그때 `IngestionService`의 호출부만 잡 제출로 바꾸면 되고, 파서·청커·임베더는 그대로다.

### 2. 청킹은 전략 선택지이고, 기본값은 구조 경계 우선 재귀 분할이다

분할 전략을 설정 항목 `chunk_strategy`로 두고 기본값을 `recursive`로 한다. **이번 범위에서 실제로 구현되는 전략은 `recursive` 하나다.** 다른 값을 넣으면 기동에 실패하며, 받아들여지는 값 목록을 오류 메시지에 담는다. 미구현 전략을 설정으로 고를 수 있게 두면 "설정에 있으니 지원한다"는 허위 기재가 된다.

전략을 선택지로 만드는 이유는 다음 후보가 이미 보이기 때문이다 — **부모-자식 청킹**(작은 자식 청크로 검색하고 답변에는 큰 부모 청크를 넘기는 방식)이다. 이번에 붙이지 않는 이유는 범위가 아니라 순서다. 부모-자식의 이득은 *검색된 자식을 부모로 확장하는 단계*에서만 나오는데, 이 change에는 검색 질의 자체가 없다(Non-Goals). 확장할 곳이 없는 상태에서 부모 텍스트를 저장하면 인덱스만 배로 커지고 검증할 수 있는 것이 없다. retrieval change가 질의 경로를 만든 뒤 그 위에서 재는 것이 맞다.

**교체 지점**: `core/chunking.py`가 `(전략 이름) → 분할 함수` 레지스트리를 갖고, 서비스는 설정에서 고른 이름으로 함수를 받아 쓴다. 분할 함수의 시그니처는 `(segments, size, overlap) -> tuple[TextChunk, ...]`로 동일하다.

> **구현 중 조정**: 분할 함수는 정체성이 붙지 않은 `TextChunk`(본문 + 위치)를 돌려주고, `core/documents.py`의 `identify_chunks`가 `document_id`·`revision`·`index_signature`·순번을 붙여 `Chunk`를 만든다. 분할은 문서가 무엇인지 몰라도 되는 순수 연산인데, 정체성 세 값을 분할 함수에 넘기면 분할이 그것에 의존하는 것처럼 보인다. 겹침도 `0`을 허용하지 않도록 설정을 `gt=0`으로 좁혔다 — spec 의 "인접 청크는 겹친다"가 무조건이라, `0`을 허용하면 설정 하나로 계약이 깨진다. 부모-자식을 붙일 때 바뀌는 것은 이 레지스트리에 항목 하나를 더하는 일과, 부모 텍스트를 어디에 둘지(청크 메타데이터 vs. 별도 저장소)를 정하는 일뿐이다. 후자는 retrieval change의 결정이다.

전략 이름은 `index_signature`의 재료다(결정 6). 전략을 바꾸면 청크 경계가 달라지므로 재색인이 강제된다.

아래는 기본 전략 `recursive`의 동작이다. `core/chunking.py`가 구분자 우선순위를 따라 재귀적으로 자른다.

```
문단(\n\n) → 줄(\n) → 한국어 문장 종결(다. / 요. / 니다. ) → 영어 문장 종결(. ) → 공백 → 문자
```

앞 구분자로 잘라 상한에 맞으면 거기서 멈추고, 안 맞으면 다음 구분자로 내려간다. 마지막 수단인 "문자"까지 가는 경우는 공백 없는 긴 토큰뿐이다.

> **구현 중 조정**: 쪼개기만으로는 부족하다. 이른 자리에 구조 경계가 하나만 있는 문서(짧은 제목 + 문단 구분자 없는 본문)에서 그 경계에 끊고 멈추면 10자짜리 청크가 나온다. **쪼갠 뒤 연속한 조각을 상한까지 합치는 단계**가 있어야 한다. 재귀는 문자열이 아니라 `(start, end)` 구간에 대해 수행해 오프셋이 재귀 인자 자체가 되게 했다. 합치기 예산은 `size - overlap`이며, 겹침은 문자 단위로 뒤에서 당기되 앞 청크의 시작을 넘지 못하게 막는다 — 넘으면 앞 청크가 뒤 청크에 통째로 삼켜진다.

| 대안 | 기각 이유 |
|------|----------|
| 고정 길이 분할 | 문장·문단 중간을 자른다. 잘린 조각이 검색되면 출처로 보여줄 때 말이 안 되는 텍스트가 나온다 |
| 문장 단위 | 한국어 문장 분리는 규칙만으로 정확하지 않고, 조각이 너무 짧아 문맥이 사라진다. 짧은 청크는 임베딩이 주변 맥락을 잃어 검색 품질이 떨어진다 |
| 시맨틱 청킹(임베딩 유사도로 경계 탐지) | 수집 비용이 문서당 임베딩 호출 수만큼 늘고, 결과가 모델에 종속돼 재현이 어렵다. 문서 종류가 두 개뿐인 지금 얻을 이득이 비용보다 작다 |
| 토큰 기준 크기 | 토크나이저를 알아야 하므로 `core/`가 임베딩 라이브러리에 의존하게 된다. 계층 규칙(`core/`는 외부 라이브러리를 import 하지 않는다) 위반이다. 대신 결정 5의 토큰 가드로 상한을 지킨다 |

**기본값**: 청크 600자, 겹침 100자. 근거는 두 가지다. (a) 출처 표기의 단위가 되므로 "이 문단에서 왔다"고 말할 수 있을 만큼 작아야 한다. 문서 한 쪽을 통째로 인용하면 출처의 의미가 없다. (b) 임베딩 모델 입력 창(512 토큰) 안에 여유 있게 들어가야 한다 — 한국어 600자는 대략 400~450 토큰이다. 겹침 100자는 문단 경계에 걸친 문장이 양쪽 청크 어디에서도 온전히 읽히게 하는 최소치다.

두 값 모두 설정 항목이다. 샘플 문서로 검색 품질을 재는 것은 retrieval change의 일이고, 그때 재조정될 수 있다.

**청크는 페이지 경계를 넘지 않는다.** PDF는 쪽 단위 세그먼트로 추출한 뒤 세그먼트별로 자른다. 두 쪽에 걸친 청크가 생기면 "이 청크는 몇 쪽인가"에 답이 두 개가 되어 출처 표기가 모호해진다. 대가는 짧은 쪽에서 짧은 청크가 나온다는 것인데, 출처 정확성이 더 중요하다.

### 3. `DocumentParser`는 동기 프로토콜이고 바이트를 받는다

```python
@dataclass(frozen=True)
class TextSegment:
    text: str
    page: int | None = None          # 1-base. PDF 만 채운다

@dataclass(frozen=True)
class ExtractedDocument:
    segments: tuple[TextSegment, ...]
    page_count: int | None = None    # 텍스트 레이어 유무 판정에 필요

@runtime_checkable
class DocumentParser(Protocol):
    format: str                       # "txt" | "md" | "pdf"
    extensions: frozenset[str]

    def parse(self, data: bytes) -> ExtractedDocument: ...
```

**왜 `async def`가 아닌가.** 두 구현 모두 CPU 바운드다. 인터페이스를 async로 선언하면 "이건 논블로킹"이라는 거짓말이 되고, 구현자가 이벤트 루프 위에서 그냥 돌려도 타입상 아무 문제가 없어 보인다. 동기로 선언하면 호출부가 오프로드를 **의식할 수밖에 없다**(결정 9).

**왜 경로가 아니라 바이트인가.** 업로드는 크기 상한 안에서 이미 메모리에 올라온다. 경로를 받게 하면 임시 파일 생성·정리 책임이 생기고, 테스트마다 파일을 만들어야 한다.

> **구현 중 조정**: `TextSegment`·`ExtractedDocument`는 값 객체이므로 `core/documents.py`에 두고, `DocumentParser` 프로토콜만 `adapters/protocols.py`에 둔다. 청킹이 `TextSegment`를 소비하는데 `core/`가 `adapters/`를 import 하면 계층이 역전된다. 프로토콜과 그것이 주고받는 값의 위치를 나누는 것은 `HealthProbe`(adapters) ↔ `ProbeResult`(core)의 기존 배치와 같다.

**왜 세그먼트 목록인가.** 파서마다 자연스러운 단위가 다르다 — PDF는 쪽, 텍스트는 문서 전체. 문자열 하나로 합쳐 돌려주면 페이지 정보가 그 시점에 소실되고, 위치 정보를 되살릴 방법이 없다. 세그먼트 경계를 유지하면 청커가 결정 2의 "페이지를 넘지 않는다"를 지킬 수 있다.

파서는 자기 경계에서 라이브러리 예외를 도메인 예외로 바꿔 던진다. 라우터까지 `fitz.FileDataError` 같은 것이 새면 계층 경계가 무의미해진다.

### 4. PDF 파서는 PyMuPDF로 구현하고, 모델 기반 파서는 교체 지점만 남긴다

**이번 범위에서 실제로 구현되는 PDF 파서는 PyMuPDF 하나다.** Marker를 비롯한 모델 기반 파서는 구현하지 않으며, 문서 어디에도 "지원한다"고 적지 않는다.

| 후보 | 성격 | 이번에 선택하지 않은 이유 |
|------|------|--------------------------|
| **PyMuPDF** (선택) | C 확장, 규칙 기반 텍스트 추출 | — |
| Marker 등 모델 기반 | 딥러닝 레이아웃 분석 → 마크다운. 표·다단·수식 복원 품질이 높다 | **실행 단순성**: 모델 가중치 다운로드와 추론 런타임이 추가로 필요해 "한 줄 실행"의 실패 지점이 늘어난다. **이미지 크기**: 가중치가 GB 단위라 임베딩 모델과 합치면 이미지가 배로 커진다. **빌드 시간**: 평가자가 이미지를 처음 빌드하는 시간이 몇 배가 된다. 얻는 품질 이득은 샘플 문서(단순 텍스트 문서) 범위에서 거의 0이다 |
| pypdf | 순수 파이썬 | 추출 속도와 레이아웃 보존이 PyMuPDF보다 떨어진다. 다만 라이선스가 더 느슨하다(아래) |

**교체 지점은 정확히 한 곳이다.** `adapters/parsers/pdf.py`가 `DocumentParser` 프로토콜을 구현하고, 앱 팩토리의 파서 레지스트리에 등록된다. 다른 파서로 바꾸려면 같은 프로토콜을 구현한 클래스를 그 자리에 등록하면 되고, `services/`·`core/`·`api/`는 한 줄도 바뀌지 않는다. 프로토콜이 반환하는 `ExtractedDocument`가 쪽 단위 세그먼트라, 마크다운을 뱉는 파서도 "쪽별 텍스트"로 감싸 넣을 수 있다.

**라이선스 주의**: PyMuPDF는 AGPL-3.0이다. 평가용 비공개 리포 범위에서는 문제가 없지만, 상용 배포로 간다면 pypdf(BSD) 교체가 먼저다. 교체 비용이 위 한 곳으로 국한된다는 점이 이 구조의 값이다. 이 사실을 `ARCHITECTURE.md`에도 적는다.

### 5. 임베딩 모델은 다국어 모델로 바꾼다 — `intfloat/multilingual-e5-small`

`openspec/config.yaml`과 `ARCHITECTURE.md`는 "sentence-transformers (로컬)"까지만 정하고 모델을 특정하지 않았다. 여기서 특정한다. 라이브러리 선택(sentence-transformers)은 유지한다.

| 후보 | 기각/선택 이유 |
|------|---------------|
| `all-MiniLM-L6-v2` | **영어 전용**. 샘플 문서가 한국어라 검색이 사실상 동작하지 않는다 |
| `paraphrase-multilingual-MiniLM-L12-v2` | 다국어지만 입력 창이 **128 토큰**이다. 한국어 600자가 들어가지 않아 청크가 조용히 잘린다. 잘린 뒷부분은 임베딩에 반영되지 않으면서 청크 본문에는 남아, 검색되지 않는 텍스트가 저장되는 최악의 형태가 된다 |
| **`intfloat/multilingual-e5-small`** (선택) | 다국어, 입력 창 **512 토큰**, 384차원, 파라미터 118M. 창이 청크 크기를 여유 있게 덮고 모델 크기가 이미지에 부담이 적다 |
| `BAAI/bge-m3` | 품질은 가장 좋지만 GB 단위라 이미지 크기·첫 로딩 시간이 감당되지 않는다 |

e5 계열은 입력에 **역할 접두사**(`passage: ` / `query: `)를 요구한다. 이 규약은 모델 고유의 것이므로 **어댑터 안에 가둔다**. 상위 계층은 `embed_documents` / `embed_query` 두 메서드만 보고, 접두사의 존재를 모른다.

```python
@runtime_checkable
class Embedder(Protocol):
    dimension: int
    max_input_tokens: int
    signature: str          # 모델 정체성 — 색인 서명의 재료 (결정 6)

    async def embed_documents(self, texts: Sequence[str]) -> list[list[float]]: ...
    async def embed_query(self, text: str) -> list[float]: ...
    def count_tokens(self, text: str) -> int: ...
    async def warm_up(self) -> None: ...   # 기동 시 선로딩 (아래)
```

**`signature`를 어댑터가 소유하는 이유.** 같은 벡터를 낼 것인가를 결정하는 사실 — 모델 식별자, 차원, 정규화 여부, 역할 접두사 규약 — 을 전부 아는 곳은 어댑터뿐이다. 접두사 규약은 방금 위에서 "상위 계층은 존재를 모른다"고 가둔 것이라, 상위 계층이 서명을 조립하려면 그 캡슐화를 깨야 한다. 어댑터가 문자열 하나로 요약해 내보내면 캡슐화를 유지한 채 서명을 만들 수 있다. 값은 `"multilingual-e5-small/384/l2norm/e5-prefix-v1"`처럼 사람이 읽을 수 있게 두어, 서명이 달라졌을 때 무엇이 달라졌는지 로그에서 바로 보이게 한다.

**토큰 가드.** 청크 크기는 문자 기준이라(결정 2) 토큰 수를 보장하지 못한다. 서비스가 임베딩 직전에 `count_tokens`로 확인하고, `max_input_tokens`를 넘는 청크는 `core/`의 분할 함수로 다시 쪼갠다. 토큰 계산은 토크나이저를 아는 어댑터가, 분할은 라이브러리를 모르는 `core/`가 맡는다 — 계층 규칙을 지키면서 조용한 절단을 막는 배치다.

**모델은 기동 시 선로딩한다 — 다만 기동 *조건*은 아니다.**

지연 초기화만 두면 비용이 사라지는 게 아니라 **첫 업로드에게 청구된다.** 그 요청 하나가 수 초를 뒤집어쓰고, 평가자가 처음 눌러 보는 요청이 정확히 그 요청이다. 더 나쁜 것은 실패가 드러나는 시점이다 — 가중치가 없거나, 선언한 차원·입력 창이 실물과 어긋나거나(결정 6의 서명이 거짓이 되는 경우), 디스크가 부족한 상황이 전부 **첫 업로드에서** 500으로 나타난다. 기동 시점에 한 번 올려 보면 그 전부가 로그 한 줄로 먼저 드러난다.

선로딩의 범위는 **가중치 로딩 + 짧은 텍스트 1회 인코딩**이다. 로딩만으로는 첫 `encode`에 남는 초기화 비용(그래프 준비, 커널 워밍)이 그대로 남아, "첫 요청 지연을 없앤다"는 목적이 절반만 달성된다. 실제로 한 번 인코딩해 보면 "이 모델로 벡터가 나오는가"까지 기동 시점에 확인된다.

**실패는 기동을 막지 않는다.** 경고를 남기고 계속 뜬다. 근거는 둘이다. `openspec/specs/service-health/spec.md`의 "설정을 전혀 제공하지 않아도 기동에 성공한다"·"깨끗한 체크아웃에서 기동"이 여전히 유효한 요구사항이고, 기동 정리(`reconcile_storage`)에서 이미 같은 규율을 쓰고 있다 — 부수 작업의 실패가 서비스 자체를 못 뜨게 하면 안 된다.

그래서 **지연 초기화를 걷어내지 않고 백스톱으로 남긴다.** 선로딩이 실패해도 첫 임베딩 호출이 다시 로딩을 시도하므로, 일시적 실패(디스크 경합, 느린 볼륨)는 스스로 회복된다. 선로딩은 "미리 해 두는 일"이지 "유일한 통로"가 아니다.

**`warm_up()`을 프로토콜에 둔다.** 앱 팩토리는 `Embedder` 프로토콜만 알고 구현체를 모른다. `isinstance`로 구체 어댑터를 확인하고 부르면 배선이 구현체를 알게 되어 계층 규약이 깨진다. 대역(`FakeEmbedder`)은 no-op으로 구현한다 — 올릴 것이 없는 임베더에게도 "미리 준비하라"는 요청은 의미가 있고, 아무것도 하지 않는 것이 그 답이다.

호출 자리는 lifespan이며 `reconcile_storage`보다 **먼저**다. 정리는 모델을 쓰지 않으므로 순서에 기능적 의존은 없지만, 오래 걸리는 쪽을 먼저 두어야 기동 로그가 "무엇을 기다리는 중인지"를 순서대로 말한다. 로딩은 블로킹이므로 어댑터 안에서 스레드풀로 나간다(결정 9의 오프로드 규칙 그대로).

**헬스는 모델 상태를 보고하지 않는다.** 프로브는 캐시·벡터 스토어 둘 그대로다. 선로딩이 생겼다고 "모델 로딩 중"을 불가용으로 보고하면, 모델이 없어도 목록·삭제·헬스는 정상 동작하는데 서비스 전체가 불가용으로 보인다.

**대가**: 가중치가 로컬에 없는 환경에서는 기동이 다운로드 시간만큼 길어진다. 컨테이너는 빌드 단계에서 가중치를 굽기 때문에(아래) 이 경로가 없고, 도커 없이 로컬로 띄우는 경우에만 해당한다.

**이미지 크기 대응**: torch를 CPU 전용 휠로 설치한다(CUDA 런타임 제외). 모델 가중치는 빌드 단계에서 미리 받아 굽는다 — 런타임 네트워크 의존과 첫 요청 지연을 동시에 없앤다. 그래도 이미지가 문제가 되면 다음 수는 ONNX 런타임 기반 임베딩(torch 제거)이며, `Embedder` 프로토콜 뒤라 교체 범위는 어댑터 한 파일이다.

### 6. 문서 식별자는 파일명에서, 리비전은 내용 해시로, 색인 서명은 구성 해시로

```
document_id     = uuid5(고정 네임스페이스, 정규화된 파일명)   # 결정론적, 조회 없이 계산 가능
revision        = sha256(원본 바이트)                        # 내용이 바뀌면 반드시 바뀐다
index_signature = sha256(색인 구성의 정규 문자열)[:16]        # 색인 방식이 바뀌면 반드시 바뀐다
```

파일명 정규화는 경로 제거 → 유니코드 NFC → 소문자화다. macOS(NFD)와 리눅스(NFC)에서 같은 한글 파일명이 다른 문서가 되는 것을 막는다.

**왜 랜덤 UUID가 아닌가.** 랜덤이면 "같은 문서인가"를 판정하려면 파일명 인덱스를 따로 조회해야 하고, 그 인덱스가 곧 또 하나의 진실 원천이 된다. 결정론적 유도는 조회 없이 같은 답을 준다.

**왜 내용 해시를 식별자로 쓰지 않는가.** 내용이 바뀌면 다른 문서가 되어버려 "문서를 갱신했다"를 표현할 수 없다. 그러면 캐시 무효화가 성립하지 않는다 — 무효화는 *같은 문서가 달라졌다*는 사건이기 때문이다.

**대가**: 같은 파일명의 서로 다른 문서는 서로를 덮어쓴다. 이는 의도된 동작이며, 응답의 `status: "replaced"`와 `previous_revision`으로 호출자에게 드러난다. 조용히 일어나지 않는다.

#### `index_signature` — 내용이 아니라 색인 방식의 신호

`revision`만으로는 표현되지 않는 변경이 있다. **모델·차원·정규화·역할 접두사 규약·분할 전략·청크 크기·겹침**이 바뀌면 같은 바이트에서 전혀 다른 벡터가 나오는데 `revision`은 그대로다. 그러면 셋이 동시에 깨진다.

1. 결정 8의 `unchanged` 단축이 그대로 걸려 **재업로드해도 재색인이 일어나지 않는다**. 사용자는 다시 색인했다고 믿는다.
2. 구 구성 벡터와 신 구성 벡터가 한 인덱스에 공존한다. 차원이 같으면 오류조차 나지 않고 검색 품질만 조용히 무너진다. 차원이 다르면 쓰기 시점에 터지는데, 그때는 이미 문서 절반이 바뀐 뒤다.
3. 캐싱 change가 캐시 항목을 `(document_id, revision)`으로 태깅하므로, 모델을 갈아도 무효화 신호가 없어 **낡은 답변이 계속 서빙된다**.

그래서 색인 결과를 결정하는 구성을 서명 하나로 묶는다.

| 서명에 들어가는 것 | 출처 |
|---|---|
| 임베딩 모델 정체성 — 모델 식별자, 차원, 정규화 여부, 역할 접두사 규약 | `Embedder.signature` (어댑터가 소유, 결정 5) |
| 분할 전략 이름 (`recursive`) | 설정 `chunk_strategy` (결정 2) |
| 분할 전략 버전 `CHUNK_STRATEGY_VERSION` | `core/chunking.py` 상수 |
| 청크 크기 · 겹침 | 설정 |

| 들어가지 않는 것 | 이유 |
|---|---|
| 문서 내용·파일명 | `revision`·`document_id`의 몫이다. 섞으면 "구성이 같은가"를 물을 수 없게 된다 |
| 임베딩 배치 크기, 업로드 상한, 수집 동시성 상한 | 결과 벡터를 한 비트도 바꾸지 않는다. 넣으면 성능 튜닝이 전면 재색인을 유발한다 |

`core/documents.py`의 순수 함수가 이 값들을 정규 문자열로 직렬화해 해시한다. 재료를 모으는 것은 서비스이고(어댑터의 `signature` + 설정), 유도 규칙은 라이브러리를 모르는 `core/`에 있다 — `document_id`·`revision`과 같은 배치다.

> **구현 중 조정**: 직렬화는 `key=value` 줄 잇기가 아니라 정렬된 JSON이다. 줄로 이으면 값 안의 개행이 구분자와 구별되지 않아 **서로 다른 구성이 같은 서명**을 받는다. `embedder_signature`가 어댑터가 만드는 자유 문자열이라 앞으로도 개행이 섞이지 않는다고 보장할 수 없고, 충돌하면 재색인이 일어나지 않아 서명이 막으려던 실패가 서명을 통해 돌아온다.

**`CHUNK_STRATEGY_VERSION`은 손으로 올려야 한다.** 구분자 우선순위나 겹침 계산을 바꾸면 설정값은 그대로인데 청크 경계가 달라진다. 자동으로 잡을 방법이 마땅치 않아(소스 해시는 주석 수정에도 반응해 무의미한 재색인을 부른다) 규율에 의존하는 지점이며, Risks에 남긴다.

**서명 자체를 설정 항목으로 두지 않는다.** 이미 있는 설정과 어댑터가 아는 사실에서 유도되는 값이기 때문이다. 손으로 적을 수 있게 하는 순간 실제 구성과 어긋난 값을 넣을 수 있고, 그러면 서명이 보증하려던 것이 사라진다. 이 결정으로 **새로 늘어나는 설정 항목은 `chunk_strategy` 하나뿐**이다.

`(document_id, revision, index_signature)`가 저장된 벡터의 완전한 정체성이다. `revision`은 "문서가 달라졌다", `index_signature`는 "같은 문서라도 다르게 색인된다"를 뜻한다. 캐싱 change는 캐시 항목을 이 셋에 태깅하고, 셋 중 하나라도 바뀐 문서를 참조하던 항목을 무효화한다. 무효화 판정에 문서 본문을 다시 읽을 필요는 여전히 없다.

### 7. 문서 레지스트리를 벡터 인덱스와 분리하고, SQLite에 둔다

"이 문서의 현재 리비전은 무엇인가"에 **단일 답**이 있어야 교체가 원자적이 된다. 그 답을 어디에 둘지가 이 change에서 가장 무거운 결정이다.

| 대안 | 기각 이유 |
|------|----------|
| 벡터 스토어 메타데이터만으로 유도 | "현재 리비전"이 여러 청크에 흩어진 값에서 *추론*된다. 교체 도중에는 두 리비전의 청크가 공존하므로 그 순간 답이 둘이다. 청크 전체의 메타데이터를 한 번에 바꾸는 원자적 연산도 없다 |
| 캐시 저장소(Redis)에 보관 | 캐시는 축출과 TTL이 있는 저장소다. 문서 목록이 조용히 사라질 수 있는 자리에 진실 원천을 두면 안 된다 |
| 별도 관계형 DB 컨테이너 | 컨테이너가 하나 늘고 "한 줄 실행"의 실패 지점이 늘어난다. 저장할 데이터는 문서 수십 건이다 |
| **SQLite 파일** (선택) | 표준 라이브러리라 의존성·이미지 크기 증가가 **0**이다. 트랜잭션이 있어 리비전 교체가 원자적이다. 벡터 스토어와 같은 볼륨에 두면 영속화 경로가 하나다 |

이는 `openspec/config.yaml`의 스택 표에 없던 구성 요소를 추가하는 결정이다. `ARCHITECTURE.md`에 **추가한 이유와 함께** 기록한다(tasks 참조).

레지스트리 레코드: `document_id`(PK), `filename`, `format`, `revision`, `index_signature`, `index_status`, `chunk_count`, `byte_size`, `ingested_at`.

`index_status`는 `indexed` | `stale` 둘뿐이다. `stale`은 **기동 시점에만** 붙는다 — 저장된 서명이 현재 색인 구성과 다르다는 뜻이고, 그 문서의 청크는 이미 제거된 상태다(결정 8의 기동 정리). 수집 경로가 `stale`을 만들지는 않는다. 상태를 레코드에 남기는 이유는 `chunk_count: 0` 하나만으로는 "빈 문서였나, 구성이 바뀐 건가"를 구분할 수 없기 때문이다. 앞의 경우는 애초에 수집이 거부되므로 존재할 수 없지만, 그 사실을 API 소비자가 알아야 할 이유는 없다.

```python
@runtime_checkable
class DocumentRegistry(Protocol):
    async def get(self, document_id: str) -> DocumentRecord | None: ...
    async def list_all(self) -> list[DocumentRecord]: ...
    async def commit(self, record: DocumentRecord) -> None: ...   # 단일 트랜잭션
    async def delete(self, document_id: str) -> DocumentRecord | None: ...
```

레지스트리도 벡터 스토어도 파일 I/O라 블로킹이다. 프로토콜은 async로 선언하고 구현체 내부에서 스레드풀로 오프로드한다 — 파서와 반대 방향의 선택인데, 이유가 다르다. 파서는 **호출부가 오프로드를 의식해야** 실수를 막을 수 있고(CPU 바운드, 수백 ms~초), 저장소는 호출부가 매번 감싸면 중복만 늘어난다(짧은 I/O, 어댑터가 책임지는 편이 자연스럽다).

> **구현 중 조정 — 벡터 스토어를 임베디드에서 Chroma 서버 모드로 옮긴다.** 이 change의 계획은 임베디드 퍼시스턴트 모드를 전제로 쓰였다(컨테이너를 늘리지 않는다는 앞 change의 결정). 요청에 따라 compose 서비스로 분리했고, 바뀐 사실은 넷이다.
>
> 1. **"도달 가능"의 의미가 캐시와 같아진다.** 저장 경로 쓰기 점검이 아니라 heartbeat다. 프로브가 그 모양으로 바뀌었다. 설정도 `vector_store_path`(경로) → `vector_store_url`(주소)로 바뀌었고, 주소 해석은 기동 시점에 하되 접속은 첫 사용까지 미룬다 — 오타는 기동을 막아야 하지만 서버 기동 여부는 기동 조건이 아니다.
> 2. **워커 1 프로세스 제약의 근거가 바뀐다.** 파일 락이 사라졌으므로 이제 그 제약을 강제하는 것은 결정 8의 `document_id` 단위 인메모리 잠금 하나뿐이다. 결론(워커 1개)은 그대로이고, 다중 워커 전환은 여전히 외부 잠금 도입이 선행 조건이다.
> 3. **블로킹의 성격이 파일 I/O에서 네트워크 I/O로 바뀐다.** 파이썬 클라이언트가 동기 HTTP라 오프로드 결정 자체는 그대로 유효하다.
> 4. **테스트 대가가 생긴다.** `tests/test_vector_store.py`는 실물 서버가 필요해, 서버가 없으면 건너뛴다. 대역으로 대체하면 그 파일이 확인하려는 것(메타데이터·필터·id 규약이 *실제 Chroma*에서 성립하는가)이 사라지므로 대체하지 않는다. `make test-all`이 서버를 띄운 뒤 전부 돌린다.
>
> 전환 중 실측으로 드러난 제약 하나를 함께 반영했다. **Chroma는 컬렉션당 벡터 차원 하나만 허용하고, 그 차원은 컬렉션을 비운 뒤에도 남는다.** 컬렉션 이름이 하나뿐이면 차원이 다른 모델로 바꿨을 때 기동 정리가 청크를 전부 지워도 재업로드가 영구히 실패해, spec의 "`stale` 문서는 재업로드로 복구된다"가 거짓이 된다. 그래서 컬렉션 이름에 차원을 붙인다(`document_chunks_d384`). 대가는 차원을 바꿨을 때 남는 버려진 컬렉션이며, 기동 정리는 현재 컬렉션만 보므로 회수하지 않는다.

### 8. 리비전 교체는 "새로 쓰고 → 커밋 → 지우기"이며, 실패하면 같은 요청 안에서 되돌린다

```
1. revision 계산, index_signature 조회 (현재 구성에서 유도된 값 — 요청과 무관하게 고정)
2. 레지스트리의 revision·index_signature가 둘 다 같으면
                                        →  아무것도 하지 않고 status="unchanged" 반환
3. 파싱 · 청킹                         (실패 시 여기서 중단 — 저장소는 손대지 않았다)
4. 새 (revision, index_signature) 청크를 배치 단위로 임베딩·저장
                                        (id 에 둘 다 들어가 기존 청크와 충돌하지 않는다)
5. 레지스트리 커밋                      ← 이 순간 교체가 확정된다
6. 이전 (revision, index_signature) 청크 삭제
```

2단계의 단축 조건이 **둘 다**인 것이 결정 6의 핵심 귀결이다. `revision`만 보면 모델이나 청킹을 바꾼 뒤 같은 파일을 다시 올려도 아무 일이 일어나지 않는다. 응답 `status`는 세 갈래다 — 내용이 바뀌면 `replaced`, 내용은 같고 서명만 바뀌면 `reindexed`, 둘 다 같으면 `unchanged`. `reindexed`를 `replaced`로 뭉개지 않는 이유는 `previous_revision`이 현재 `revision`과 같아져 응답이 자기모순이 되기 때문이다.

4 또는 5에서 실패하면 **서비스가 같은 요청 안에서** 이미 기록된 새 리비전 청크를 되돌린다 — `delete_document(document_id, revision=새 리비전)` 한 번이다. 되돌리기를 어댑터가 아니라 서비스에 두는 이유: 임베디드 벡터 스토어의 배치 쓰기는 트랜잭션을 보장하지 않으므로, 프로토콜에 "`add_chunks`는 원자적이어야 한다"고 적어도 구현이 지킬 수단이 없다. 지킬 수 없는 약속을 계약에 적는 대신, 교체 순서를 아는 곳이 되돌리기도 책임진다. 4단계가 배치로 나뉘면서 부분 기록의 폭이 커졌으므로 이 되돌리기는 선택이 아니다.

각 단계 실패의 결과:

| 실패 지점 | 결과 |
|----------|------|
| 3 (파싱·청킹) | 저장소 무변경. 이전 리비전 그대로 |
| 4 (임베딩·청크 쓰기) | 같은 요청 안에서 이미 기록된 새 리비전 청크를 되돌리고 `503 storage_unavailable`로 응답. 이전 리비전 그대로 |
| 5 (커밋) | 새 리비전 청크를 되돌리고 `503 storage_unavailable`. 이전 리비전 그대로 |
| 4·5의 되돌리기마저 실패 | 응답은 동일하게 `503 storage_unavailable`, 로그에 경고. 잔여 청크는 레지스트리가 가리키지 않아 검색 대상이 아니며, 다음 기동 시 정리가 제거한다 |
| 6 (이전 청크 삭제) | **교체는 이미 성립**. 이전 청크가 잔여물로 남지만 검색은 현재 `(revision, index_signature)`로 필터하므로 결과에 섞이지 않는다 |

역순(먼저 지우고 새로 쓰기)을 쓰면 중간 실패 시 문서가 **통째로 사라진다**. 답변할 수 있던 질문에 답할 수 없게 되는 것이 잔여 청크가 잠시 남는 것보다 훨씬 나쁘다.

#### 기동 시 저장소를 레지스트리에 맞춘다 — 규칙 둘

기동 정리는 두 가지 일을 한다. 성격이 달라 나눠 적는다.

**규칙 1 (크래시 백스톱)** — 레지스트리의 어떤 문서도 현재 값으로 가리키지 않는 `(document_id, revision, index_signature)` 청크를 지운다. 정합성 수단이 아니다. 요청 안의 되돌리기가 닿지 못하는 실패 — 프로세스 강제 종료, 되돌리기 자체의 실패 — 가 남긴 잔여물만 회수한다.

**규칙 2 (구성 변경 처리)** — 레지스트리에 기록된 `index_signature`가 현재 구성의 것과 다른 문서는 청크를 전부 지우고 `chunk_count = 0`, `index_status = "stale"`로 커밋한다.

규칙 2가 필요한 이유는 결정 6이 막은 구멍의 나머지 절반이다. `unchanged` 단축은 **재업로드가 있을 때만** 작동한다. 모델을 바꾸고 아무도 아무것도 올리지 않으면, 구 구성 벡터는 그대로 살아서 검색되고 아무도 그 사실을 모른다.

**원본 바이트를 보관하지 않으므로 자동 재색인은 불가능하다.** 선택지는 셋뿐이었다.

| 대안 | 판단 |
|---|---|
| 구 서명 벡터를 그대로 둔다 | 기각. 다른 의미 공간의 벡터가 검색에 섞여 답변 품질이 조용히 무너진다. 차원이 다르면 다음 쓰기에서 터진다 |
| 기동을 실패시킨다 | 기각. 데이터를 임의로 지우지 않는 장점은 있지만, 평가자가 설정을 한 번 만져 본 순간 "한 줄 실행"이 깨진다. 새 볼륨에서는 애초에 일어나지 않는 상황이라 보호 가치도 낮다 |
| **지우고 그 사실을 드러낸다** (선택) | 청크가 실제로 없으므로 **검색 계층이 별도 필터를 두지 않아도** 낡은 벡터가 답변에 섞이지 않는다. `index_status`가 무엇을 다시 올려야 하는지 알려 준다 |

세 번째의 값은 retrieval change에 아무 약속도 넘기지 않는다는 데 있다. "stale 문서는 검색에서 제외하라"는 규칙을 남기면 그 change가 지켜야 할 조건이 하나 늘고, 안 지켜도 테스트가 잡아 주지 않는다. 청크를 없애면 그 규칙 자체가 필요 없다.

대가는 재업로드 없이는 복구되지 않는다는 것이다. 이를 감수하는 대신 기동 로그에 영향받은 문서 목록을 경고로 남긴다. 원본 바이트를 레지스트리에 함께 보관해 자동 재색인하는 방안은 Open Questions에 남긴다.

**원자성은 여기서도 같은 순서를 쓴다** — 청크를 지우고 나서 레코드를 커밋한다. 사이에서 죽으면 다음 기동의 규칙 1이 회수한다. 반대로 하면 커밋 후 죽었을 때 `chunk_count: 0`인데 청크가 남아 있는, 아무도 지우지 않는 상태가 된다.

#### 같은 문서의 동시 요청은 document_id 단위 잠금으로 직렬화한다

위 순서는 한 요청 안에서만 성립한다. 같은 `document_id`의 요청 둘이 겹치면 `get → 저장 → 커밋 → 삭제`가 인터리빙되어, 마지막 커밋이 아닌 쪽의 청크가 잔여물이 되거나 삭제가 새 청크를 지운다. **전역 `CapacityLimiter`는 이를 막지 못한다** — 동시성 총량만 제한할 뿐 같은 문서 두 건을 그대로 통과시킨다.

그래서 수집 서비스가 `document_id`별 `asyncio.Lock`을 잡고 수집·삭제 유스케이스 **전체**를 그 안에서 실행한다. 잠금 구간은 레지스트리 조회부터 이전 청크 정리 완료까지다. 서로 다른 문서는 서로를 기다리지 않는다.

인메모리 잠금으로 충분한 근거는 워커가 **1 프로세스로 고정**돼 있다는 사실이다(임베디드 벡터 스토어의 파일 락 — `ARCHITECTURE.md`에 기록된 기존 결정). 레지스트리 compare-and-swap은 두지 않는다: 단일 프로세스에서는 잠금이 이미 직렬화를 보장해 CAS가 죽은 코드가 되고, 다중 프로세스에서는 CAS만으로 벡터 스토어 쓰기와의 원자성이 어차피 성립하지 않는다.

**다중 워커로 가는 순간 이 잠금이 가장 먼저 깨진다.** 그때는 벡터 스토어 파일 락 문제와 함께 외부 잠금으로 옮겨야 하며, 둘은 같은 change에서 다뤄야 한다. 이 경계를 `ARCHITECTURE.md`에 남긴다.

청크 id와 메타데이터:

```
id       = f"{document_id}:{revision[:12]}:{index_signature[:8]}:{chunk_index:05d}"
metadata = document_id, revision, index_signature, filename, format, chunk_index,
           char_start, char_end, page(PDF 만)
본문      = 청크 텍스트
```

**id 에 서명이 들어가야 하는 이유는 재색인 경로 때문이다.** 재색인은 `revision`이 그대로인 채 일어난다. id 가 `document_id:revision:index` 뿐이면 새 청크가 이전 청크의 id 를 그대로 덮어써, 결정 8의 "새로 쓰고 → 커밋 → 지우기" 순서가 성립하지 않는다. 4단계에서 이미 이전 벡터가 사라지고, 실패해도 되돌릴 원본이 없다. 서명을 붙이면 두 세대가 서로 다른 id 를 가져 순서가 그대로 지켜진다.

`page`는 값이 없으면 키 자체를 넣지 않는다. 임베디드 벡터 스토어가 널 메타데이터를 허용하지 않고, 센티널 값(-1 같은)을 쓰면 소비자가 그 규약을 알아야 한다.

### 9. 블로킹 작업은 세 지점에서 스레드풀로 나간다

| 지점 | 성격 | 오프로드 주체 |
|------|------|-------------|
| PDF·텍스트 파싱 | CPU 바운드, 문서 크기에 비례 | **서비스**가 명시적으로 오프로드 (결정 3) |
| 임베딩 인코딩 (모델 로딩 포함) | CPU 바운드, 가장 무겁다. 배치 단위로 반복 호출된다 | 어댑터 내부 |
| 레지스트리·벡터 스토어 파일 I/O | 짧은 블로킹 I/O | 어댑터 내부 (결정 7) |

`anyio.to_thread.run_sync`를 쓴다. FastAPI가 이미 anyio 위에서 돌고 있어 새 의존성이 아니다.

> **구현 중 조정**: 오프로드는 `asyncio.to_thread`, 동시성 상한은 `anyio.CapacityLimiter` 로 갈렸다. `asyncio.to_thread` 는 리미터를 인자로 받지 않으므로 둘을 한 라이브러리로 맞추려면 `anyio.to_thread.run_sync(..., limiter=...)` 로 통일해야 하는데, 그러면 **상한이 스레드 수에 걸린다.** 우리가 제한하려는 것은 스레드가 아니라 **수집 유스케이스의 동시 실행 수**다 — 수집 한 건은 파싱 한 번과 배치 수만큼의 인코딩·쓰기로 스레드를 여러 번 빌린다. 그래서 리미터는 `IngestionService.ingest` 전체를 감싸는 자리에 두고, 개별 오프로드는 표준 라이브러리를 그대로 쓴다. 리미터를 앱 팩토리(동기 함수)에서 만들어야 하는 제약도 확인했다 — `anyio.CapacityLimiter` 는 이벤트 루프 밖에서도 생성된다.

**동시 실행에 상한을 건다.** 무제한이면 업로드 여러 건이 동시에 들어올 때 스레드가 무한정 늘고, 각 스레드가 임베딩 모델을 돌려 CPU가 포화된다. `CapacityLimiter`로 수집 동시성을 제한한다(기본 2, 설정 항목). 상한에 걸린 요청은 실패하지 않고 대기한다.

**임베딩과 저장은 배치 단위로 진행한다.** 청크 전체를 한 번에 임베딩에 넘기지 않고 `embedding_batch_size`(기본 64, 설정 항목)씩 끊어 인코딩하고, 배치가 끝날 때마다 벡터 스토어에 쓴 뒤 이벤트 루프에 양보한다.

이건 큰 파일을 받기 위한 장치가 아니라 **지금 설계에 빠져 있던 것**이다. 업로드 상한(20 MiB) 안의 문서도 청크가 3만 개를 넘을 수 있고, 그걸 한 번에 인코딩하면 결과 벡터만 수십 MB에 모델 내부 버퍼가 더해진다. 배치로 끊으면 **메모리 사용량이 문서 크기가 아니라 배치 크기에 비례**하고, 배치 사이의 양보 덕분에 임베딩 단계도 다른 요청을 굶기지 않는다.

대가는 부분 기록의 폭이 커진다는 것이다 — 배치 k에서 실패하면 1..k-1 배치가 이미 저장돼 있다. 그래서 결정 8의 되돌리기가 필수가 된다.

이 성질을 문서가 아니라 **테스트로 고정**한다 — 지연을 주입한 스텁 파서·임베더로 수집을 진행시킨 상태에서 헬스를 호출하고, 이벤트 루프 시계로 잰 헬스 소요 시간이 **주입한 지연보다 짧다**고 단언한다.

절대 수치 상한이 아니라 상대 단언인 이유가 있다. 이 테스트가 판별할 것은 "이벤트 루프가 수집에 막혔는가"이고, 막히면 헬스 소요 시간이 주입한 지연만큼 늘어난다. 상대 단언은 CI 머신 속도와 무관하게 그 회귀만 결정론적으로 잡는다.

**새 설정을 만들지 않는다.** 헬스 응답 시간의 절대 상한을 설정 항목으로 두려면 그 값을 실제로 강제하는 코드가 있어야 하는데, 현재 `health_total_timeout_seconds`는 프로브 수집 단계(`asyncio.wait`)에만 걸리고 라우트·직렬화·미들웨어는 그 밖이다. 강제하지 않는 설정을 문서화하면 그 자체가 문서-코드 불일치다. 기존 `tests/test_health.py`의 루프 시계 측정 패턴을 그대로 쓴다.

### 10. 업로드 크기 상한은 스트리밍으로 강제한다

`Content-Length`가 있으면 먼저 본다(빠른 거절). 다만 클라이언트가 보낸 값이므로 신뢰하지 않고, **본문을 청크 단위로 읽으면서 누적 바이트가 상한을 넘는 순간 중단**하는 쪽을 실제 강제 수단으로 삼는다. 전체를 메모리에 올린 뒤 크기를 재면 상한의 목적 자체가 무의미해진다.

상한 초과는 파싱·임베딩 이전에 판정되므로, 큰 파일이 CPU를 쓰는 일은 없다.

> **구현 중 조정 — 스트리밍 강제를 철회하고 `UploadFile` + `file.size` 검사를 쓴다.**
>
> 위 방식은 `MultiPartParser`를 직접 구동하고 요청 스트림을 감싼 제너레이터로 누적 바이트를 세야 한다. 프레임워크의 표준 업로드 경로를 우회하는 대가로 얻는 것이 크지 않다고 판단했다(사용자 결정).
>
> **바뀐 것**: 상한이 막는 대상이 **수신**에서 **파싱·임베딩**으로 바뀐다. `UploadFile`은 핸들러가 불릴 때 본문이 이미 수신된 뒤이므로, 21 MB 요청도 일단 받은 뒤 413으로 끝난다(측정 9 ms, 파서 미도달).
>
> **바뀌지 않은 것**: 메모리는 여전히 문서 크기에 묶이지 않는다 — Starlette이 1 MiB를 넘는 파트를 디스크로 스풀한다. "큰 파일이 CPU를 쓰지 않는다"도 그대로다. 상한은 여전히 설정 항목이고 응답에 실린다.
>
> **비용**: 수신 자체를 끊으려면 리버스 프록시의 `client_max_body_size` 같은 앞단 상한이 함께 있어야 한다. 이 서비스 코드만으로는 그 층을 대신할 수 없다는 사실을 `ARCHITECTURE.md`에 적는다.
>
> 상한을 재는 대상은 요청 본문이 아니라 **파일**이다. 본문에 걸면 상한에 꼭 맞는 파일이 multipart 봉투 몇백 바이트 때문에 거절되어, 응답이 알려주는 상한과 실제 동작이 어긋난다.

**이 상한이 막는 것은 메모리가 아니라 시간이다.** 메모리는 결정 9의 배치 처리가 이미 문서 크기와 무관하게 만들었다. 그럼에도 상한이 남는 이유는 결정 1의 동기 수집 때문이다 — 임베딩 총량은 배치로 쪼개도 줄지 않으므로, 충분히 큰 문서는 배치로 처리해도 HTTP 타임아웃을 넘긴다.

바꿔 말하면 **상한을 없애려면 배치 처리가 아니라 작업 큐가 필요하다.** 그 교체 지점은 결정 1에 이미 적혀 있다. 상한 안에서 문서를 여러 논리 문서로 쪼개 받는 방식도 기각한다 — `document_id`가 하나여야 출처 표기와 재업로드 교체가 성립하는데, 쪼개면 그 전제가 무너진다.

### 11. 새 오류 코드와 오류 봉투 확장

`ErrorCode`에 항목을 **추가**한다. 기존 값과 봉투 구조는 바꾸지 않는다(앞 change의 규약).

| 도메인 예외 | HTTP | code |
|------------|-----:|------|
| `UnsupportedDocumentFormat` | 415 | `unsupported_document_format` |
| `DocumentTooLarge` | 413 | `document_too_large` |
| `EmptyDocument` | 422 | `empty_document` |
| `NoExtractableText` | 422 | `no_extractable_text` |
| `DocumentParseError` | 422 | `document_parse_error` |
| `DocumentNotFound` | 404 | `not_found` (기존 코드 재사용) |
| `StorageUnavailable` | 503 | `storage_unavailable` |

spec은 오류 응답에서 **지원 포맷 목록**과 **적용된 크기 상한**을 확인할 수 있어야 한다고 요구한다. 메시지 문자열에 섞으면 소비자가 파싱해야 하므로 구조화된 필드로 싣되, **새 중첩 객체를 만들지 않고 기존 관습을 따른다.** `api/errors.py`의 `error_response(status, code, message, **extra)`는 추가 항목을 이미 `error` 객체 안에 평평하게 넣고 있고, 검증 오류의 `fields`가 그 방식이다. 같은 봉투에 형식이 두 가지면 소비자가 파서를 둘 들어야 한다.

```json
{ "error": { "code": "unsupported_document_format",
             "message": "지원하지 않는 문서 포맷입니다",
             "supported_formats": ["txt", "md", "pdf"] } }
```

구조화 필드는 도메인 예외가 나른다 — `AppError`에 선택적 `extra` 매핑을 추가하고, 핸들러가 `error_response(..., **exc.extra)`로 옮긴다. 담기는 값은 포맷 목록·바이트 수 같은 도메인 사실뿐이라 `core/`가 HTTP를 알게 되는 것은 아니다.

기존 422 검증 오류의 `fields`는 그대로 둔다. 이미 나가 있는 형식을 바꾸면 앞 change의 테스트가 깨지고, 봉투 안정성이라는 원래 의도에도 반한다.

**상태 코드 변환에는 손볼 곳이 하나 있다.** 현재 `handle_app_error`는 모든 `AppError`를 **무조건 500으로** 변환한다 — `AppError`에는 상태 코드 개념이 없고 `code`만 있다. 위 표의 415/413/422/404/503을 내보내려면 `api/errors.py`에 `ErrorCode → HTTP 상태` 표를 두고 핸들러가 조회해야 한다. 표를 도메인이 아니라 API 계층에 두는 것은 "도메인 예외의 HTTP 변환은 API 계층에서만"이라는 기존 규약 그대로다. 표에 없는 코드는 지금처럼 500이므로, 기존 예외의 동작과 `tests/test_errors.py`가 고정한 봉투는 바뀌지 않는다.

**`empty_document`와 `no_extractable_text`를 나누는 이유**는 spec에 적힌 그대로다 — 클라이언트가 "파일이 잘못됐다"와 "OCR이 필요하다"를 구분할 수 있어야 한다. 판정은 `ExtractedDocument.page_count`로 한다: 쪽이 1 이상인데 추출 텍스트가 비면 텍스트 레이어 부재, 쪽 자체가 없거나 바이트가 없으면 빈 문서.

### 12. 계층 배치

```
api/routes/documents.py     업로드 수신, 크기 상한 강제, 응답 직렬화. 도메인 로직 없음
api/errors.py               새 예외 → HTTP 매핑 추가 (변환은 여전히 이 계층에서만)
services/ingestion.py       파서 선택 → 파싱(오프로드) → 청킹 → 토큰 가드 → 임베딩 → 저장 → 커밋 → 정리
core/chunking.py            전략 레지스트리 + recursive 분할 알고리즘. 순수 함수, 외부 라이브러리 없음
core/documents.py           Document·Chunk 값 객체, document_id·revision·index_signature 유도 규칙
core/exceptions.py          새 도메인 예외 추가
adapters/protocols.py       DocumentParser · Embedder · VectorStore · DocumentRegistry 추가
adapters/parsers/           text.py (txt·md) · pdf.py
adapters/embedding/         로컬 모델 어댑터
adapters/vector_store/      쓰기·삭제·집계 구현 (query 는 retrieval change 에서)
adapters/registry/          SQLite 구현
```

`core/`가 외부 라이브러리를 import 하지 않는다는 규칙은 린트로 이미 강제돼 있다. 청킹이 `core/`에 있는 것은 그 규칙을 지킬 수 있기 때문이고(순수 문자열 연산), 토큰 계산이 어댑터에 있는 것은 지킬 수 없기 때문이다.

### 13. 테스트에서 임베딩을 실물로 돌리지 않는다 — ingestion 한정

`openspec/config.yaml`의 테스트 전략은 "임베딩은 목이 아니라 실물로 돌린다"고 적고 있다. **ingestion 테스트에 한해 이 방침에서 벗어난다.** 바꾼 이유를 남긴다.

- ingestion이 검증하는 것은 **저장 결과의 모양**이다 — 청크 수, 위치 정보, 리비전 교체, 오류 경로. 벡터의 *의미*는 하나도 검증하지 않는다. 실제 모델을 돌려도 단언이 강해지지 않는다.
- 반면 비용은 크다. 모델 가중치가 캐시되지 않은 환경에서 `pytest` 한 줄을 실행하면 수백 MB를 내려받는다. "한 줄로 테스트가 돈다"가 네트워크에 묶인다.

그래서 ingestion 테스트는 **결정론적 페이크 임베더**(텍스트 해시 기반 고정 차원 벡터)를 주입한다. 이 페이크는 `signature`·`dimension`을 생성 시점에 지정할 수 있어야 한다 — 결정 6의 "모델 정체성이 바뀌면 서명이 바뀐다"와 기동 시 `stale` 처리를 실제 모델 없이 검증하는 유일한 수단이다. 실제 모델이 정말로 붙는지는 별도로 확인한다 — 컨테이너 이미지에 모델이 구워져 있으므로, 모델이 있을 때만 실행되고 없으면 스킵하는 통합 테스트 하나가 실제 어댑터로 차원과 접두사 규약을 단언한다.

**검색 품질을 실물 모델로 검증하는 것은 retrieval change의 몫이다.** 거기서는 벡터의 의미가 검증 대상 그 자체이므로 페이크로 대체할 수 없다.

PDF 픽스처는 리포에 바이너리로 넣지 않고 테스트 시점에 생성한다 — 텍스트 레이어가 있는 PDF와 이미지만 있는 PDF 둘 다. 바이너리 픽스처는 무엇이 들었는지 diff로 보이지 않아, 실패했을 때 원인 추적이 어렵다.

## Risks / Trade-offs

**[이미지 크기와 빌드 시간이 늘어난다]** → 임베딩 런타임과 모델 가중치가 더해진다. CPU 전용 휠로 GPU 런타임을 빼고, 모델 다운로드를 별도 레이어로 분리해 코드 변경 시 재다운로드가 없게 한다. 그래도 문제가 되면 ONNX 기반 임베딩으로 교체하며, 범위는 어댑터 한 파일이다.

**[선로딩이 기동 시간을 늘린다]** → 가중치가 로컬에 없으면 기동이 다운로드만큼 길어진다. 컨테이너는 빌드 단계에서 굽기 때문에 이 경로가 없고, 도커 없이 로컬로 띄우는 경우에만 해당한다. 실패는 경고로 끝나고 지연 초기화가 백스톱으로 남으므로 **기동이 실패하지는 않는다** — 늘어나는 것은 시간뿐이다. 반대로 선로딩을 두지 않으면 그 비용이 사라지는 게 아니라 첫 업로드에게 청구되고, 가중치·차원 선언의 문제가 첫 업로드에서 500으로 드러난다.

**[되돌리기가 닿지 못한 잔여 청크]** → 저장·커밋 실패는 같은 요청 안의 되돌리기가 지운다. 프로세스 강제 종료나 되돌리기 자체의 실패만 잔여 청크를 남기는데, 레지스트리가 가리키지 않아 검색에 섞이지 않고 기동 시 정리가 공간을 회수한다. 반대 순서(먼저 지우기)는 문서가 통째로 사라지는 훨씬 나쁜 실패이므로 이쪽을 감수한다.

**[document_id 잠금이 프로세스 로컬이다]** → 워커 1 프로세스 고정이라는 기존 결정 위에서만 성립한다. 다중 워커로 가면 이 잠금과 임베디드 벡터 스토어 파일 락이 함께 깨지므로, 그 전환은 외부 잠금 도입과 벡터 스토어 교체를 묶은 별도 change가 된다. 경계를 `ARCHITECTURE.md`에 명시한다.

**[`CHUNK_STRATEGY_VERSION`을 손으로 올려야 한다]** → 분할 알고리즘을 고치면서 이 상수를 안 올리면 서명이 그대로여서 재색인이 일어나지 않고, 구 경계 청크와 신 경계 청크가 섞인다. 결정 6이 막으려던 바로 그 실패가 다른 경로로 돌아온다. 자동 유도(소스 해시)는 주석 수정에도 반응해 무의미한 전면 재색인을 부르므로 택하지 않았다. 대신 `core/chunking.py` 상단 주석과 청킹 테스트에 "경계가 바뀌는 수정을 하면 이 상수를 올린다"를 명시하고, `ARCHITECTURE.md`에도 남긴다. 규율에 의존하는 지점임을 인정한다.

**[구성이 바뀐 문서는 재업로드해야만 복구된다]** → 원본 바이트를 보관하지 않으므로 기동 시 `stale` 처리는 청크를 지우는 데서 끝난다. 그 문서는 다시 올릴 때까지 답변 근거가 되지 못한다. 대안(원본 보관 후 자동 재색인)은 blob 저장과 기동 시 대량 임베딩을 이 change에 들여오므로 미뤘고, Open Questions에 남겼다. 지금은 기동 로그 경고와 `index_status`로 드러내는 것이 최선이다.

**[배치 크기가 처리량과 응답성을 맞바꾼다]** → 배치가 작으면 양보가 잦아 다른 요청이 잘 살지만 임베딩 처리량이 떨어지고, 크면 반대다. 기본 64는 두 목적의 절충이며 설정 항목이므로, 검색 품질 측정과 함께 retrieval change에서 재조정될 수 있다.

**[큰 PDF 하나가 스레드를 오래 점유한다]** → 업로드 크기 상한과 동시성 상한으로 묶는다. 수집 시간이 HTTP 타임아웃에 근접하면 그때가 작업 큐 도입 시점이며, 교체 지점은 `IngestionService` 호출부 한 곳이다.

**[같은 파일명의 다른 문서가 서로를 덮어쓴다]** → 의도된 동작이지만 사고의 여지가 있다. 조용히 일어나지 않도록 응답의 `status`와 `previous_revision`으로 드러내고, spec 시나리오로 고정한다.

**[PyMuPDF의 AGPL 라이선스]** → 평가용 비공개 리포 범위에서는 문제가 되지 않는다. 상용 배포로 갈 경우 pypdf 교체가 선행되어야 하며, 교체 범위가 어댑터 한 파일이라는 점이 이 구조의 값이다. `ARCHITECTURE.md`에 명시한다.

**[문자 기준 청크가 토큰 창을 넘을 수 있다]** → 언어에 따라 문자당 토큰 수가 다르다. 임베딩 직전 토큰 가드가 잡아 재분할한다. 가드가 없으면 조용한 절단이 되어, 저장은 됐는데 검색되지 않는 텍스트가 생긴다.

**[SQLite가 스택에 추가된다]** → 문서에 없던 구성 요소가 늘어난다. 표준 라이브러리라 배포 비용은 없지만, `ARCHITECTURE.md`에 추가 이유를 적지 않으면 문서-코드 불일치가 된다. tasks에 문서 갱신을 명시적으로 넣는다.

## Migration Plan

기존 데이터가 없는 신규 기능이라 마이그레이션 대상이 없다. SQLite 스키마는 최초 접근 시 생성한다. 이후 색인 구성이 바뀌는 경우의 이행은 결정 8의 기동 정리가 담당한다 — 별도 마이그레이션 절차를 두지 않는 것이 그 설계의 목적이다. 되돌리려면 change를 되돌리고 볼륨의 레지스트리 파일과 벡터 스토어 디렉터리를 지우면 된다.

## Open Questions

- **청크 크기·겹침 기본값(600자/100자)이 적정한가.** 검색 품질을 실측해야 답이 나오고, 그 측정은 retrieval change에서 이루어진다. 두 값 모두 설정 항목이므로 조정이 spec·설계·태스크 어느 것도 바꾸지 않는다.
- **원본 바이트를 레지스트리에 함께 보관해 구성 변경 시 자동 재색인할 것인가.** 그러면 `stale`이 사라지고 데이터 손실도 없다. 대가는 blob 저장(문서 수십 건 × 최대 20 MiB)과 기동 시 대량 임베딩이며, 후자는 "기동 조건을 늘리지 않는다"는 규약과 정면으로 부딪힌다. 판단은 실제 운영에서 구성이 얼마나 자주 바뀌는지에 달렸고, 지금은 그 데이터가 없다. `index_status`를 남겨 두었으므로 나중에 붙일 때 API 형태는 바뀌지 않는다.
- **부모-자식 청킹을 언제 붙일 것인가.** 결정 2의 전략 레지스트리에 항목 하나를 더하는 일이지만, 이득이 나오는 곳은 검색된 자식을 부모로 확장하는 단계다. retrieval change가 질의 경로를 만든 뒤 샘플 문서로 재고 판단한다. 부모 텍스트를 청크 메타데이터에 넣을지 별도 저장소에 둘지도 그때 정한다.
- **잔여 청크 정리를 기동 시점 외에 주기적으로도 돌릴 것인가.** 정확성이 아니라 공간 문제이고(요청 안의 되돌리기가 정합성을 이미 담당한다), 문서 수십 건 규모에서는 기동 시 1회로 충분하다. 필요해지면 붙인다.
