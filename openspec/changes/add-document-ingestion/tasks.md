## 1. 설정과 도메인 값 객체

- [x] 1.1 설정 항목 추가 — 임베딩 모델 이름, **분할 전략**(`chunk_strategy`, 기본 `recursive`), 청크 크기·겹침, **임베딩 배치 크기**(기본 64), 업로드 크기 상한, 레지스트리 경로, 수집 동시성 상한. 전부 기본값을 두어 "설정 없이 기동된다"는 기존 요구사항을 깨지 않는다. **`index_signature`는 설정 항목이 아니다** — 유도값이다 (design 결정 6)
- [x] 1.2 설정 테스트 — 새 항목 없이도 기동되고 전략이 `recursive`인지 / 무효값(음수 청크 크기, 겹침 ≥ 청크 크기, 배치 크기 0)이면 기동에 실패하는지 / **구현되지 않은 전략 값이면 기동에 실패하고 오류 메시지에 받아들여지는 값 목록이 나오는지** (spec "구현되지 않은 전략 값은 기동을 막는다")
- [x] 1.3 `core/documents.py` — `Document`·`Chunk`·`ChunkLocation` 값 객체. **dataclass + 표준 라이브러리만** 사용한다. `core/`는 pydantic도 금지돼 있다
- [x] 1.4 `document_id`·`revision` 유도 규칙 구현 — 파일명 정규화(경로 제거 → NFC → 소문자) 후 uuid5, 원본 바이트 sha256 (design 결정 6)
- [x] 1.5 유도 규칙 테스트 — 같은 파일명은 같은 id / 대소문자·NFD·NFC 차이가 같은 id / 파일명이 다르면 다른 id / 내용 1바이트 차이가 다른 revision (spec "문서 식별자는 파일명에서, 리비전은 내용에서 결정된다")
- [x] 1.6 `index_signature` 유도 규칙 구현 — `core/documents.py`의 순수 함수. 재료는 임베더 `signature` + 전략 이름 + `CHUNK_STRATEGY_VERSION` + 청크 크기 + 겹침. 정규 문자열로 이어 붙여 sha256 후 앞 16자 (design 결정 6)
- [x] 1.7 `index_signature` 테스트 — 재료가 같으면 같은 값 / 재료 하나씩 바꿀 때마다 값이 달라짐(모델 식별자·차원·정규화·접두사 규약·전략 이름·전략 버전·크기·겹침 각각) / **문서 내용과 파일명이 달라도 값이 같음** / **배치 크기·업로드 상한·동시성 상한은 재료가 아님** (spec "색인 서명은 저장 시점의 색인 구성에서 결정된다")
- [x] 1.8 `core/exceptions.py`에 도메인 예외 추가 — `UnsupportedDocumentFormat`·`DocumentTooLarge`·`EmptyDocument`·`NoExtractableText`·`DocumentParseError`·`DocumentNotFound`·`StorageUnavailable`. 아울러 `AppError`에 **선택적 `extra` 매핑**을 추가한다(지원 포맷 목록·크기 상한을 오류 응답까지 나르는 통로, design 결정 11). `ErrorCode`에는 항목을 **추가만** 하고 기존 값을 바꾸지 않는다
- [x] 1.9 `src/app/core/.ruff.toml`의 금지 목록에 PDF 파서·임베딩 라이브러리 추가 — `core/`가 새 어댑터 의존성을 import 하지 못하게 한다. **자식 `banned-api` 테이블은 부모를 대체하므로** 기존 항목(`os.environ`·`os.getenv`·`fastapi`·`pydantic`·…)을 그대로 다시 나열해야 한다. 규칙을 컨벤션이 아니라 도구로 강제한다는 기존 방침의 연장

## 2. 청킹 (core, 순수 함수)

- [x] 2.1 전략 레지스트리 — `(전략 이름) → 분할 함수` 매핑과 `CHUNK_STRATEGY_VERSION` 상수를 `core/chunking.py`에 둔다. 함수 시그니처는 `(segments, size, overlap) -> tuple[TextChunk, ...]`로 통일한다(정체성은 `identify_chunks`가 나중에 붙인다). **등록된 전략은 `recursive` 하나이며**, 미등록 이름은 기동 시 실패한다. 상수 옆에 "경계가 바뀌는 수정을 하면 이 값을 올린다"를 주석으로 남긴다 (design 결정 2·6)
- [x] 2.2 `recursive` 전략 구현 — 구분자 우선순위 재귀 분할: 문단 → 줄 → 한국어 문장 종결 → 영어 문장 종결 → 공백 → 문자 (design 결정 2)
- [x] 2.3 겹침 처리 — 인접 청크가 원문 구간에서 겹치도록. 겹침이 청크 크기 이상이면 무한 루프가 되므로 방어
- [x] 2.4 세그먼트 단위 분할 — 청크가 세그먼트(= PDF 쪽) 경계를 넘지 않게 한다. 넘으면 페이지 출처가 모호해진다
- [x] 2.5 재분할 함수 — 이미 만들어진 청크를 더 작게 쪼갠다 (6.4 토큰 가드가 호출)
- [x] 2.6 청킹 테스트 — 상한보다 짧은 문서는 청크 1개이고 본문이 원문(앞뒤 공백 제거)과 같음 / 긴 문서는 2개 이상이고 모든 청크가 상한 이하 / 인접 청크의 원문 구간이 겹침 / **원문의 모든 비공백 문자가 어느 청크엔가 포함됨** / 공백 없는 긴 토큰도 상한을 지킴 (spec "청크는 설정된 크기 상한을 넘지 않고 인접 청크는 겹친다")
- [x] 2.7 `ARCHITECTURE.md`에 청킹 전략 기록 — 전략을 설정 선택지로 둔 이유와 **이번에 구현한 것은 `recursive` 하나뿐이라는 사실**(부모-자식은 retrieval 이후로 미룬 이유와 붙일 자리까지. "지원"으로 적지 않는다), 구분자 우선순위, 기본값(600자/100자)의 근거, 페이지 경계를 넘지 않는 이유, 기각한 대안(고정 길이·문장 단위·시맨틱 청킹), `CHUNK_STRATEGY_VERSION`을 손으로 올려야 한다는 규율. **구현 직후에 적는다**

## 4. 임베딩 어댑터

- [x] 4.1 `Embedder` 프로토콜 정의 — `dimension`·`max_input_tokens`·**`signature`**·`embed_documents`·`embed_query`·`count_tokens` (design 결정 5)
- [x] 4.2 로컬 모델 어댑터 구현 — `intfloat/multilingual-e5-small`. `passage: `/`query: ` 접두사를 **어댑터 안에 가둔다**. 상위 계층에 노출하지 않는다. `signature`는 `모델식별자/차원/정규화/접두사규약버전` 형태의 사람이 읽을 수 있는 문자열로 노출한다 — 접두사 규약을 캡슐화한 채 색인 서명의 재료를 내보내는 유일한 통로다
- [x] 4.3 **모델 선로딩** — `Embedder` 프로토콜에 `warm_up()` 을 추가하고, 어댑터가 **가중치 로딩 + 짧은 텍스트 1회 인코딩**까지 수행한다. 로딩은 블로킹이므로 어댑터 안에서 스레드풀로 나간다. **지연 초기화는 걷어내지 않고 백스톱으로 남긴다** — 선로딩이 실패해도 첫 임베딩 호출이 다시 시도해야 일시적 실패가 스스로 회복된다 (design 결정 5)
- [x] 4.4 인코딩을 스레드풀로 오프로드 — 서비스가 배치 단위로 반복 호출하므로 호출당 오프로드가 성립해야 한다
- [x] 4.5 테스트용 결정론적 페이크 임베더 — 텍스트 해시 기반 고정 차원 벡터. ingestion 테스트의 기본 주입 대상이며, **`signature`·`dimension`을 생성 시점에 지정**할 수 있어야 한다(모델 교체 상황을 실제 모델 없이 재현하는 유일한 수단). **지연 주입**도 지원해 8.2에서 쓴다. `warm_up()` 은 no-op 으로 구현하되 **호출 여부를 기록**한다 — 배선이 정말로 부르는지를 확인할 수단이 있어야 한다 (design 결정 5·13)
- [x] 4.6 실제 모델 통합 테스트 1개 — 모델이 로컬에 없으면 스킵. 차원 일치, 접두사 규약이 실제로 붙는지, `signature`가 실제 모델 식별자·차원과 어긋나지 않는지 확인. 이게 없으면 페이크만 검증한 셈이 된다
- [x] 4.7 `ARCHITECTURE.md`에 임베딩 모델 선택 이유 기록 — 다국어·512 토큰 창·크기. 후보들을 왜 기각했는지 포함 (영어 전용 모델, 128 토큰 창 모델의 조용한 절단 문제)
- [x] 4.8 앱 팩토리 lifespan 에서 `warm_up()` 호출 — `reconcile_storage` **보다 먼저**. 오래 걸리는 쪽을 먼저 두어야 기동 로그가 무엇을 기다리는 중인지 순서대로 말한다. **실패는 경고만 남기고 기동을 계속한다** — `openspec/specs/service-health/spec.md` 의 "설정 없이 기동 성공"이 유효하고, 기동 정리가 이미 같은 규율을 쓴다. 배선은 프로토콜만 알아야 하므로 `isinstance` 로 구체 어댑터를 확인하지 않는다 (design 결정 5)
- [x] 4.9 선로딩 테스트 — 대역이 `warm_up()` 을 실제로 받았는지(lifespan 을 태운 앱으로) / **선로딩이 실패해도 기동이 성공하고 헬스가 200 인지** / 그 뒤 첫 업로드가 여전히 성공하는지(지연 초기화 백스톱) / 실제 어댑터의 `warm_up` 이 모델을 올리고 인코딩까지 했는지(느린 모델 대역으로, 가중치 없이). **기동을 실패시키지 않는다**가 이 묶음에서 가장 중요한 단언이다
- [x] 4.10 `ARCHITECTURE.md` 에 선로딩 기록 — 지연 초기화에서 **선로딩으로 바꾼 이유**(첫 업로드에 비용이 청구되는 문제, 가중치·차원 선언 불일치가 첫 업로드에서야 드러나는 문제), 범위가 인코딩 1회까지인 이유, 실패해도 기동을 막지 않는 이유와 백스톱, 헬스가 모델 상태를 보고하지 않는 이유. **앞 문서가 '기동 경로에서 로딩하지 않는다'고 적고 있으므로 반드시 함께 고친다** — 안 고치면 문서-코드 불일치다

## 5. 저장소 — 레지스트리와 벡터 스토어

- [x] 5.1 `DocumentRegistry` 프로토콜과 SQLite 구현 — `get`·`list_all`·`commit`(단일 트랜잭션)·`delete`. 레코드에 **`index_signature`·`index_status`**(`indexed` | `stale`) 포함. 스키마는 최초 접근 시 생성 (design 결정 7)
- [x] 5.2 레지스트리 파일 I/O를 스레드풀로 오프로드
- [x] 5.3 레지스트리 테스트 — 커밋 후 조회 / 같은 문서 재커밋이 리비전을 교체 / **서명만 다른 재커밋이 서명을 교체** / 삭제 후 조회 불가 / 스키마 자동 생성 / 프로세스를 새로 열어도 값이 남아 있음
- [x] 5.4 `VectorStore` 프로토콜 정의 — `add_chunks`·`delete_document(revision·index_signature 각각 선택)`·`count_chunks`·저장된 `(revision, index_signature)` 조합 목록 조회(6.10 기동 정리용). **`query`는 정의하지 않는다** — retrieval change가 자기 요구를 알고 정한다 (design Non-Goals)
- [x] 5.5 벡터 스토어 쓰기 구현 — 청크 id `{document_id}:{revision[:12]}:{index_signature[:8]}:{index:05d}`, 메타데이터(document_id·revision·**index_signature**·filename·format·chunk_index·char_start·char_end, PDF 만 page). 값이 없는 키는 넣지 않는다. **id 에 서명이 없으면 재색인이 이전 청크를 덮어써 결정 8의 순서가 깨진다** (design 결정 8)
- [x] 5.6 리비전·서명 단위 삭제와 문서 단위 삭제 구현 — 문서 단위 삭제는 `revision`·`index_signature`가 무엇이든 전부 지운다
- [x] 5.7 벡터 스토어 테스트 — 저장한 청크 수와 `count_chunks` 일치 / 메타데이터 왕복(서명 포함) / 리비전만 지정한 삭제가 다른 리비전을 건드리지 않음 / **서명만 지정한 삭제가 다른 서명을 건드리지 않음** / **같은 revision·다른 서명의 청크가 서로 덮어쓰지 않고 공존** / 문서 단위 삭제가 모든 조합을 지움 / 존재하지 않는 문서 삭제가 0을 반환
- [x] 5.8 `ARCHITECTURE.md`에 **레지스트리를 별도로 둔 이유** 기록 — 스택 표에 없던 구성 요소를 추가하는 결정이므로, 대안(벡터 메타데이터 유도 / 캐시 저장소 / 별도 DB 컨테이너)을 기각한 이유까지 남긴다. 적지 않으면 문서-코드 불일치가 된다

- [x] 6.3 빈 문서 / 텍스트 레이어 없는 PDF 판정 — `page_count` ≥ 1 인데 추출 텍스트가 비면 `NoExtractableText`, 그 외 비면 `EmptyDocument`. 두 코드를 뭉개지 않는다
- [x] 6.4 토큰 가드 — 임베딩 직전 `count_tokens`로 확인하고 초과 청크를 2.5로 재분할. 조용한 절단을 막는다 (design 결정 5)
- [x] 6.5 `unchanged` 경로 — 레지스트리의 `revision`과 `index_signature`가 **둘 다** 같을 때만 파싱·임베딩·저장을 전부 건너뛴다. `revision`만 같고 서명이 다르면 재색인하고 `status: "reindexed"`로 응답한다. **`revision`만 보고 단축하면 모델 교체 후 재업로드가 조용히 무시된다** (design 결정 6·8)
- [x] 6.6 **배치 단위 임베딩·저장** — 청크를 `embedding_batch_size`씩 끊어 인코딩하고 배치마다 벡터 스토어에 쓴 뒤 이벤트 루프에 양보한다. 메모리가 문서 크기가 아니라 배치 크기에 비례해야 한다 (design 결정 9)
- [x] 6.7 리비전 교체 — 새 청크 저장 → 레지스트리 커밋 → 이전 `(revision, index_signature)` 청크 삭제 순서. **저장·커밋 실패 시 같은 요청 안에서 새 리비전 청크를 되돌리고** `StorageUnavailable`로 끝낸다. 되돌리기 실패는 로그 경고만 남기고 응답 코드는 그대로 둔다. 배치 저장이라 부분 기록의 폭이 크므로 이 되돌리기가 필수다 (design 결정 8)
- [x] 6.8 **`document_id` 단위 잠금** — 수집·삭제 유스케이스 전체를 같은 문서끼리 직렬화한다(레지스트리 조회부터 이전 청크 정리 완료까지). 서로 다른 문서는 병렬을 유지한다. 워커 1 프로세스 전제이며 다중 워커 경계는 6.16에서 문서화 (design 결정 8)
- [x] 6.9 문서 삭제 유스케이스 — 레지스트리에서 지우고 벡터 스토어의 청크를 `revision`·`index_signature` 구분 없이 전부 제거
- [x] 6.10 기동 시 저장소 정합 — **규칙 1**: 레지스트리가 현재 값으로 가리키지 않는 `(document_id, revision, index_signature)` 청크 제거(크래시 백스톱). **규칙 2**: 기록된 `index_signature`가 현재 구성과 다른 문서는 청크를 전부 지우고 `chunk_count = 0`·`index_status = "stale"`로 커밋. 순서는 **지우고 나서 커밋** — 반대로 하면 중간에 죽었을 때 아무도 지우지 않는 잔여물이 생긴다. 어느 경우에도 기동이 실패하지 않아야 하며, 영향받은 문서 목록을 경고 로그로 남긴다 (design 결정 8)
- [x] 6.11 기동 정리 테스트 — 잔여 청크가 제거되고 현재 값 청크는 보존됨 / 구성을 바꿔 재기동하면 `chunk_count` 0 · `index_status` `stale` · 청크 0이고 **기동은 성공** / 구성이 그대로면 청크가 유지됨 / 서명이 일치하는 다른 문서는 무영향 / `stale` 문서를 재업로드하면 `reindexed`로 복구 (spec "기동 시 저장소를 레지스트리에 맞춘다")
- [x] 6.12 수집 동시성 상한 — `CapacityLimiter`. 상한 초과 요청은 실패하지 않고 대기 (design 결정 9). 같은 문서 직렬화는 이것이 아니라 6.8이 담당한다는 점을 코드 주석으로 남긴다
- [x] 6.13 실패 주입 대역 — `tests/stubs.py`에 `add_chunks`·`delete_document` 실패를 각각 지정할 수 있는 벡터 스토어 스텁과, 지연을 주입할 수 있는 파서 스텁을 추가한다 (기존 `StubProbe`의 주입 패턴을 따른다)
- [x] 6.14 서비스 테스트 (재업로드) — 내용이 바뀐 재업로드가 `replaced`이고 이전 리비전 청크가 0 / 짧은 문서로 교체 시 청크가 누적되지 않음 / 바이트 동일 + 서명 동일 재업로드가 `unchanged`이고 `ingested_at` 불변 / **바이트 동일 + 서명 변경 재업로드가 `reindexed`이고 `revision` 유지·`index_signature` 변경·이전 서명 청크 0** / **새 청크 저장 실패 시 503 `storage_unavailable`이 반환되고 이전 리비전이 그대로이며 새 리비전 청크가 0개** / **되돌리기까지 실패해도 503이고 이전 리비전 보존** (spec "같은 문서의 재업로드는 교체이며 이전 청크를 남기지 않는다". 기동 정리는 6.11이 덮는다)
- [x] 6.15 서비스 테스트 (오류 경로) — 빈 문서 / 공백만 있는 문서 / 스캔본 PDF가 서로 다른 예외 / **실패한 업로드가 기존 문서의 리비전·청크를 건드리지 않음**
- [x] 6.16 `ARCHITECTURE.md`에 수집 파이프라인 기록 — 리비전 교체 순서와 되돌리기, `document_id` 잠금과 **다중 워커로 갈 때 깨지는 지점**, 스레드풀 오프로드 3지점, 배치 처리와 상한이 막는 것(메모리가 아니라 시간), **`index_signature`가 무엇을 재료로 삼고 무엇을 배제하는지**, 구성 변경 시 기동 정리가 하는 일과 `stale`이 재업로드로만 복구된다는 사실(원본 바이트를 보관하지 않는 대가), 기동 정리 규칙 1의 성격(백스톱). **구현 직후에 적는다**

## 7. API 계층

- [x] 7.1 `POST /documents` — multipart 업로드. 성공 시 `document_id`·`filename`·`format`·`revision`·**`index_signature`**·**`index_status`**·`chunk_count`·`ingested_at`·`status` 반환. 최초 수집 201, 교체·재색인·무변경 200. `status`는 `created`|`replaced`|`reindexed`|`unchanged`
- [x] 7.2 업로드 크기 상한 — `UploadFile` 주입 후 `file.size`가 설정 상한을 넘으면 `DocumentTooLarge`. **상한이 막는 것은 수신이 아니라 파싱·임베딩이다**(design 결정 10의 구현 중 조정). 재는 대상은 요청 본문이 아니라 파일이며, 프레임워크의 파트 기본 상한(1 MiB)이 파일 파트에 걸리지 않는다는 경계를 테스트로 고정한다
- [x] 7.3 `GET /documents` · `GET /documents/{document_id}` — 목록과 상세. `index_signature`·`index_status` 포함. 없는 문서는 404
- [x] 7.4 `DELETE /documents/{document_id}` — 204, 없는 문서는 404
- [x] 7.5 `api/errors.py`에 **`ErrorCode` → HTTP 상태 표**(415/413/422/404/503)를 두고, 모든 `AppError`를 무조건 500으로 변환하는 현재 `handle_app_error`를 표 조회로 바꾼다. 표에 없는 코드는 500 유지 — 기존 `tests/test_errors.py`가 깨지지 않아야 한다. 변환은 여전히 이 계층에서만 (design 결정 11)
- [x] 7.6 오류 봉투에 구조화 필드 추가 — 지원 포맷 목록·적용된 크기 상한을 `error` 객체 안에 **평평하게** 싣는다(기존 `fields` 관습, `error_response`의 `**extra` 경유). **중첩 `details` 객체를 만들지 않는다.** 값은 1.8의 `AppError.extra`가 나른다
- [x] 7.7 앱 팩토리에 배선 — 파서 레지스트리·임베더·벡터 스토어·문서 레지스트리를 주입 가능하게. 모듈 전역 싱글턴을 두지 않는다
- [x] 7.8 API 테스트 (성공 경로) — txt / md / 텍스트 레이어 있는 PDF 각각 201과 `chunk_count` ≥ 1 / 목록·상세 반영 / 저장된 청크 수가 `chunk_count`와 일치 (spec "지원 포맷의 문서는 검색 가능한 청크로 저장된다" — **PRD §5 Ingestion 경로**)
- [x] 7.9 API 테스트 (위치 정보) — PDF 청크의 페이지 번호가 1 이상이고 총 쪽 수 이하 / 텍스트 청크의 오프셋이 시작 < 끝이고 원문 길이 이하 / 청크 본문이 원문의 부분 문자열 (spec "모든 청크는 원문 위치를 특정하는 정보를 갖는다")
- [x] 7.10 API 테스트 (오류 경로) — 미지원 확장자 415 + 지원 목록 노출 / 확장자 없음 415 / `.pdf`인데 PDF 아님 422 `document_parse_error` + 내부 예외 미노출 / 0바이트 422 `empty_document` / 공백만 422 / 스캔본 422 `no_extractable_text`(`empty_document`가 **아님**) / 상한 초과 413 + 상한 노출. **모든 경우에 문서 목록이 업로드 이전과 동일한지 단언** (spec 오류 요구사항 4건)
- [x] 7.11 API 테스트 (삭제) — 삭제 후 목록·상세·청크 수 / 다른 문서 무영향 / 없는 문서 404 / 삭제 후 재수집이 `created`이고 같은 `document_id`
- [x] 7.12 일부 쪽에만 텍스트가 있는 PDF 테스트 — 201이고 텍스트 있는 쪽에서만 청크가 나오며 페이지 번호가 일치
- [x] 7.13 배치 경계 테스트 — 배치 크기보다 많은 청크로 나뉘는 문서가 201이고, 저장된 청크 수가 `chunk_count`와 같으며, **청크 인덱스가 0부터 `chunk_count - 1`까지 빠짐없이 하나씩** 존재 (spec "청크가 배치 크기를 넘는 문서도 전부 저장된다")
- [x] 7.14 API 테스트 (색인 서명) — 같은 구성에서 수집한 두 문서의 `index_signature`가 같음 / 청크 크기·겹침·임베더 `signature`를 각각 바꾼 구성에서 값이 달라짐 / 배치 크기·업로드 상한·동시성 상한만 바꾸면 값이 같음 / 저장된 청크의 서명이 응답 값과 일치 / 구성을 바꾼 뒤 같은 바이트 재업로드가 `reindexed` (spec "색인 서명은 저장 시점의 색인 구성에서 결정된다", "색인 구성이 바뀐 뒤의 같은 바이트 재업로드는 재색인된다")
- [x] 7.15 `README.md` 갱신 — 새 엔드포인트 4개, 새 설정 항목 표(이름·의미·기본값, `chunk_strategy` 포함), 지원 포맷, **`status` 네 값의 의미와 `index_status`가 `stale`이 되는 조건·복구 방법**. **API가 완성된 직후에 적는다**

## 8. 오프로드와 동시성 검증

- [x] 8.1 지연 주입 스텁 **파서**로 수집을 진행시킨 상태에서 `GET /health` 소요 시간을 이벤트 루프 시계로 재고 **주입한 지연보다 짧음**을 단언 — `tests/test_health.py`의 측정 패턴과 픽스처 상한(0.2s/0.5s)을 재사용한다. 누가 파서를 이벤트 루프에서 직접 호출하면 여기서 깨진다 (spec "텍스트 추출이 오래 걸리는 수집 중 다른 요청")
- [x] 8.2 지연 주입 스텁 **임베더**로 같은 단언 — 배치가 여러 개 나오는 문서를 쓰고, 헬스 소요 시간이 전체 임베딩 지연보다 짧은지 본다. 배치 사이 양보가 없으면 깨진다 (spec "임베딩이 오래 걸리는 수집 중 다른 요청")
- [x] 8.3 서로 다른 문서 동시 업로드 (정확성) — 두 요청 모두 성공하고, 한 문서의 청크가 다른 문서의 `document_id`로 저장되지 않음
- [x] 8.4 서로 다른 문서 동시 업로드 (병렬성) — 지연 `T`의 파서로 2건을 동시 업로드해 총 소요가 `2 × T`보다 짧은지 단언. 잠금이 문서별이 아니라 전역이 되면 여기서 깨진다 (spec "서로 다른 문서는 서로를 기다리지 않는다")
- [x] 8.5 같은 파일명 동시 재업로드 — 지연 파서로 겹침을 강제하고 내용이 다른 2건을 `asyncio.gather`로 동시 전송. 둘 다 성공, 최종 `revision`이 둘 중 하나와 일치, 남은 청크가 전부 그 리비전이고 다른 리비전 청크 0. **어느 쪽이 이기는지는 단언하지 않는다** (spec "같은 문서에 대한 동시 요청은 직렬화된다")
- [x] 8.6 재업로드-삭제 경합 — 동시 전송 후 최종 상태가 두 직렬 순서 중 하나와 일치함을 단언: 문서가 남았으면 청크가 `chunk_count`만큼, 없으면 0. 뒤섞인 상태(삭제 성공 + 잔여 청크)가 관측되지 않음

> `tests/`에 `asyncio.gather` 전례가 없다. 8.3~8.6은 동시 요청 하네스부터 새로 만든다.

- [ ] 9.1 의존성 추가 — PDF 파서, 임베딩 런타임. torch는 **CPU 전용 휠**로 설치해 이미지 크기를 줄인다

- [x] 9.4 컬렉션 이름에 벡터 차원을 붙인다 — Chroma 는 컬렉션당 차원 하나만 허용하고 **비운 뒤에도 그 차원이 남는다**(실측). 이름이 하나면 차원이 다른 모델로 바꿨을 때 재업로드 복구가 영구히 실패해 spec 의 "`stale` 은 재업로드로 복구된다"가 거짓이 된다. 이 사실 자체를 실물 서버 테스트로 고정한다
- [x] 9.5 문서 레지스트리에 전용 볼륨 — 벡터 스토어가 별도 서비스가 되면서 볼륨을 공유할 수 없다. 컨테이너를 다시 만들어도 "지금 유효한 리비전이 무엇인가"가 남아야 한다
