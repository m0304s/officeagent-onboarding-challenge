## Context

동기는 `proposal.md` 「Why」에 있다. 여기서는 설계를 제약하는 **지금의 사실**만 적는다.

- **Redis 는 서 있지만 비어 있다.** `docker-compose.yml` 에 `redis:7` 서비스가 있고 `adapters/cache/probe.py` 가 연결 후 `ping` 만 한다. 실제 클라이언트 어댑터는 없다.
- **`/qa` 는 두 단계로 갈려 있다.** `QaService.prepare` 가 스트림 밖에서 검색까지 하고, `stream` 이 스트림 안에서 생성한다. 상태 코드가 첫 바이트와 함께 확정되므로 그 경계가 코드 구조다. 캐시 조회는 **`prepare` 안**에, 저장은 **`stream` 안**에 들어간다.
- **답변의 정체성 재료가 이미 다 있다.** `PROMPT_VERSION`(`core/prompting.py`), `index_signature`(`RetrievalService._index_signature`), `qa_llm_model`(`config.py` — "다음 change 의 캐시 키에 들어갈 값이라 설정으로 노출해 둔다"고 적혀 있다), `top_k`. 새로 만들 것은 질의 정규화뿐이다.
- **문서의 진실 원천은 SQLite 레지스트리다.** `DocumentRegistry.get` 이 `(revision, index_signature, index_status)` 를 준다. 현재성 재검증은 이것으로 한다 — 벡터 스토어 메타데이터에서 유도하면 교체 도중 답이 둘이 된다.
- **`ScoredChunk` 는 이미 직렬화 가능한 값 객체다.** `SearchResultView.of` 가 그것을 그대로 뷰로 바꾼다. 캐시가 담아야 할 것은 새 표현이 아니라 이 값들이다.
- **동시성 상한이 2다.** 생성 하나가 프로세스 하나라 `qa_concurrency=2`. 캐시 히트는 이 limiter 를 **잡지 않아야** 한다 — 히트가 미스 뒤에서 대기하면 캐시가 지연을 줄이지 못한다.

## Goals / Non-Goals

**Goals**

- 캐시 유무가 **답변의 내용**을 바꾸지 않는다. 캐시를 끄면 달라지는 것은 응답 시간뿐이다.
- 무효화가 **문서 단위**로 좁게 돈다. 전체 비우기는 무효화가 아니라 포기다.
- 낡은 답변이 나가는 경로를 **두 겹**으로 막는다 — 태그 무효화(쓰기 시점)와 인용 문서 현재성 재검증(읽기 시점).
- 캐시 계층이 죽어도 `/qa` 가 지금과 **글자 하나까지 같게** 동작한다.
- `add-multiturn-qa` 가 나중에 들어와도 캐시 키 정의를 고치지 않아도 된다.

**Non-Goals**

- **ANN 인덱스를 쓰지 않는다.** 항목 수 상한이 수백 규모라 완전 탐색이 ANN 보다 빠르고 정확하다.
- **동일 질문 동시 요청을 병합하지 않는다**(single-flight). 두 요청이 동시에 미스면 둘 다 생성한다.
- **캐시 관리 API 를 만들지 않는다.** 수동 비우기·통계 조회는 없다.
- **검색 결과를 캐시하지 않는다.** `ARCHITECTURE.md` 「검색 결과 캐시는 넣지 않았다」의 결정을 유지한다.
- **부분 답변을 캐시하지 않는다.** `error` 로 끝난 스트림은 아무것도 남기지 않는다.

## Decisions

### 결정 1 — L2 를 Redis 안의 완전 탐색으로 구현한다. RediSearch 도 Chroma 도 아니다

| 후보 | 기각 이유 |
|------|----------|
| **RediSearch VSS** (`redis/redis-stack-server`) | 이미지를 갈아야 하고, 벡터 인덱스의 차원·거리 함수 설정이 임베더 서명과 **따로 관리되는 두 번째 진실 원천**이 된다. 임베딩 모델을 바꾸면 인덱스를 손으로 재생성해야 한다. 수백 건 규모에서 ANN 이 주는 이득은 0 이다 |
| **Chroma 에 캐시 컬렉션 추가** | 캐시를 벡터 DB 에 두면 **수명이 섞인다** — Chroma 에는 TTL 이 없어 만료를 직접 구현해야 하고, 무효화가 두 저장소를 걸치게 된다. 문서 코퍼스와 캐시가 같은 백업·삭제 절차를 공유하게 되는 것도 잘못이다 |
| **프로세스 메모리** | 워커가 둘이면 캐시가 둘이 되고, 재배포마다 사라진다. 무효화가 프로세스 경계를 넘지 못한다 |
| **완전 탐색 (채택)** | 후보 수 상한 200 × 384 차원 = 76,800 회 곱셈. numpy 로 밀리초 미만이다. 추가 의존성·추가 설정·추가 진실 원천이 없다 |

**재고 시점은 명확하다** — 항목 수 상한을 수천 단위로 올려야 할 때다. 그때 붙일 것은 RediSearch 이고, 교체 지점은 `adapters/cache/store.py` 한 파일이다(프로토콜은 "후보 중 가장 가까운 하나"만 요구한다).

### 결정 2 — Redis 키 구조: 페이로드·벡터·순서 인덱스·태그를 나눈다

    qa:v1:entry:{fp}     STRING  JSON 페이로드      TTL O
    qa:v1:vec:{fp}       STRING  float32 packed     TTL O
    qa:v1:index          ZSET    fp → 단조 증가 seq  TTL X (지연 정리)
    qa:v1:doc:{doc_id}   SET     fp 들               TTL O (갱신)
    qa:v1:negative       SET     fp 들               TTL O (갱신)
    qa:v1:seq            STRING  INCR 카운터

**벡터를 페이로드에서 뗀 것이 핵심이다.** 합쳐 두면 L2 후보 스캔이 답변 본문·근거 청크 본문까지 전부 끌어온다 — 200건이면 수 MB 다. 나누면 스캔이 `ZREVRANGE`(fp 200개) + `MGET`(384×4 = 1536바이트 × 200 = 300KB) 로 끝나고, **이긴 하나만** 페이로드를 읽는다.

**순서 인덱스의 점수는 시계가 아니라 `INCR` 카운터다.** 시계를 쓰면 같은 밀리초의 두 항목 순서가 결정되지 않아 "가장 최근 N개"가 흔들리고, 테스트가 확률적이 된다.

**ZSET 에는 TTL 이 없어 죽은 fp 가 쌓인다.** 이것은 결함이 아니라 선택이다 — 스캔이 `MGET` 결과에서 `None` 을 만나면 그 fp 를 `ZREM` 으로 걷어낸다(**지연 정리**). 만료된 항목의 정리 비용을 만료 시점의 백그라운드 작업이 아니라 **다음 조회**가 조금씩 나눠 문다. 백그라운드 스위퍼가 없으므로 프로세스가 하나 더 늘지 않는다.

**용량 상한은 `ZREMRANGEBYRANK` 로 건다.** 저장 직후 `ZCARD` 가 상한을 넘으면 가장 오래된 것부터 잘라내고 그 fp 의 `entry`·`vec` 키를 지운다. 저장이 거부되는 경로는 만들지 않는다 — 캐시가 가득 찼다고 새 질문의 답변을 못 남기면 캐시가 시간이 지날수록 쓸모없어진다.

**태그 SET 에는 죽은 fp 가 섞인다.** 무효화는 `SMEMBERS` 로 받은 fp 를 통째로 `DEL` 하는데, 없는 키를 지우는 것은 무해하다. 태그 SET 자체는 항목을 더할 때마다 TTL 을 갱신해 언젠가 사라지게 둔다.

### 결정 3 — 캐시 키는 정규화된 질의가 아니라 **다섯 재료의 정규 직렬화**의 해시다

`core/documents.py` 의 `derive_index_signature` 와 같은 방식을 쓴다 — 정규 JSON(`sort_keys`, 명시적 구분자) → SHA-256.

```
fingerprint = sha256(canonical_json({
    "query":            normalize_query(search_query),
    "top_k":            effective_k,
    "prompt_version":   PROMPT_VERSION,
    "index_signature":  index_signature,
    "model":            qa_llm_model,
}))
```

- **해시인 이유**는 두 가지다. 값 경계가 모호한 연결(`q + ":" + str(k)`)은 서로 다른 구성이 같은 키를 받는 자리를 남긴다. 그리고 키가 질의 문자열을 그대로 담으면 `redis-cli KEYS *` 나 로그에 질문이 복원 가능한 형태로 노출된다(`response-cache` 스펙의 마지막 요구사항).
- **재료가 `search_query` 인 것이 멀티턴 대비다.** 지금은 `question` 과 같은 값이지만, 재작성이 들어오면 `QaContext` 가 들고 있는 "검색에 실제로 쓰인 질의"가 자동으로 그 자리에 온다. `add-multiturn-qa` 제안이 캐시 change 에 못 박아 둔 요구를 **키 정의로** 흡수한 것이라, 나중에 고칠 코드가 없다.
- **정규화는 네 가지만 한다** — NFC, `strip`, 연속 공백 축약, `casefold`. `normalize_filename` 이 이미 같은 조합을 쓴다. 어간 추출·조사 제거를 넣지 않는 이유는 그것이 L1 의 일이 아니기 때문이다. "정확 매치"가 의미를 판정하기 시작하면 L2 의 임계값이 무엇을 뜻하는지 아무도 말할 수 없게 된다.

**기각한 대안 — 프롬프트 문자열 전체를 해시하는 것.** 프롬프트에는 검색된 청크 본문이 들어가므로 키를 만들려면 먼저 검색을 해야 한다. 그러면 캐시가 검색 비용을 하나도 아끼지 못하고, 청크 하나의 위치가 밀리는 것만으로 캐시가 전부 미스가 된다.

### 결정 4 — 캐시 항목은 `sources` 전체를 담는다. 인용만 담지 않는다

페이로드에 들어가는 것:

| 필드 | 왜 |
|------|-----|
| `answer_text`, `finish_reason`, `citations`, `dropped_markers` | `done` 이벤트를 그대로 복원하기 위해 |
| `sources` (`ScoredChunk` 전체) | `sources` 이벤트를 복원하기 위해. 히트에도 출처가 실려야 한다 |
| `top_k`, `target_documents` | `sources` 이벤트의 나머지 필드 |
| `source_versions` — `(document_id, revision)` 목록 | 태그 무효화의 대상이자 현재성 재검증의 기준 |

**인용된 문서가 아니라 `sources` 의 문서 전부를 기록하는 것이 결정이다.** 히트 시 재생되는 것은 인용뿐이 아니라 근거 청크 **본문**이다 — 인용되지 않은 근거가 낡으면, 화면에는 지금 문서에 없는 문장이 출처로 떠 있게 된다. 게다가 `insufficient_evidence` 로 끝난 항목에는 인용이 아예 없어(도메인 불변식) 인용만 기록하면 무효화 대상이 0개가 된다.

**부정 판정에는 축을 하나 더 단다** — `qa:v1:negative` 집합이다. `no_evidence` 와 `insufficient_evidence` 로 끝난 항목이 **둘 다** 여기 들어가고, 코퍼스 내용이 바뀌면 집합을 통째로 비운다.

**긍정과 부정의 비대칭이 이 결정의 핵심이다.**

| 종료 | 그 답변이 주장하는 것 | 무엇이 뒤집나 | 방어 |
|------|---------------------|--------------|------|
| `stop` | **이 청크들이** 답을 담고 있다 | 그 청크들이 바뀌는 것 | 문서 태그 + 재검증 |
| `insufficient_evidence` | **코퍼스 어디에도** 답이 없다 | 코퍼스에 내용이 더해지는 것 | 문서 태그 + 재검증 + **부정 집합** |
| `no_evidence` | **코퍼스 어디에도** 답이 없다 | 코퍼스에 내용이 더해지는 것 | **부정 집합뿐** |

부정 판정은 **없음에 대한 주장**이라 자기가 건드린 문서만 봐서는 반증되지 않는다. 새 문서 하나가 그 주장을 깨는데, 그 새 문서에는 이 항목을 가리키는 태그가 없다.

- **`no_evidence` 는 부정 집합이 유일한 방어다.** 근거가 0건이라 태그도 `source_versions` 도 비어 있어, 문서 태그 무효화도 현재성 재검증(결정 7)도 이 항목에 닿지 못한다.
- **`insufficient_evidence` 는 둘을 겹쳐 쓴다.** 자기가 본 청크가 바뀌면 문서 태그가, 코퍼스에 내용이 더해지면 부정 집합이 잡는다. 두 기제가 **다른 사건**을 덮으므로 중복이 아니다.
- **`stop` 은 부정 집합에 넣지 않는다.** 새 문서에 더 나은 답이 있을 수는 있지만 캐시된 답변이 **틀린 것은 아니다** — 여전히 현재 문서에 근거한다. 긍정까지 코퍼스 변경으로 지우면 업로드 한 번이 캐시 전체를 비우는 것과 같아지고, 그것은 스펙이 금지한 전체 비우기다.
- **삭제로는 비우지 않는다** — 문서를 지워서 없던 근거가 생기지는 않는다.

### 결정 5 — 조회는 `prepare` 에서, 저장은 `stream` 에서. 히트는 동시성 limiter 를 잡지 않는다

```
prepare(question, top_k):
    lookup = cache.lookup(search_query, top_k)      # L1 → L2 → 현재성 재검증
    if lookup.hit:  return QaContext(cache=lookup)  # 검색을 하지 않는다
    result = retrieval.search(...)                  # 지금과 같다
    return QaContext(result=result, cache=miss)
```

- **히트면 검색도 하지 않는다.** 캐시가 아끼는 것은 생성 비용만이 아니다 — 임베딩·벡터 질의·어휘 질의·융합이 전부 빠진다.
- **`prepare` 는 여전히 예외를 잡지 않는다.** 캐시 조회 실패만 삼킨다(미스로 강등). 검색 예외를 삼키면 같은 장애가 `/search` 와 `/qa` 에서 다르게 보인다는 기존 결정이 그대로다.
- **히트 경로는 `anyio.CapacityLimiter` 를 잡지 않는다.** 그 상한이 존재하는 이유는 "생성 하나가 프로세스 하나"이기 때문인데, 히트에는 프로세스가 없다. 잡으면 히트가 미스 뒤에 줄을 서서 캐시가 지연을 줄이지 못한다.
- **저장은 `done` 을 내보내기 직전이다.** 뒤에 두면 클라이언트가 마지막 프레임 직전에 끊었을 때 저장이 건너뛰어진다. 실패는 삼키고 로그로 남긴다.

### 결정 6 — 히트 재생은 `answer` 이벤트 **한 개**다. 원래의 조각 경계를 저장하지 않는다

`answer-generation` 스펙은 "서버가 조각의 크기를 인위적으로 나누거나 합쳐서는 안 된다"고 못 박고 그 근거를 이렇게 적어 두었다 — *"조각을 서버가 쪼개면 스트리밍하고 있다는 겉모습은 얻지만 첫 조각이 도착하는 시각은 하나도 앞당겨지지 않는다."*

**캐시 히트에는 생성기가 없다.** 조각이 도착하는 사건 자체가 없으므로, 저장해 둔 경계를 재생하는 것은 **없던 진행을 연출하는 일**이다. 정직한 표현은 조각 하나다. 스펙의 불변식(`answer` 들을 이어 붙이면 `done.answer` 와 같다)은 그대로 성립하고, 조각 경계를 저장하지 않으므로 페이로드도 작아진다.

**기각한 대안 — 저장한 경계로 재생하며 사이에 지연을 넣는 것.** 사용자에게 "생성 중"으로 보이게 만드는 값이지만, 그것은 캐시가 아낀 시간을 도로 쓰는 일이다.

### 결정 7 — 현재성 재검증은 레지스트리 조회 한 번(기여 문서만)이다

히트 후보의 `source_versions` 에 담긴 `document_id` 들만 `DocumentRegistry.get` 으로 읽고, 각각에 대해 `Document.is_up_to_date(revision=…, index_signature=현재 서명)` 을 확인한다. 하나라도 실패하면 **히트를 버리고 항목을 지운 뒤 미스로 진행**한다.

- **`RetrievalService._drop_superseded` 와 같은 판정 함수를 쓴다.** 검색과 캐시가 각자 "현재인가"를 구현하면 한쪽만 고쳐졌을 때 각자 자기 기준으로는 옳은 채로 어긋난다 — `core/documents.py` 의 주석이 경고하는 바로 그 자리다.
- **비용은 문서 수십 건 규모의 SQLite 조회 몇 건이다.** 히트가 아끼는 것(임베딩 + 벡터 질의 + 생성 수 초)에 비해 무시할 만하다.
- **재검증에서 버린 항목은 지운다.** 남기면 같은 항목이 요청마다 재검증 비용을 다시 물린다.

**이것이 왜 태그 무효화만으로 부족한가.** 검색이 끝나고 생성이 도는 십수 초 사이에 문서가 바뀌면, 무효화는 **아직 존재하지 않는 항목**을 지우고 그 뒤에 낡은 항목이 저장된다. 그 항목은 이후 어떤 무효화에도 걸리지 않는다. `ARCHITECTURE.md` 가 검색 재검증을 설명하며 *"밀리초짜리 읽기 어긋남이 무기한 캐시 오염으로 증폭됩니다"* 라고 예고한 것이 정확히 이 경로다. 재검증은 그 창을 응답 시점에 닫는다.

### 결정 8 — 무효화는 `IngestionService` 안, 레지스트리 커밋 **뒤**

`ingest` 와 `delete` 가 성공을 확정한 뒤에 `cache.invalidate_document(document_id)` 를 부른다.

- **커밋 앞이면** 실패해 롤백된 수집이 멀쩡한 캐시를 날린다.
- **`IngestionStatus.UNCHANGED` 에서는 부르지 않는다.** 바뀐 것이 없으면 캐시된 답변도 여전히 옳다.
- **`UNCHANGED` 를 뺀 전부에서 `negative` 집합을 함께 비운다** — `CREATED`·`REPLACED`·`REINDEXED`. 판정을 뒤집는 것은 문서 **개수**가 아니라 **내용**이다. 교체는 개수를 그대로 둔 채 내용을 바꾸므로, 없던 답이 생길 수 있다. `REINDEXED` 도 마찬가지다 — 청킹·임베딩이 달라지면 관련성 하한을 넘는 청크의 집합이 달라진다.
  - **`REINDEXED` 를 빠뜨리면 stale 복구가 낫지 않는다.** `STALE` 문서는 검색 대상에서 빠지므로(`is_searchable_under`), 그 동안 들어온 질문은 `no_evidence` 로 캐시된다. 재업로드로 복구되면 `REINDEXED` 인데 **색인 서명이 그대로라 캐시 키가 여전히 맞는다** — 서명이 바뀌는 재색인은 키가 갈려 저절로 낫지만, 이 경로는 낫지 않는다.
  - **`UNCHANGED` 만 예외인 이유**는 그것이 아무것도 쓰지 않고 끝나는 유일한 경로이기 때문이다. 규칙을 "청크를 실제로 쓴 수집"으로 읽으면 판정이 하나로 정리된다.
- **실패는 삼키고 경고 로그를 남긴다.** 문서는 이미 바뀌었고 그것을 되돌리는 것이 더 큰 손해다. 그리고 재검증(결정 7)이 두 번째 방어선으로 서 있다.

**기각한 대안 — 무효화를 서비스가 아니라 어댑터(벡터 스토어) 안에 두는 것.** 어댑터가 캐시를 알게 되면 저장소 두 개가 서로를 참조하고, 테스트에서 벡터 스토어를 스텁으로 갈면 무효화가 함께 사라진다.

### 결정 9 — 임계값 기본값은 계측해서 정한다. 지금 적는 값은 출발점이다

`retrieval_min_score = 0.82` 가 계측값(관련 1위 최솟값 0.8511 / 무관 1위 최댓값 0.8134 사이)인 것과 같은 방식을 쓴다. **E5 계열 임베딩은 무관한 문장 사이에서도 코사인 유사도가 0.8 대에 앉으므로, 검색용 하한을 그대로 가져오면 서로 다른 질문이 전부 히트가 된다.**

기본값 `0.93` 은 출발점이고, `tasks.md` 에 `sample-docs/` 기반 계측 태스크를 둔다 — 같은 뜻의 다른 표현 쌍과 서로 다른 질문 쌍의 유사도를 재서, 그 사이에서 값을 고르고 근거를 `ARCHITECTURE.md` 에 남긴다.

**이 값은 "얼마나 아끼는가"가 아니라 "얼마나 틀려도 되는가"를 정한다.** 그래서 계측 없이 고르면 안 되고, 근거가 코드 밖에 남아야 한다.

### 결정 10 — 미스에서 질의 임베딩을 두 번 만드는 것을 받아들인다

L2 조회가 `Embedder.embed_query` 를 부르고, 미스로 진행하면 `DenseRetriever` 가 같은 질의를 다시 임베딩한다.

**받아들이는 이유** — 없애려면 미리 계산한 벡터를 `Retriever.retrieve` 로 흘려야 하는데, 그 프로토콜은 의도적으로 `query: str` 만 받는다(어휘 retriever 는 벡터가 필요 없고, 융합은 둘을 같은 모양으로 다룬다). 이득 몇 밀리초를 위해 세 파일의 시그니처를 바꾸는 것은 남는 장사가 아니다.

**대신 공짜인 최적화 하나를 넣는다** — `ZCARD` 가 0 이면 L2 를 건너뛴다. 캐시가 빈 상태(=평가자의 첫 실행, 대부분의 테스트)에서는 임베딩이 한 번만 돈다.

### 결정 11 — 응답 필드는 평평하게 셋

`done` 페이로드에 `cache_hit: bool`, `cache_layer: "exact" | "semantic" | null`, `cache_similarity: float | null` 을 더한다.

`cache_hit` 이라는 이름은 PRD 와 `openspec/config.yaml` 의 도메인 용어집이 이미 쓰는 단어다. `{"cache": {"hit": …}}` 로 감싸면 그 단어가 응답에서 사라진다. 스트림의 다른 페이로드도 전부 평평하다(`finish_reason`, `elapsed_ms`).

### 결정 12 — 구현이 셋이다. "꺼짐"과 "죽음"과 "테스트"는 서로 다른 상태다

`ResponseCache` 프로토콜 뒤에 구현 **셋**을 둔다. 하나로 겸하게 만들면 세 상태 중 둘이 조용히 틀린다.

| 구현 | 언제 배선되나 | 조회 | 저장 | 관측 |
|------|--------------|------|------|------|
| `NullResponseCache` | `cache_enabled=false` | 항상 미스 | 무동작 | 기동 시 한 줄 |
| `InMemoryResponseCache` | **테스트가 명시적으로 주입할 때만** | 전체 의미(TTL·상한·유사 매치·태그) | 프로세스 로컬 | — |
| `RedisResponseCache` | 그 외 전부 | 히트/미스, 실패는 미스 | 실패는 무동작 | 상태 전이 시 경고 |

**프로덕션 배선이 인메모리로 떨어지는 경로를 만들지 않는다.** 이것이 이 결정의 전부다.

**`cache_enabled=false` 를 인메모리로 잇지 않는 이유** — 그러면 캐시를 껐는데 꺼지지 않는다. 히트가 계속 나고 프로세스 로컬이 될 뿐이다. 운영자가 캐시를 끄는 이유는 대개 "캐시를 배제하고 원인을 보겠다"인데, 그 상태에서 히트가 나면 배제가 성립하지 않는다. `response-cache` 스펙의 「캐시를 꺼도 서비스가 기동된다」 시나리오가 요구하는 것도 **모든 요청이 미스**다.

**Redis 장애를 인메모리로 폴백하지 않는 이유** — 폴백은 관측을 흐리는 정도가 아니라 **무효화를 프로세스 경계에서 끊는다.** 구체적으로: Redis 가 죽은 동안 워커 A 가 `no_evidence` 답변을 자기 메모리에 캐시하고, 그 뒤 워커 B 로 새 문서가 업로드된다. 무효화는 워커 A 의 메모리에 닿지 못한다. 그리고 **결정 7(현재성 재검증)이 이것을 잡지 못한다** — `no_evidence` 항목에는 `source_versions` 가 비어 있어 재검증할 문서가 없고, 그 항목의 방어는 `negative` 집합뿐인데 그 집합이 Redis 에 있다. **폴백 하나가 2중 방어를 둘 다 무력화한다.** 그래서 장애 시의 정답은 폴백이 아니라 미스다.

**관측이 두 상태에서 갈린다.** 꺼짐은 의도된 상태라 **기동 시 한 줄**이면 된다. 죽음은 사고라 경고가 필요하지만 **요청마다 찍으면 로그가 넘쳐 진짜 신호가 묻힌다** — 가용/불가용 **상태가 바뀌는 시점**에만 찍는다. Redis 가 죽었다는 사실 자체는 이미 `adapters/cache/probe.py` 가 `/health` 로 보고하고 있어, 새 응답 필드를 만들지 않는다.

### 결정 13 — 캐시 조회에 짧은 타임아웃과 차단기를 건다

**죽은 Redis 는 "미스"로 끝나지 않고 "느린 미스"가 된다.** 조회 타임아웃이 없으면 매 요청이 연결 타임아웃만큼 멈추고, 그것도 L1·L2 두 번이다. `probe_timeout_seconds=2.0` 을 그대로 쓰면 캐시가 **캐시 없을 때보다 4초 느린** 상태를 만든다. 지연을 줄이려고 넣은 층이 지연을 늘리는 것은 설계 실패다.

- **작업 타임아웃 `cache_operation_timeout_seconds = 0.2`.** 캐시는 최적화라 200ms 안에 답하지 못하면 도움이 되지 않는다. 헬스 프로브의 2초와 값이 다른 것은 묻는 것이 다르기 때문이다 — 프로브는 "살아 있나"를, 조회는 "지금 도움이 되나"를 묻는다.
- **차단기.** 연속 실패 `cache_circuit_breaker_failures = 3` 회면 `cache_circuit_breaker_cooldown_seconds = 30` 동안 조회·저장을 **아예 건너뛴다**(즉시 미스). 타임아웃만 있으면 죽은 Redis 에 매 요청 400ms 를 계속 잃는다. 쿨다운이 지나면 다음 요청 하나가 탐침 역할을 하고, 성공하면 차단이 풀린다.
- **차단기는 캐시 계층 안에만 있다.** 상태를 프로세스 메모리에 든다 — 차단기 상태를 공유하려면 저장소가 필요한데, 그 저장소가 지금 죽은 Redis 다.
- 차단 열림/닫힘은 **상태 전이 시점에** 로그를 남긴다(결정 12).

**기각한 대안 — 타임아웃만 두고 차단기를 생략하는 것.** 200ms × 2 × 모든 요청은 생성 비용(수 초)에 비하면 작아 보이지만, 캐시 히트가 있었어야 할 요청에서는 그것이 **응답 시간의 전부**다. 그리고 캐시가 죽은 상태는 대개 짧지 않다.

### 결정 14 — 키 재료 셋이 `QaService` 에 없다. 유도하지 말고 소유자에게서 읽는다

캐시 키는 다섯 재료를 요구하는데(결정 3), **`QaService` 가 지금 들고 있는 것은 둘뿐이다** — `question` 과 `PROMPT_VERSION`. 나머지 셋의 현재 위치:

| 재료 | 지금 어디 있나 | 문제 |
|------|---------------|------|
| `effective_k` | `RetrievalService.search` 안에서 `self._top_k if top_k is None else top_k` 로 계산 | 요청이 `top_k` 를 생략하면 `QaService` 는 `None` 만 안다. **조회는 검색보다 앞이라**(결정 5) 결과에서 꺼낼 수도 없다 |
| `index_signature` | `RetrievalService._index_signature` (비공개) | 접근 경로가 없다 |
| `qa_llm_model` | 배선이 생성기 어댑터에만 넘긴다 (`main.py:242`) | `QaService` 에 오지 않는다 |

**`effective_k` 를 `None` 인 채로 키에 넣으면 안 된다.** `top_k` 를 생략한 요청과 `top_k=5` 를 명시한 요청이 같은 질문인데 다른 항목이 되고, 설정 기본값을 바꾸면 `None` 으로 만들어진 옛 항목이 새 기본값의 답인 척 남는다.

**`RetrievalService` 가 둘을 노출한다** — `index_signature` 읽기 전용 프로퍼티와 `resolve_top_k(top_k) -> int`. `QaService` 는 이미 들고 있는 `RetrievalService` 에서 읽는다.

**배선에서 각자 주입하지 않는 이유**가 핵심이다. `main.py:230` 에 이미 적혀 있다 — *"수집이 청크를 찍은 것과 같은 서명이라 두 서비스가 같은 색인 세대에 묶인다."* `RetrievalService` 의 생성자 주석은 더 직접적이다 — *"각자 유도하면 한쪽만 고쳐진 순간 방금 올린 문서가 오류 없이 검색되지 않는다."* 캐시가 서명을 따로 받으면 **세 번째 유도 지점**이 생기고, 어긋났을 때의 증상은 조용하다: 캐시가 검색과 다른 세대의 키를 쓰면서 히트율이 0 이 되거나, 더 나쁘게는 옛 세대 답변을 현재 세대의 답으로 내놓는다. 소유자에게서 읽으면 유도 지점은 배선 한 곳으로 유지된다.

**K 의 기본값 규칙도 마찬가지로 한 곳이다.** `resolve_top_k` 를 두는 것은 값 하나를 넘기기 위해서가 아니라 **"생략되면 설정 기본값"이라는 규칙을 복제하지 않기 위해서다.** 복제하면 `retrieval_top_k` 를 바꿨을 때 검색과 캐시가 서로 다른 K 를 믿는다.

**`qa_llm_model` 은 배선이 `QaService` 에도 넘긴다.** 생성기 프로토콜(`AnswerGenerator`)에 `model` 속성을 더하지 않는다 — 모든 테스트 스텁이 그 속성을 선언해야 하고, 생성기는 자기 모델 이름을 알 이유가 없다. 두 곳이 같은 `settings.qa_llm_model` 을 읽으므로 진실 원천은 여전히 하나다.

> **남는 구멍 하나** — `qa_llm_model` 이 빈 문자열이면 CLI 기본 모델을 쓴다는 뜻인데, 그 기본값이 CLI 업그레이드로 바뀌어도 캐시 키는 `""` 그대로다. 옛 모델의 답변이 새 모델의 답인 척 남는다. 막으려면 모델 이름을 명시적으로 설정하면 되고, 그 사실을 `README.md` 의 캐시 절에 적는다.

## Risks / Trade-offs

**[부정문이 긍정문과 구분되지 않는다 — 임계값으로 못 막는다]** → **이 설계에서 가장 큰 위험이고, 계측으로 없앨 수 없다.**

    "환불 정책이 어떻게 되나요?"  ↔  "환불이 안 되는 경우가 있나요?"
    E5 코사인 유사도 0.95 초과 — 기본값 0.93 은 이것을 히트로 판정한다

두 질문은 묻는 바가 반대인데 임베딩은 거의 같다. **문장 임베딩이 부정을 사실상 인코딩하지 않는 구조적 한계**라, 계측을 아무리 정교하게 해도 이 쌍은 임계값 위에 남는다. 0.95 위로 임계값을 올려 이 쌍을 떨어뜨리면 진짜 같은 질문의 쌍도 함께 떨어져 **L2 가 사실상 꺼진다.** 임계값 하나로는 풀 수 없는 문제다.

→ 완화는 셋이고, **어느 것도 이 쌍을 완전히 없애지 못한다는 것을 전제로** 고른다:
1. **계측 집합에 부정문 쌍을 필수로 넣는다**(태스크 7.1). 값을 고르는 사람이 이 한계를 **모르고** 고르는 일만은 막는다. 계측 결과와 이 한계를 `ARCHITECTURE.md` 에 함께 남긴다.
2. **확신이 없으면 임계값을 1.0 가까이 올린다.** L2 가 꺼지고 L1 만 남는다 — **이것이 안전한 기본 상태이고, 이 위험이 그 선택의 근거다.** PRD 의 "유사 질문 캐시"는 L2 로 충족하지만, 틀린 답을 내는 L2 보다 꺼진 L2 가 낫다.
3. **`cache_similarity` 를 응답에 싣는다.** 운영자가 실제 분포를 보고 조정할 수 있게 한다.

**다음 단계의 후보**(이 change 범위 밖) — 부정 표지(`안`·`못`·`없`·`아닌`·`불가`·`제외`)의 유무가 두 질의 사이에서 갈리면 L2 히트를 거부하는 어휘 가드. 임베딩이 못 보는 것을 정규식이 보는 자리다. 지금 넣지 않는 이유는 한국어 부정 표현의 목록이 열려 있어 가드 자체가 계측 대상이 되기 때문이고, 그 계측 없이 넣으면 "막은 것 같은 느낌"만 남는다.

**[임계값이 낮으면 그 밖의 틀린 답도 히트로 나간다]** → 부정문 외의 일반적인 오판은 (1) 계측으로 고른 보수적 기본값(결정 9), (2) 유사 매치 후보를 **같은 정체성 재료를 공유하는 항목**으로 한정, (3) `cache_similarity` 노출로 방어한다.

**[히트가 미스보다 느려지는 지점이 있다]** → 항목이 많아지면 완전 탐색 비용이 생성 절약분을 잠식한다. `cache_semantic_candidates` 상한(기본 200)이 이 비용을 고정한다. 상한 때문에 오래된 항목은 L2 대상에서 빠지지만 **L1 에서는 여전히 찾힌다** — 정확히 같은 질문은 항상 히트한다.

**[동시 미스가 같은 답을 두 번 생성한다]** → single-flight 는 범위 밖(`proposal.md`). 동시성 상한이 2 라 최악이 두 배이고, 두 번째가 첫 번째의 항목을 덮어쓰는 것은 무해하다(같은 키·같은 근거). 재고 시점은 동시 사용자가 늘어 생성기 대기열이 눈에 띌 때다.

**[ZSET 이 죽은 fp 로 부푼다]** → 지연 정리(결정 2)가 조회할 때마다 조금씩 걷어내지만, **조회가 아예 없으면 정리도 없다.** 항목 수 상한의 `ZREMRANGEBYRANK` 가 백스톱이라 무한히 자라지는 않는다.

**[캐시가 문서 삭제를 지연 반영하는 창이 남는다]** → 무효화와 재검증 사이에도 창은 있다 — 재검증이 레지스트리를 읽은 직후에 문서가 지워지면 그 응답은 나간다. 이것은 스냅숏 격리가 없는 읽기의 정상 동작이고, 검색 경로도 같은 창을 갖는다(`ARCHITECTURE.md`). 캐시가 이 창을 **넓히지 않는다**는 것이 재검증의 목표다.

**[Redis 페이로드가 커진다]** → 항목 하나가 근거 청크 본문 5개(청크 600자)를 담아 3~5KB 다. 상한 500건이면 2.5MB 규모라 문제가 아니다. 상한을 크게 올릴 때 다시 볼 값이다.

**[테스트가 실제 Redis 를 요구하면 `pytest` 한 줄이 깨진다]** → PRD 는 테스트가 한 줄로, 가능하면 구독 없이 돌 것을 요구한다. 기본 테스트는 `InMemoryResponseCache` 를 **명시적으로 주입해서** 돌고, 히트를 포함한 전체 의미를 실제로 검증한다. Redis 어댑터 자체의 계약 테스트는 `redis` 마커 뒤에 두어(`llm` 마커와 같은 방식) 기본 실행에서 빠진다. 인메모리 구현이 프로덕션 배선으로 새어 나가면 결정 12 가 막으려던 실패가 그대로 돌아온다 — **배선 코드에 인메모리로 가는 분기가 없다**는 것을 테스트로 고정한다.

**[차단기가 열려 있는 동안은 살아난 Redis 를 못 쓴다]** → 쿨다운(기본 30초)만큼 히트를 놓친다. 놓치는 것이 지연뿐이고 정확성이 아니라 받아들인다 — 반대 방향(죽은 Redis 를 매 요청 다시 찔러 보기)의 손해가 더 크다. 쿨다운 뒤 첫 요청이 탐침이라 회복은 자동이다.

**[차단기 상태가 워커마다 따로다]** → 워커 넷이면 각자 3회씩, 최대 12회의 느린 요청을 겪은 뒤에야 전부 차단된다. 상태를 공유하려면 저장소가 필요한데 그 저장소가 지금 죽은 Redis 라, 공유할 방법이 원리적으로 없다.

## Migration Plan

데이터 마이그레이션이 없다. Redis 는 비어 있고, 키 접두사에 `v1` 이 있어 다음 세대와 섞이지 않는다.

**배포** — `docker compose up -d --build`. 기동 시 캐시 연결을 확인하지 않는다(연결은 첫 사용에서 지연 생성). 캐시 저장소가 없어도 기동이 성공해야 한다는 것이 스펙 요구사항이다.

**롤백** — `APP_CACHE_ENABLED=false` 로 재기동하면 캐시 계층이 통째로 빠지고 `/qa` 가 지금과 같아진다. 코드 롤백 없이 되는 것이 이 설계의 안전장치다. 남은 키는 TTL 로 사라지고, 급하면 `redis-cli --scan --pattern 'qa:v1:*' | xargs redis-cli DEL` 이다.

**키 세대 교체** — 페이로드 구조를 바꿔야 하면 접두사를 `qa:v2:` 로 올린다. 옛 키는 TTL 로 사라진다. 마이그레이션 스크립트를 쓰지 않는 이유는 캐시가 재생성 가능한 데이터이기 때문이다.
