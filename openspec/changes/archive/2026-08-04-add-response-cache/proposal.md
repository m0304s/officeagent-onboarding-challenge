## Why

**PRD §3(LLM 응답 캐싱)이 통째로 비어 있다.** 지금 `/qa` 는 같은 질문을 열 번 받으면 생성기를 열 번 부른다. 답변 생성은 이 서비스에서 가장 비싼 연산이고(실측 최악 18.9초, 시도 하나가 프로세스 하나, 동시성 상한 2), 같은 질문의 두 번째 요청이 그 비용을 다시 치를 이유가 없다. Redis 는 이미 compose 서비스와 헬스 프로브로 서 있지만 **실제로 무언가를 담고 있지는 않다.**

PRD 는 캐싱에 세 가지를 요구한다 — **동일·유사 질문의 재호출 회피**, **캐시 히트 여부의 응답 노출**, **문서 변경 시 관련 캐시 무효화**. 셋 중 마지막은 핵심 3경로 테스트 대상이기도 하다(§5). 캐시 DB 미구현은 불합격 기준에 명시되어 있다.

## What Changes

`/qa` 파이프라인의 **검색 앞과 생성 앞** 두 자리에 조회 지점을 두고, **생성이 끝난 자리**에 저장 지점을 둔다. 검색·생성·SSE 계약은 하나도 바뀌지 않는다.

    질문
      → [신규] L1 조회 — 질의 문자열 정규화 후 정확 매치
      → [신규] L2 조회 — 질의 임베딩 최근접 + 임계값 + 인용 문서 현재성 재검증
                ↓ 미스                                    ↓ 히트
          기존 retrieval → 기존 생성 → [신규] 저장    [신규] 캐시 재생
                ↓                                          ↓
              ────────────── 같은 SSE 이벤트 시퀀스 ──────────────

- **2단 캐시를 신설한다.** L1 은 정규화된 질의 문자열의 해시로 찾는 정확 매치, L2 는 질의 임베딩의 코사인 유사도로 찾는 유사 질문 매치다. 두 층을 나누는 이유는 비용이 다르기 때문이다 — L1 은 Redis 왕복 한 번이고, L2 는 임베딩 한 번 + 후보 스캔이다. 정확히 같은 질문이 L2 의 비용을 치를 이유가 없다.
- **캐시 히트도 미스와 **똑같은** SSE 이벤트 시퀀스로 응답한다.** `sources` → `answer`* → `done` 이 그대로 나가고, 히트임은 `done` 이벤트의 필드로만 드러난다. 히트/미스에 따라 응답 모양이 갈리면 클라이언트가 두 경로를 각각 다뤄야 하고, `answer-generation` 이 정한 이벤트 계약이 조건부가 된다.
- **문서 변경이 관련 캐시만 무효화한다.** 캐시 항목은 자기가 인용한 문서를 기록하고, 문서의 수집·재업로드·삭제가 그 문서를 인용한 항목만 지운다. 전체 비우기가 아니다 — PRD 가 요구하는 것은 "**관련** 캐시 무효화"다.
- **L2 히트에는 무효화와 독립된 2중 방어를 건다.** 유사도가 임계값을 넘어도, 캐시된 답변이 인용한 `(document_id, revision)` 이 지금도 현재 값이 아니면 히트를 버리고 미스로 처리한다. 무효화가 한 번 새면 오염이 TTL 까지 남는데, 재검증은 그 창을 닫는다.
- **캐싱은 꺼도 서비스가 성립한다.** Redis 에 닿지 못하면 조회 실패는 미스로, 저장 실패는 로그로 끝난다. 캐시 장애가 `/qa` 를 `503` 으로 만들어서는 안 된다 — 캐시는 지연을 줄이는 층이지 답변의 성립 조건이 아니다.

**범위 밖** — 검색 결과 캐시(`ARCHITECTURE.md` 「검색 결과 캐시는 넣지 않았다」의 결정을 유지한다. 이 change 가 다루는 것은 결과를 바꾸는 LLM 응답 캐시다), 임베딩 캐시, 캐시 관리 API(수동 비우기·통계 조회), 분산 락, 동일 질문 동시 요청의 병합(single-flight).

**멀티턴과의 관계** — `add-multiturn-qa` 는 아직 착수 전이고, 이 change 는 그것을 기다리지 않는다. 대신 캐시 키의 재료를 "사용자가 보낸 질문"이 아니라 **"검색에 실제로 쓰인 질의"** 로 정의한다. 지금은 둘이 같은 값이고, 멀티턴이 재작성을 넣으면 재작성된 질의가 자동으로 그 자리에 온다 — `add-multiturn-qa` 제안이 캐시 change 에 못 박아 둔 요구를 키 정의로 흡수한다.

## Capabilities

### New Capabilities

- `response-cache`: LLM 응답 캐시의 계약. 캐시 항목의 정체성(무엇이 같은 질문인가), L1 정확 매치와 L2 유사 매치의 판정 조건, 히트가 응답에 드러나는 형태, 캐시된 답변의 재생 규칙, 수명(TTL)과 용량 상한, 문서 변경에 따른 무효화 범위, 캐시 저장소에 닿지 못할 때의 축소 동작.

### Modified Capabilities

- `answer-generation`: 종료 이벤트가 **캐시 히트 여부와 히트 층(L1/L2)** 을 노출한다는 요구사항이 더해진다. 이벤트 종류·순서·조각 전달 규칙·인용 형식은 바뀌지 않는다 — 캐시 히트도 미스와 같은 시퀀스를 낸다는 것이 요구사항으로 명시된다.
- `document-ingestion`: 문서의 수집·교체·삭제가 **그 문서를 인용한 캐시 항목을 무효화한다**는 요구사항이 더해진다. 저장 결과의 모양과 상태 코드는 바뀌지 않는다.

> `answer-generation` 은 아직 `openspec/specs/` 에 없다 — 구현은 끝났으나 `add-answer-generation` change 가 아카이브되지 않은 상태다. 이 change 의 델타는 그 change 가 아카이브된 뒤에 얹힌다. `document-ingestion` 은 이미 `openspec/specs/` 에 있다.

## Impact

**신규 코드**

| 경로 | 내용 |
|------|------|
| `core/cache.py` | 캐시 도메인 — 캐시 키 유도, 질의 정규화, 캐시 항목 값 객체, 유사도 판정(순수 함수) |
| `adapters/cache/redis.py` | Redis 클라이언트 어댑터. 지금 없는 것을 새로 만든다(`probe.py` 는 연결 후 ping 만 한다) |
| `adapters/cache/store.py` | `ResponseCacheStore` 구현 — L1 조회·L2 후보 스캔·저장·태그 무효화 |
| `services/cache.py` | 캐시 오케스트레이션 — 조회 순서(L1 → L2), 현재성 재검증, 저장 정책, 축소 동작 |

**변경되는 코드**

| 경로 | 변경 |
|------|------|
| `adapters/protocols.py` | `ResponseCache` 프로토콜. 소비처가 생기는 지금 정의한다 |
| `services/qa.py` | `prepare` 가 검색 전에 캐시를 조회하고, `stream` 이 히트면 재생·미스면 생성 후 저장한다. `QaContext` 가 캐시 조회 결과를 담는다 |
| `services/ingestion.py` | `ingest`·`delete` 가 성공 후 해당 문서의 캐시를 무효화한다 |
| `api/sse.py` | `done` 페이로드에 `cache_hit`·`cache_layer` 필드 |
| `config.py` | TTL, L2 유사도 임계값, L2 후보 스캔 상한, 캐시 활성화 플래그, 항목 수 상한 |
| `main.py` | 캐시 스토어 배선. Redis 에 닿지 못하는 기동이 실패하지 않아야 한다 |

**손대지 않는 코드** — `services/retrieval.py`, `adapters/vector_store/`, `adapters/retrievers/`, `core/prompting.py`, `core/answers.py`. 이 다섯이 그대로인 것이 "검색·생성 계약 불변"의 실물 증거다.

**문서** — `ARCHITECTURE.md` 에 2단 캐시 구조와 Redis 자료구조 선택 근거, L2 를 벡터 DB 가 아닌 Redis 로 구현한 이유, 무효화 태그 설계. `README.md` 에 캐시 설정 항목과 `cache_hit` 확인 방법. `PROMPT_DESIGN.md` 는 프롬프트가 안 바뀌므로 손대지 않되, **프롬프트 버전이 캐시 키에 들어간다**는 사실만 적는다 — 프롬프트를 고치면 캐시가 저절로 갈리게 하는 장치다.

**테스트** — 캐시 무효화는 PRD §5 의 핵심 3경로 중 하나다. L1 히트·L2 히트·임계값 미달·문서 변경 후 무효화·인용 문서 현재성 재검증·Redis 부재 시 축소 동작이 전부 테스트 대상이며, LLM 은 스텁이라 구독 없이 돈다.

**앞으로 지어질 것에 미치는 영향** — `add-multiturn-qa` 가 들어오면 캐시 키의 "검색에 쓰인 질의"가 재작성된 질의가 되고, 세션 스코프가 필요하면 키에 축을 하나 더한다. `add-demo-ui` 는 `done` 의 `cache_hit` 를 화면에 표시할 수 있게 된다 — 지금은 서버가 주지 않아 자리를 두지 않았다(`ARCHITECTURE.md`).
