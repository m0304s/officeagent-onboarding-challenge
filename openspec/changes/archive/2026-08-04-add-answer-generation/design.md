## Context

동기는 `proposal.md` — Why, 요구사항은 `specs/answer-generation/spec.md` 참조.

앞선 change가 남긴 것은 **근거까지 고르는 파이프라인**이다. `RetrievalService`가 질의 하나에 대해 지금 유효한 청크 상위 K개를 출처 정보와 함께 돌려주고, 결과 하나가 스스로 `document_id`·`filename`·`format`·`revision`·`chunk_index`·본문·원문 위치·점수를 말한다. `POST /search`가 그 계층을 단독으로 관측할 수 있게 열려 있다.

설계를 좌우하는 제약은 다섯이다.

1. **생성기는 HTTP 클라이언트가 아니라 로컬 CLI다.** 프로세스를 띄워 stdout을 파싱해야 하므로 프로세스 수명·타임아웃·취소·인증 판정을 전부 직접 구현한다. 파이썬 SDK가 대신해 줄 것이 없다.
2. **그 CLI는 에이전트다.** 텍스트 생성기가 아니라 도구를 쓰고 파일을 읽을 수 있는 실행체다. 좁혀 두지 않으면 RAG 프롬프트를 받고 컨테이너 파일시스템을 뒤지러 갈 수 있다.
3. **토큰 델타는 표면에 따라 있기도 없기도 하다.** `codex exec --json`은 메시지를 통째로 한 이벤트로 주지만(4,808자 답변도 한 번), `codex app-server`는 `item/agentMessage/delta`로 토큰 단위로 준다(209자에 112건). 스트리밍 설계가 이 사실 위에 서야 하고, **계약은 둘 다를 견디는 형태여야 한다** — 어느 표면을 쓰든 스펙이 흔들리지 않게.
4. **상태 코드는 첫 바이트와 함께 확정된다.** 스트림을 연 뒤에 발견한 실패는 어떤 방법으로도 상태 코드로 알릴 수 없다. 무엇을 스트림 밖에서 끝내고 무엇을 안으로 넣을지가 설계 결정이 된다.
5. **인증이 없는 것이 정상인 환경이 있다.** 기동과 헬스는 이미 그 전제로 짜여 있고(`tests/test_boot.py`가 고정한다), 이 change가 그 전제를 깨지 않으면서 인증 부재를 요청 시점에 명확히 드러내야 한다.

## Goals / Non-Goals

**Goals**

- 이벤트 **시퀀스 자체를 계약**으로 만든다 — 무엇이 몇 번, 어떤 순서로, 무엇으로 끝나는가.
- 상태 코드로 알릴 수 있는 실패와 스트림 안으로만 알릴 수 있는 실패의 **경계를 코드 구조에 새긴다**.
- "답할 수 없다"의 판정 주체를 둘로 나누고, 각각이 관측 가능한 서로 다른 사유를 남기게 한다.
- 출처를 **검증된 구조**로 닫는다 — 모델이 만든 문자열을 그대로 믿지 않는다.
- 에이전트 CLI를 **결정론적인 텍스트 생성기로 좁힌다**.
- 프롬프트를 LLM 없이 테스트할 수 있는 순수 함수로 둔다.

**Non-Goals**

- **비스트리밍 엔드포인트.** 결정 1.
- **캐싱.** 응답 봉투에 `cache_hit` 자리를 미리 뚫어 두지도 않는다 — 소비자가 없는 필드는 항상 거짓말(`false` 고정)로 시작한다. 다음 change가 필드와 함께 그 의미를 정한다.
- **대화 맥락·멀티턴.** 질문 하나가 요청 하나다. 스레드를 이어 붙이면 캐시 키가 대화 이력에 의존하게 되어 다음 change의 문제 크기가 달라진다.
- **재랭킹·질의 재작성·다단계 추론.** 검색 파이프라인을 고정한 이유(`add-qa-retrieval` 결정 9)가 여기서도 유효하다 — 답이 이상할 때 의심할 계층을 늘리지 않는다.
- **인용의 문장 단위 정렬.** 마커가 어느 문장에 붙었는지까지 구조화하지 않는다. 근거 청크 단위가 이 과제의 검증 가능한 최소 단위다.
- **토큰 사용량·비용 회계.** CLI가 사용량을 돌려주지만 소비자가 없다.

## Decisions

### 1. `/qa`는 SSE 전용이다. 비스트리밍 엔드포인트를 두지 않는다

`POST /qa` → `text/event-stream`. 같은 파이프라인을 JSON 한 방으로 내보내는 표면을 함께 두지 않는다.

- **계약이 둘이 되면 두 배로 틀린다.** 거절 두 갈래·인용 검증·오류 세 종류가 각 표면에서 각각 표현돼야 하고, 다음 change의 캐시는 두 경로 모두에 붙어야 한다. 표면 하나당 스펙 시나리오가 통째로 복제된다.
- **전체 답변만 필요한 소비자는 `done` 이벤트 하나만 읽으면 된다.** `done`이 `answer`·`citations`·`finish_reason`을 모두 들고 있으므로 정보가 부족하지 않다. 그래서 두 번째 표면이 주는 것은 편의뿐이다.
- 관측 지점은 이미 `POST /search`가 맡고 있다. 검색 단독 관측이 필요하면 그쪽이고, 생성까지 필요하면 `/qa`다.

기각한 대안:

- **`stream: false` 플래그로 같은 엔드포인트가 두 콘텐츠 타입을 낸다** — 같은 URL이 요청 본문에 따라 응답 타입을 바꾸면 OpenAPI 문서가 둘 중 하나만 기술하게 되고, 클라이언트 코드 생성이 깨진다.
- **`/qa/sync`를 따로 둔다** — 표면이 둘이라는 문제가 그대로다. 평가자의 `curl` 편의는 `curl -N`으로 충분히 해결되며 그 명령을 `README.md`에 적는다.

### 2. 이벤트 어휘는 넷, 종료는 하나

`sources` → `answer`* → (`done` | `error`). **이름 있는 SSE 이벤트**를 쓴다(`event:` 필드).

- **이름을 쓰지 않고 데이터 안의 `type` 필드로 구분하는 방식을 기각한다.** SSE는 이벤트 이름이 프로토콜 수준의 개념이고 브라우저 `EventSource`가 `addEventListener("sources", ...)`로 바로 분기한다. 데이터 안에 넣으면 모든 소비자가 파싱 후 분기를 다시 만들어야 한다.
- **종료 이벤트를 배타적으로 정확히 하나**로 두는 이유는 클라이언트의 상태 기계가 단순해지기 때문이다. `done`도 `error`도 없이 연결이 닫히는 경우를 계약이 허용하면 클라이언트는 모든 스트림에 대해 "정상 종료인가 끊긴 것인가"를 타임아웃으로 추정해야 한다.
- **`answer`가 0회일 수 있는 경우가 셋이다** — 근거 0건(`sources` 다음이 곧바로 `done`, `answer`는 빈 문자열), 시도 소진, 인증 실패(뒤의 둘은 `sources` 다음이 곧바로 `error`).

`done` 이벤트가 `answer` 전문을 **다시** 싣는 것은 중복이지만 의도한 중복이다. 조각을 이어 붙이는 책임을 모든 클라이언트에 지우지 않으면서, 이어 붙인 결과와 서버의 최종본이 같아야 한다는 불변식을 스펙이 검증 가능하게 만든다.

### 3. 검색은 스트림 **밖**에서 끝낸다 — 서비스가 두 단계로 갈라진다

```python
context = await qa_service.prepare(question, top_k=...)   # 예외가 그대로 올라온다 → 4xx / 503
return StreamingResponse(qa_service.stream(context), media_type="text/event-stream")
```

`prepare`는 질의 검증과 검색까지다. 여기서 나는 `EmptyQuery`·`QueryTooLong`·`InvalidTopK`·`StorageUnavailable`은 기존 오류 핸들러가 공통 봉투와 상태 코드로 바꾼다 — `/search`와 **완전히 같은 코드와 형식**이다. `stream`은 그 뒤부터이고, 여기서부터의 실패는 스트림 안의 `error` 이벤트로만 나간다.

**이 분할이 결정 4번(제약)을 코드 구조로 만든 것이다.** 두 단계를 한 async generator에 넣으면 첫 `yield` 전에 던진 예외가 FastAPI에서 어떻게 처리되는지가 프레임워크 내부 사정에 달리게 되고, 실제로는 이미 `200`과 `text/event-stream` 헤더가 나간 뒤에 예외가 터져 **본문 없는 200**이 된다. 그 형태는 스펙의 어떤 시나리오로도 잡히지 않는다.

부수 효과가 하나 있고 그게 오히려 이득이다 — `sources` 이벤트에 실을 값이 스트림이 시작되기 전에 이미 손에 있으므로, 첫 이벤트가 지연 없이 나간다.

**기각한 대안 — 검색도 스트림 안에서 하고 저장소 실패를 `error` 이벤트로 낸다.** 그러면 저장소가 죽은 상태의 관측이 `/search`(503)와 `/qa`(200 + error 이벤트)에서 갈린다. 같은 장애가 엔드포인트마다 다른 형태로 보이면 모니터링이 두 규칙을 들어야 한다.

### 4. 모델 출력은 **판정 줄 + 마커 산문**이다. `--output-schema`를 쓰지 않는다

모델에게 요구하는 형식:

```
VERDICT: ANSWERABLE
교육비는 연 200만원까지 지원됩니다 [1]. 신청은 부서장 승인 후 가능합니다 [1][2].
```

`--output-schema`(CLI가 지원하는 JSON Schema 강제 출력)를 **쓰지 않는다.** 결정의 근거가 셋이다.

- **JSON은 스트리밍과 원리적으로 충돌한다.** 부분 JSON은 파싱할 수 없으므로 답변 문자열을 꺼내려면 전체를 받아야 한다. 즉 스키마를 쓰는 순간 스트리밍은 오늘 델타가 없어서가 아니라 **형식 때문에** 불가능해지고, 나중에 CLI가 델타를 내기 시작해도 열리지 않는다. 스트리밍은 PRD의 하드 요구사항이고 구조화 출력은 그렇지 않다.
- **스키마가 검증 단계를 없애 주지 못한다.** 스키마는 `cited_chunks: [7]`의 형식은 보증하지만 근거가 2건뿐일 때 `7`이 존재하지 않는다는 사실은 보증하지 않는다. 어느 형식을 쓰든 **범위 검증은 우리가 한다.** 그렇다면 스키마가 대신해 주는 일은 괄호 세기뿐이고, 그건 정규식 한 줄이다.
- **판정 줄을 첫 줄에 두면 스트리밍과 판정이 양립한다.** 델타가 생기는 날 첫 줄만 버퍼링하면 판정을 즉시 알 수 있고 나머지는 그대로 흘려보낸다. JSON이면 판정이 어디에 있든 전체를 기다려야 한다.

**구조화 출력을 포기하는 것이 아니라 위치를 옮긴다.** 구조를 보증하는 곳이 모델이 아니라 서버다 — `done` 이벤트의 `citations`는 검증을 통과한 항목만 담긴 배열이고, 그 모양은 pydantic 응답 모델이 강제한다. 모델이 형식을 어겨도 소비자가 받는 구조는 흔들리지 않는다. 모델이 지키는 형식에 응답 구조를 의존시키는 쪽이 오히려 약하다.

`--output-schema`가 필요해지는 자리는 남겨 둔다 — 스트리밍이 아닌 배치 경로(예: 다음 change의 캐시 예열)가 생기면 그쪽에는 스키마가 맞다.

**파싱 규칙**

| 입력 | 처리 |
|------|------|
| 첫 줄 `VERDICT: ANSWERABLE` | 나머지가 답변, 마커 검증 진행 |
| 첫 줄 `VERDICT: INSUFFICIENT` | 나머지가 거절 문구, `citations` 비움 |
| 판정 줄 없음 | `ANSWERABLE`로 본다 + 경고 로그 |
| 본문이 비어 있음 | 생성 실패로 본다 (재시도 대상) |

판정 줄이 없을 때 **답변을 버리지 않는** 이유는, 그 본문이 이미 근거만 주어진 프롬프트에서 나온 것이라 형식 위반이 곧 환각은 아니기 때문이다. 마커 검증은 그대로 돌므로 출처 보증도 그대로다. 형식 위반은 응답이 아니라 **로그와 프롬프트 회귀 테스트**로 잡는다.

### 5. 인용은 마커를 검증해 조립한다

`\[(\d+)\]`로 답변 본문을 훑어 등장 순서대로 번호를 모으고, 중복을 제거하고, `1..len(sources)` 밖은 버린다. 남은 번호를 `sources`의 해당 결과에 대응시켜 `citations`를 만든다.

- **본문의 마커를 지우지 않는다.** 지우면 스트림으로 흘러간 문장과 `done.answer`가 달라져, 둘 다 받은 클라이언트가 무엇을 표시할지 알 수 없다. 마커는 인용 표기의 일부이지 내부 토큰이 아니다.
- **버린 개수를 응답에 싣는다**(`dropped_markers`). 숨기면 "인용이 왜 하나뿐인가"를 로그 없이 설명할 수 없고, 그 수가 늘어나는 것이 프롬프트가 나빠졌다는 가장 이른 신호다.
- **판정이 `INSUFFICIENT`면 마커를 무시한다.** "답할 수 없다"면서 근거를 인용하는 출력은 모순이고, 둘 중 판정을 이기게 하는 편이 안전하다 — 인용을 남기면 거절문에 출처가 붙어 답변처럼 보인다.
- 인용 항목의 값은 `ScoredChunk`에서 그대로 복사한다. 검색 결과가 곧 인용이라는 앞 change의 설계(`add-qa-retrieval` 결정 2)가 여기서 회수된다.

### 6. 거절의 판정 주체를 근거 유무로 가른다

| 사건 | 판정 주체 | 생성기 호출 | `finish_reason` | `answer` |
|------|----------|------------|-----------------|----------|
| 근거 0건 | 서비스 | **안 한다** | `no_evidence` | **빈 문자열** |
| 근거는 있으나 무관 | 생성기(프롬프트) | 한다 | `insufficient_evidence` | 생성기가 쓴 사유 |
| 답변 | 생성기 | 한다 | `stop` | 생성기가 쓴 답변 |

**근거가 0건일 때 부르지 않는 이유**는 문맥이 빈 프롬프트에서 모델이 쓸 수 있는 재료가 학습된 지식뿐이기 때문이다. "문서에 없으면 답하지 마라"는 지시로 그것을 막는 것보다 묻지 않는 편이 확실하고, 초 단위 지연과 호출 비용도 사라진다.

**그 대신 서비스가 문구를 쓰지도 않는다.** `answer`는 빈 문자열이고 `answer` 이벤트는 한 번도 나가지 않는다. 근거가 없다는 **사실**은 `finish_reason`이 나르고, 사용자에게 보일 **표현**은 소비자가 정한다.

이 선택으로 **"하드코딩된 응답" 경계가 논쟁이 아니라 구조가 된다.** 답변 문자열을 만드는 곳은 생성기뿐이며 예외가 없다 — PRD의 불합격 기준이 막으려는 것과 이 서비스의 실제 동작이 정확히 일치하므로, 해석의 여지 자체가 남지 않는다. 부수적으로 얻는 것도 있다: 문구가 서버에 있으면 언어·톤·제품 문맥에 따라 변형이 늘어나고 그때마다 서버가 답변 작성자에 가까워지는데, 그 미끄러짐이 시작될 자리가 없어진다.

대가는 소비자가 문구 하나를 들어야 한다는 것이고, 이는 `finish_reason`이 이미 열거형이라 분기 하나로 끝난다. **빈 `answer`의 의미를 하나로 고정하는 것**이 그 분기가 성립하기 위한 조건이라, 본문 없는 생성 출력을 성공으로 받지 않는다(결정 4의 파싱 표 — 빈 본문은 재시도 대상). 빈 `answer`에 도달하는 경로가 둘이면 소비자 화면에서 "근거가 없습니다"(정상)와 "모델이 아무것도 쓰지 않았습니다"(장애)가 같아진다.

**기각한 대안 — 근거가 0건이어도 항상 호출한다.** 판정 주체가 하나로 통일된다는 장점이 있지만, 아무 문맥 없이 "답하지 마세요"를 시키는 호출에 초 단위 지연과 구독 호출을 쓰게 되고, 무엇보다 그 호출이 성공적으로 답을 만들어 낼 여지를 스스로 연다.

### 7. 재시도는 서비스가, 타임아웃은 어댑터가

| 관심사 | 소유 | 이유 |
|--------|------|------|
| 한 시도의 시간 상한, 턴 중단과 자원 회수 | 어댑터 | 중단할 대상(턴)과 회수 방법을 아는 곳이 거기뿐이다 |
| 시도 횟수, 백오프, 재시도 가부 | 서비스 | 정책이다. 어댑터에 두면 생성기를 바꿀 때 정책이 따라 이사한다 |

**타임아웃이 프로세스를 죽이지 않는다.** 프로세스가 요청당 일회성이 아니라 **풀 자산**이기 때문이다(결정 9). 상한을 넘기면 `turn/interrupt`를 보내고 유예 안에 `turn/completed`가 오면 세션을 반납한다 — 오지 않으면 그때 폐기한다. `LlmTimeout`은 어느 쪽이든 동일하게 난다.

스펙의 "중단된 시도가 만든 자원(외부 프로세스 등)은 함께 정리되어야 한다"를 이렇게 읽는다: **시도가 만든 것은 thread와 turn이고 프로세스는 그 전부터 있다가 그 뒤에도 산다.** 둘 다 정리하므로(interrupt + `ephemeral` thread 폐기) 요구사항을 만족한다. 이 독법을 적어 두는 이유는 나중에 누가 "프로세스를 죽이라는 뜻"으로 읽고 풀을 해체하는 일을 막기 위해서다.

**재시도 가부의 규칙이 스트리밍 때문에 생긴다** — `answer` 이벤트가 하나라도 나갔으면 재시도하지 않는다. 두 번째 시도의 출력은 첫 시도를 이어 쓰는 것이 아니라 처음부터 다시 쓰는 것이라, 이어 붙이면 클라이언트가 앞부분이 두 번 적힌 답변을 본다. 서비스가 "첫 조각을 이미 내보냈는가"를 들고 있으므로 판정이 한 줄이다.

기각한 대안:

- **버퍼링해 두었다가 성공한 시도만 내보낸다** — 재시도가 항상 가능해지지만 스트리밍이 사라진다. 요구사항을 정면으로 포기하는 선택이다.
- **두 번째 시도의 출력을 클라이언트에 "재시작"으로 알린다** — `reset` 같은 이벤트를 하나 더 정의해야 하고, 모든 클라이언트가 렌더링 버퍼를 되감는 로직을 들어야 한다. 얻는 것(드문 경우의 복구 한 번)보다 계약이 비싸다.

**재시도 대상과 비대상**

| 사유 | 재시도 |
|------|--------|
| 시간 초과 (`LlmTimeout`) | 한다 |
| 세션 사망·핸드셰이크 실패·출력 파싱 실패·빈 본문 (`LlmGenerationFailed`) | 한다 |
| 인증 부재·만료 (`LlmUnauthenticated`) | **안 한다** (결정 9) |
| 이미 조각을 내보낸 뒤의 모든 실패 | **안 한다** |

어댑터가 실패를 이 **세 예외로 정규화**하므로, 생성 표면을 바꿔도(`exec` → `app-server`) 이 표와 서비스 코드는 그대로다.

백오프는 `base * 2^(n-1)`. 지터를 넣지 않는다 — 워커 1개에 동시 생성 상한이 2라(결정 11) 동기화된 재시도가 몰릴 규모 자체가 없고, 지터를 넣으면 "두 번째 대기가 첫 번째보다 길다"는 스펙 단언이 확률적이 된다.

### 8. `AnswerGenerator` — 프롬프트를 받아 텍스트 조각을 흘린다

```python
@runtime_checkable
class AnswerGenerator(Protocol):
    def generate(self, prompt: str, *, timeout_seconds: float) -> AsyncIterator[str]: ...
```

- **문자열 하나를 받는다 — 문맥 목록이 아니라.** 프롬프트를 조립하는 규칙은 도메인 지식이고 `core/prompting.py`에 있다. 어댑터가 청크를 받아 조립하면 프롬프트가 생성기 구현마다 하나씩 생기고, 프롬프트 회귀 테스트가 어느 어댑터의 것인지 정해야 한다.
- **조각을 yield 한다 — 완성본을 반환하지 않는다.** 델타가 없는 오늘의 구현은 조각 하나를 yield 하고 끝난다. 계약이 이미 여러 조각을 허용하므로, CLI가 델타를 내기 시작하면 어댑터만 바뀐다.
- **취소는 async generator 종료로 표현된다.** 소비자가 순회를 멈추면(`aclose`) 어댑터가 `finally`에서 프로세스를 죽인다. 별도의 `cancel()` 메서드를 두지 않는 이유는 그 메서드가 있으면 호출을 잊을 수 있고, 순회 종료는 잊을 수 없기 때문이다.
- 실패는 어댑터 경계에서 도메인 예외가 된다 — `LlmTimeout`·`LlmUnauthenticated`·`LlmGenerationFailed`. `asyncio.TimeoutError`나 `CalledProcessError`가 서비스까지 새면 계층 경계가 무의미해진다.

### 9. Codex 어댑터 — `app-server` 세션 풀 위에서, 에이전트를 텍스트 생성기로 좁힌다

`codex app-server`를 `asyncio.create_subprocess_exec`로 띄우고 stdio 위의 **줄 단위 JSON-RPC**로 대화한다. `initialize`/`initialized` 핸드셰이크 후 요청마다 `thread/start` → `turn/start`를 보내고, `item/agentMessage/delta` 알림의 `delta`를 yield 한다.

**`codex exec`가 아닌 이유는 실측이다.** 두 표면이 이렇게 다르다.

| | `codex exec --json` | `codex app-server` |
|---|---|---|
| 토큰 델타 | **없음** (4,808자도 한 이벤트) | **있음** (209자에 112건) |
| 요청당 지연 | 12 ~ 19초 | **4.5초** (세션이 따뜻할 때) |
| 인증 실패 판정 | 종료 코드 1 + 문구 매칭 | `codexErrorInfo.responseStreamDisconnected.httpStatusCode == 401` |
| 인증 실패까지 | 19.3초 (CLI 자체 재시도 10회) | 첫 401 알림이 **약 2초** |
| 성숙도 | 안정 | `[experimental]` |

스트리밍은 PRD의 하드 요구사항이고, 얻는 것이 그것 하나가 아니라 지연 3분의 1과 구조화된 인증 판정까지 셋이다. `[experimental]`을 감수하는 근거는 **되돌리기 비용이 낮다**는 것이다 — `AnswerGenerator` 계약이 안 바뀌므로 어댑터 디렉터리 하나를 `exec` 구현으로 되돌리면 끝난다.

**부품이 셋이다.**

```
adapters/llm/session.py   프로세스 하나 = 세션 하나. 기동 · 핸드셰이크 · JSON-RPC 송수신 ·
                          id로 응답 짝짓기 · 알림을 threadId로 갈라 큐에 넣기 · 생존 판정 · 회수
adapters/llm/pool.py      세션 풀. 지연 기동, 상한(qa_concurrency), 빌려주기/반납, 죽은 세션 교체
adapters/llm/codex.py     AnswerGenerator 구현. 턴 하나의 수명 · 델타 파싱 · 타임아웃 · 인증 판정
```

세션이 독립 부품인 이유는 거기에만 **두 개의 비동기 흐름**이 있어서다 — 우리가 보내는 요청과, 우리와 무관하게 흘러드는 알림. 이 라우팅이 어댑터에 섞이면 "델타를 어떻게 텍스트로 바꾸는가"와 "메시지를 누구에게 주는가"가 한 함수에서 얽힌다. 풀이 독립 부품인 이유는 이번에 새로 생기는 위험이 전부 거기 있어서다 — 죽은 세션, 상한 대기, 기동 실패. 가짜 프로세스로 실물 CLI 없이 전부 시험할 수 있다(결정 14).

**세션을 재사용하는 이유**는 기동 비용이 첫 요청에만 붙기 때문이다. `thread/start`의 첫 응답이 8.11초인데 두 번째는 **0.07초**다(그 8초는 인증·세션 준비다 — 인증 없는 상태에서는 0.16초에 끝난다). 요청마다 프로세스를 띄우면 `exec`보다 빨라지지 않고 델타만 얻는다.

**세션당 활성 턴은 하나**로 못 박는다. 풀 상한이 `qa_concurrency`와 같아 자연히 그렇게 되지만 명시적 규칙으로 둔다 — 한 세션에서 턴 둘을 돌리면 `turnId`가 없는 알림의 주인이 모호해지고, 동시 턴을 한 세션이 감당하는지 확인할 필요도 없어진다.

**thread는 요청마다 새로 판다**(`ephemeral: true`). 대화 맥락 없음(Non-Goals)이 유지되고 이전 요청의 문서 본문이 다음 문맥에 남지 않는다. 0.07초라 비용이 없다.

**반납의 불변식 — 애매하면 버린다.** 반납 전에 턴이 확실히 끝나 있어야 한다. 아니면 다음 요청이 이전 턴의 델타를 받는다. 반납 조건은 `turn/completed`를 받았을 때뿐이고, 그 외에는 전부 폐기다. 8초가 아깝지만 답변이 섞이는 것보다 훨씬 싸다.

**좁히는 조치들** — 이것이 이 어댑터의 핵심이다. 대상이 에이전트라 기본값이 우리가 원하는 것과 다르다.

조치는 그대로이고 **전달 경로만 CLI 플래그에서 JSON-RPC 파라미터로 옮겨진다.**

| 조치 | 어디에 싣는가 | 이유 |
|------|--------------|------|
| 프롬프트를 argv에 넣지 않는다 | `turn/start`의 `input` | argv에 넣으면 문서 본문이 프로세스 목록에 그대로 노출되고, 길이 상한(플랫폼별 100~200KB)이 문맥 크기의 숨은 천장이 된다. JSON-RPC는 그 천장 자체가 없다 |
| 작업 디렉터리를 **빈 임시 디렉터리**로 준다 | `thread/start`의 `cwd` | 에이전트가 파일을 뒤질 대상 자체를 없앤다. 리포 루트에서 돌면 소스 코드를 읽고 답할 여지가 생긴다 |
| 샌드박스를 **읽기 전용**으로 고정한다 | `thread/start`의 `sandbox` | — |
| 승인을 **비대화형**으로 고정한다 | `thread/start`의 `approvalPolicy: never` | 승인 프롬프트를 기다리며 매달리는 것이 타임아웃의 가장 흔한 원인이 된다 |
| 세션 파일을 남기지 않는다 | `thread/start`의 `ephemeral: true` | 요청 간에 맥락이 새지 않는다 |
| 프롬프트에 "제공된 근거 밖을 조회하지 말라"를 명시한다 | 프롬프트 본문 | 위가 전부 실패해도 남는 방어선 |
| 환경을 **상속하지 않고 최소 집합만** 넘긴다 (`HOME`·`PATH`·`CODEX_HOME`) | 프로세스 기동 | 컨테이너 환경변수에 저장소 접속 정보가 들어 있고, 그걸 에이전트에게 통째로 넘길 이유가 없다 |

**stdout을 줄 단위로 소비하는 것이 곧 스트리밍이다.** 델타 알림이 도착하는 즉시 yield 한다. 턴이 끝나기를 기다렸다가 `item.completed`의 완성본을 파싱하면 델타가 있어도 스트리밍이 되지 않는다.

**`item.completed`의 완성본은 출력에 쓰지 않는다.** 이미 델타로 다 나갔으므로 또 yield 하면 답변이 두 번 적힌다. **예외 하나** — 어떤 아이템에 델타가 0건인데 `item.completed`에 텍스트가 있으면 그때만 그 텍스트를 한 번 yield 한다. 델타가 사라지는 회귀가 나도 빈 답변(결정 4에서 생성 실패로 분류돼 헛재시도)이 아니라 `exec` 시절 동작으로 **degrade** 되게 하는 안전판이다.

**타임아웃은 턴을 중단하지 프로세스를 죽이지 않는다** — 프로세스가 풀 자산이기 때문이다(결정 7). `turn/interrupt` → 유예 안에 `turn/completed`가 오면 반납, 아니면 폐기.

**인증 판정이 문구가 아니라 구조다.** `error` 알림의 `codexErrorInfo.responseStreamDisconnected.httpStatusCode == 401`을 본다. CLI 버전에 따라 흔들리는 문구 매칭이 필요 없어졌고, 판정은 여전히 **어댑터 안에만** 있다.

**401은 `willRetry`와 무관하게 즉시 끊는다.** 실측에서 첫 401 알림이 `willRetry: true`로 왔다 — 그걸 "CLI가 알아서 하겠지"로 넘기면 CLI 자체 재시도 10회를 기다려 18.6초를 쓴다. 백오프를 몇 번 돌아도 자격증명이 생기지 않는다는 논리는 CLI의 재시도에도 그대로 적용된다. `willRetry`는 **401이 아닌** `error`에만 적용해 로그로만 남긴다(태우면 재시도가 이중으로 걸린다).

**종료 판정에 함정이 하나 있다.** `turn/failed`라는 알림은 **없다.** 실패해도 메서드는 `turn/completed`로 오고 성패는 `turn.status`에 있다 — 메서드 이름만 보면 실패를 성공으로 센다.

**stderr는 삼키지 않는다.** 별도로 읽어 실패 시 로그에 남긴다 — 응답에는 싣지 않는다(내부 메시지 노출 금지). `exec` 때보다 **더 중요하다**: 일회성 프로세스는 버퍼가 차봐야 그 요청만 멈추지만, 살아 있는 세션은 계속 쌓여 어느 순간 조용히 멎는다. app-server는 401마다 stderr에 ERROR 줄을 쓴다.

### 10. 프롬프트는 `core/`의 순수 함수 두 개, 그리고 판정 줄 분리 상태 기계

```python
def build_prompt(question: str, sources: Sequence[ScoredChunk]) -> str
def parse_answer(raw: str, source_count: int) -> ParsedAnswer   # verdict, body, markers, dropped

class VerdictSplitter:                              # 스트리밍용. 표준 라이브러리만
    def feed(self, chunk: str) -> list[str]: ...    # 내보낼 본문 조각들
    @property
    def verdict(self) -> Verdict | None: ...
```

**`VerdictSplitter`가 `services/`가 아니라 `core/`에 있는 이유**는 위 두 함수와 같다 — 출력 형식이 무엇을 뜻하는지는 도메인 지식이고, 순수 함수여야 비동기·페이크 없이 문자열 단언으로 회귀를 고정할 수 있다. 이 change에서 가장 틀리기 쉬운 로직인데 서비스에 두면 그 테스트가 페이크 생성기와 이벤트 시퀀스 위에 서게 된다.

실측이 이 부품을 필수로 만들었다. 판정 줄 하나가 델타 **7조각**에 걸쳐 온다 — `VER`·`DICT`·`:`·`' ANSW'`·`ER`·`ABLE`·`\n`. 결정 4가 "델타가 생기는 날 첫 줄만 버퍼링하면 된다"고 예측한 자리가 실제 코드가 되는 지점이다.

**규칙 둘**

- 개행이 오면 → 첫 줄을 판정으로 파싱. 형식이 맞으면 그 뒤가 본문, 안 맞으면 **첫 줄까지 통째로 본문**(결정 4: 답변을 버리지 않는다).
- 누적 문자열이 `VERDICT: ANSWERABLE`·`VERDICT: INSUFFICIENT` 어느 쪽의 접두사도 아니게 되는 순간 → 판정 없음으로 확정하고 **즉시 전부 내보낸다.**

두 번째 규칙이 없으면 판정 줄을 쓰지 않은 출력에서 첫 줄 전체(짧은 답이면 답변 전부)를 붙들게 된다. 하필 형식을 어긴 회차에서만 스트리밍이 죽는다. 이 규칙 덕에 **버퍼 상한이 21자로 고정된다** — 무한정 자라는 경로가 없다.

- **`core/`에 두는 이유**는 프롬프트가 도메인 지식이고, 순수 함수여야 LLM·네트워크·구독 없이 회귀를 문자열 단언으로 고정할 수 있기 때문이다. 프롬프트 문자열이 서비스나 어댑터 안에 흩어지면 "무엇을 지시했는가"의 진실 원천이 사라진다.
- `core/`는 표준 라이브러리만 쓴다는 기존 규약을 지킨다 — 정규식과 문자열 연산뿐이다.
- **프롬프트에 버전 상수를 둔다**(`PROMPT_VERSION`). 다음 change의 캐시 키에 들어가야 할 값이다 — 프롬프트가 바뀌면 같은 질문의 답이 달라지므로, 버전이 키에 없으면 프롬프트 개선이 낡은 캐시에 가려 관측되지 않는다. 여기서 값을 만들어 두고 키 설계는 그쪽에 넘긴다.

문맥 블록의 모양은 검색 결과가 이미 들고 있는 값으로만 만든다:

```
[1] company-policy.txt (문자 120–540)
<청크 본문>

[2] development-guide.md (3쪽)
<청크 본문>
```

파일명과 위치를 문맥에 넣는 이유는 두 가지다 — 모델이 "어느 문서에서 왔는가"를 답변 문장에 녹일 수 있고, 마커가 가리키는 대상이 사람이 읽어도 확인 가능해진다. 설계 의도 전체는 `PROMPT_DESIGN.md`에 적는다.

### 11. 계층 배치와 자원 상한

```
api/routes/qa.py     요청 모델, prepare 호출(예외 → 상태 코드), StreamingResponse 조립, 로깅
api/sse.py           SSE 프레이밍 — event:/data: 직렬화, 하트비트 주석
services/qa.py       프롬프트 조립 → 생성 → 재시도 → 이벤트 시퀀스 산출
core/answers.py      FinishReason, Citation, 조립된 답변 값 객체
core/prompting.py    build_prompt / parse_answer (표준 라이브러리만)
adapters/llm/session.py  app-server 프로세스 수명·핸드셰이크·JSON-RPC 송수신·알림 라우팅
adapters/llm/pool.py     세션 풀 — 지연 기동·상한·죽은 세션 교체
adapters/llm/codex.py    턴 수명·델타 파싱·타임아웃·취소·인증 판정
```

**SSE 프레이밍이 `api/`에 있는 이유**는 그것이 전송 형식이기 때문이다. 서비스는 `QaEvent` 값 객체를 yield 하고, `event:`/`data:`/빈 줄로 바꾸는 일은 라우터가 한다. 서비스가 문자열 `"event: done\n\n"`을 만들면 서비스 테스트가 SSE 문법을 단언하게 되어, 전송 형식을 바꿀 때 서비스 테스트가 깨진다.

**하트비트는 SSE 주석(`: keep-alive`)이다.** 이벤트가 아니므로 클라이언트 파서에 나타나지 않고, 계약을 건드리지 않은 채 프록시의 유휴 연결 종료만 막는다. 간격 기본값 15초는 흔한 프록시 기본 유휴 상한(60초)의 4분의 1이다.

**동시 생성 상한을 둔다**(`qa_concurrency`, 기본 2). 생성 하나가 app-server 세션 하나이고 세션 하나가 Node 프로세스 하나다 — 상한이 없으면 동시 요청 수만큼 프로세스가 뜨고 컨테이너 메모리가 요청 수에 비례한다. **세션 풀의 상한이 이 값과 같아** 세마포어와 풀이 같은 수를 두 번 세지 않는다. 수집이 같은 이유로 이미 세마포어를 쓰고, 같은 규율을 따른다: **상한에 걸린 요청은 실패하지 않고 대기한다.** 대기 중에도 `sources`는 이미 나갔고 하트비트가 연결을 유지하므로, 사용자에게는 생성이 느린 것과 구분되지 않는다.

### 12. 오류 코드 두 개를 추가한다

`llm_unavailable`(시도 소진)과 `llm_unauthenticated`(인증 부재). 기존 `ErrorCode`에 **추가만** 한다.

- **두 코드를 나누는 이유**는 소비자가 할 일이 다르기 때문이다. 앞은 재시도나 상한 조정이고, 뒤는 자격증명 주입 경로 확인이다. 뭉치면 평가자가 `.secrets/codex/auth.json`을 볼 이유를 못 찾는다.
- **타임아웃에 별도 코드를 주지 않는다.** 타임아웃은 그 자체로 스트림을 끝내지 않으므로 종료 코드가 될 자격이 없다 — 스트림을 끝내는 것은 "시도가 다 떨어졌다"는 사건이고, 마지막 실패가 타임아웃이었다는 사실은 `error` 이벤트의 `reason`이 말한다. 코드는 종료 사건을, `reason`은 그 원인을 가리킨다.
- 두 코드 모두 `_CODE_TO_STATUS`에 `503`으로 등록한다. 오늘 이 매핑을 타는 경로는 없지만(둘 다 스트림 안에서만 나온다), 표에 없는 코드가 `500`이 되는 기본값 때문에 나중에 비스트리밍 경로가 생기면 조용히 틀린 상태가 나간다.

`error` 이벤트의 데이터는 오류 봉투와 **같은 어휘**를 쓴다 — `code`·`message`에 `attempts`·`reason`이 붙는다. 봉투 구조까지 같게 하지는 않는다(`{"error": {...}}`로 한 겹 더 싸지 않는다) — SSE는 이벤트 이름이 이미 "이건 오류다"를 말하므로 중첩이 정보를 더하지 않는다.

### 14. 테스트는 다섯 겹이다

app-server로 오면서 둘이 늘었다 — 새로 생긴 위험(판정 줄이 델타로 쪼개짐, 프로세스가 상태를 가짐)이 각각 자기 층을 요구한다.

| 층 | 검증 대상 | 무엇으로 | 실행 조건 |
|----|----------|---------|----------|
| 시퀀스·정책 | 이벤트 순서, 거절 두 갈래, 인용 검증, 재시도·오류 3종 | **스크립트된 페이크 생성기** | 항상 |
| 판정 줄 분리 | 델타가 판정 줄을 쪼개는 전 경우 | `VerdictSplitter` 순수 함수 — **문자열 단언만** | 항상 |
| 알림 파싱 | 델타 알림 → 텍스트 조각, 401 판정, 종료 판정 | 없음 — **저장된 실물 알림 샘플** | 항상 |
| 세션·풀 수명 | 타임아웃·사망·취소·핸드셰이크 실패·상한 대기 | **가짜 app-server 스크립트** | 항상 |
| 실물 | CLI가 실제로 답을 만드는가 | 실물 CLI | 마커로 격리, 기본 제외 |

- **페이크 생성기가 이 change의 테스트 하네스 핵심이다.** 조각 목록·조각 사이 지연·N번째 호출에서의 예외를 스크립트로 받고, 호출 횟수를 센다. 스펙의 THEN에 있는 "생성기 호출 횟수가 `2`", "한 번도 호출되지 않는다"가 전부 이 카운터로 관측된다.
- **알림 파싱을 실물 CLI 없이 검증하려면 진짜 출력 샘플이 필요하다.** 손으로 지어낸 샘플은 우리가 상상한 형식을 검증할 뿐이다. 실측 태스크에서 실제 알림 스트림을 파일로 떠서 픽스처로 커밋한다 — 그 파일이 곧 "우리가 무엇을 보고 파서를 만들었는가"의 증거가 된다.
- **가짜 app-server가 프로세스 실패를 재현한다.** 같은 줄 단위 JSON-RPC를 말하는 짧은 파이썬 스크립트이고, 인자로 어떻게 망가질지를 지시받는다 — 핸드셰이크 무응답, 턴 도중 사망, 침묵(타임아웃), `turn/interrupt` 무시(세션 폐기 경로), 401, 델타 사이 지연. **실물 CLI로는 인위적으로 만들 수 없는 것들이라, 이 층은 실물 층의 대체재가 아니라 실물 층이 닿지 못하는 곳이다.** 전부 즉시 응답하므로 타임아웃 상한을 수십 ms로 두면 밀리초 단위로 끝난다.
- **실물 층은 기본 실행에서 빠진다.** `pytest` 한 줄이 구독과 네트워크에 묶이면 안 된다는 기존 규율 그대로다. 임베딩 품질 테스트가 가중치 유무로 갈리는 것과 같은 자리이고, 실행 방법을 `README.md`에 적는다.

시간에 의존하는 단언(하트비트 간격, 백오프 증가, `sources` 선행)은 **실제 대기 대신 관측된 시각 차**로 잰다. 페이크가 조각 사이 지연을 만들 수 있으므로 짧은 값(수십 ms)으로 관계만 확인하고 절대 시간을 단언하지 않는다.

### 15. 스트리밍 입자도는 실측하고, 흉내 내지도 되돌리지도 않는다

**표면마다 다르다는 것이 실측의 결론이다.** `codex exec --json`은 토큰 델타가 없어 4,808자 답변도 `item.completed` 한 이벤트로 온다. `codex app-server`는 209자 답변을 `item/agentMessage/delta` **112건**으로 흘린다. 우리는 후자를 쓴다(결정 9).

**서버는 그 조각을 다시 만지지 않는다.** 쪼개지도, 합치지도 않는다.

- **쪼개면** 얻는 것은 "스트리밍처럼 보이는 화면"뿐이고 — 첫 글자가 도착하는 시각은 1밀리초도 앞당겨지지 않는다 — 잃는 것은 문서와 구현의 일치다.
- **합치면**(예: 델타를 모아 문장 단위로 내보내면) 실제로 앞당겨진 도착을 되돌리는 일이 된다. 델타가 없던 시절에는 존재하지 않던 실수 방향이라 명시해 둔다.

유일한 예외가 **판정 표시 제거**이고, 그건 조각을 재조립하는 것이 아니라 확정 전까지 보류했다가 본문만 흘려보내는 것이다(결정 10). 스펙이 이 예외를 이미 그렇게 그어 두었다.

**이 change가 계약을 되돌리지 않는 것이 설계의 값이다.** `AnswerGenerator`의 "조각 0회 이상"과 스펙의 시나리오들은 델타가 없다고 가정하지 않았기 때문에, 표면을 바꾸는데 **어댑터 안쪽만** 바뀌었다 — 스펙 0줄, 서비스 0줄. 그러라고 계약을 그렇게 썼고, 여기서 그 값을 회수했다.

`sources` 선행의 이득은 여전히 별개로 진짜다(생성 지연 전체만큼 앞선다).

## Risks / Trade-offs

**[`app-server`가 `[experimental]`이다]** → 프로토콜이 예고 없이 바뀌면 델타 파싱이 깨진다. 완화: 알림 파싱을 저장된 실물 샘플로 고정하고, `AnswerGenerator` 계약이 안 바뀌므로 최악의 경우 어댑터 디렉터리 하나를 `exec` 구현으로 되돌린다. **되돌리기 비용이 낮다는 것이 이 실험을 감수하는 근거다.**

**[프로세스가 상태를 갖게 됐다]** → 일회성 프로세스에는 없던 실패 모드가 생긴다 — 죽은 세션, 반쯤 끝난 턴, 이전 턴의 델타 누수. 완화: 세션당 활성 턴 하나, 반납 조건을 `turn/completed` 하나로 좁힘, 애매하면 폐기(결정 9). 가짜 app-server가 이 셋을 전부 시험한다(결정 14).

**[기동 8초가 첫 요청에 몰린다]** → 첫 `/qa`는 여전히 12초대다. 완화: **하지 않는다.** 기동 시 예열하면 부팅 경로가 CLI를 건드리게 되어 `tests/test_boot.py`의 계약이 깨진다 — 자격증명이 없는 환경에서 기동이 느려지거나 실패하는 쪽이 훨씬 비싸다. 첫 요청이 느린 것은 받아들인다.

**[에이전트 CLI가 우리가 주지 않은 것을 보러 갈 수 있다]** → 도구 실행이 가능한 실행체다. 완화: 빈 작업 디렉터리·읽기 전용 샌드박스·최소 환경·프롬프트 지시의 네 겹(결정 9). 그럼에도 이것이 HTTP API가 아닌 대가이고, 남는 위험은 "우리가 좁힌 방식이 CLI 버전 변화에 의존한다"는 것이다 — 실측으로 고정하고 값이 바뀌면 `ARCHITECTURE.md`를 함께 고친다.

**[인증 판정이 CLI의 종료 코드·문구에 의존한다]** → 버전이 바뀌면 인증 오류가 일반 실패로 분류될 수 있다. 완화: 판정을 어댑터 한 곳에 가두고, 오분류의 결과가 "재시도 두 번 더 하고 다른 코드로 실패"라서 잘못된 성공이 되지 않게 설계했다. 실제 문구를 실측해 상수로 고정한다.

**[모델이 출력 형식을 지키지 않을 수 있다]** → 판정 줄 누락, 마커 없음, 존재하지 않는 마커. 완화: 세 경우 모두 파서가 정의된 동작을 갖고(결정 4·5), 스펙 시나리오가 각각을 고정하며, 버려진 마커 수가 응답에 실려 열화가 관측된다. 근본적으로는 프롬프트 품질 문제이고 `PROMPT_DESIGN.md`가 그 근거를 남긴다.

**[근거 없음의 문구를 소비자가 들어야 한다]** → 서버가 `answer`를 비워 보내므로 화면에 무엇을 띄울지는 클라이언트의 몫이다(결정 6). 완화: `finish_reason`이 열거형이라 분기 하나로 끝나고, `sources.count == 0`이 같은 사실을 독립적으로 확인해 준다. `README.md`의 `curl` 예시에 그 종료 형태를 그대로 실어 소비자가 무엇을 받는지 먼저 보게 한다. 대신 얻는 것이 크다 — 답변 문자열을 만드는 곳이 생성기뿐이라는 규칙에 예외가 없어져 "하드코딩된 응답" 경계가 해석 문제에서 구조 문제로 바뀐다.

**[빈 `answer`의 의미가 갈리면 장애가 조용해진다]** → 모델이 판정 표시만 내고 본문을 못 낸 회차가 성공으로 집계되면, 사용자에게는 근거 없음과 똑같은 빈 화면으로 보인다. 완화: 본문 없는 출력을 생성 실패로 다뤄 재시도에 태우고, 소진되면 `error`로 끝낸다(결정 4). 스펙이 "빈 `answer`로 끝나는 종료는 `no_evidence`뿐"을 단언하므로 이 규칙이 깨지면 테스트가 먼저 깨진다.

**[테스트 대부분이 페이크 위에서 돈다]** → 실물 CLI에서만 드러나는 실패(프로세스 인자 형태, JSON-RPC 스키마 변화)를 잡지 못한다. 완화: 알림 파싱 층이 **실제 알림 샘플**을 픽스처로 쓰고, 실물 층이 마커 뒤에 존재하며, 컨테이너 안에서 그 층을 돌리는 명령을 `README.md`에 적는다.

**[프로세스 기반 생성이 동시성에 비싸다]** → 동시 생성 하나당 Node 프로세스 하나. 완화: 동시 상한 2(결정 11)이고 **풀 상한이 같은 값이라 프로세스 수가 그 위로 늘지 않는다.** 대가는 상한에 걸린 요청의 대기이고, 그 대기는 `sources`가 이미 나간 뒤라 사용자에게는 느린 생성과 구분되지 않는다. 재고 시점은 명확하다 — 대기가 생성 시간에 비해 눈에 띄기 시작할 때이고, 그때 필요한 것은 상한 조정이 아니라 작업 큐다.

**[`done`이 답변 전문을 중복해 싣는다]** → 긴 답변에서 전송량이 두 배가 된다. 완화: 이 과제 규모(수백~수천 자)에서 무시할 만하고, 그 대가로 "조각을 이어 붙인 것 = 최종본"이라는 불변식이 검증 가능해진다(결정 2).

## Migration Plan

배포 절차상의 변경은 없다. 새 파이썬 의존성도 새 컨테이너도 없고 — `codex` CLI와 자격증명 주입 경로는 이미 이미지와 compose에 있다 — 새 엔드포인트는 추가일 뿐이며 기존 엔드포인트의 동작은 그대로다.

저장소 마이그레이션도 없다. `/qa`가 읽는 것은 검색 결과뿐이고, 이미 색인된 문서는 재수집 없이 그대로 답변에 쓰인다.

되돌리기는 라우터 등록을 빼면 된다. `AnswerGenerator` 추가와 오류 코드 추가는 기존 경로의 관측 가능한 동작을 바꾸지 않으므로, `/qa`를 걷어내도 수집·검색·헬스가 영향받지 않는다.

**인증이 없는 환경에서의 동작이 배포 전 확인 항목이다** — 기동 성공, `/health` 200, `/documents`·`/search` 정상, `/qa`만 `error` 이벤트. 이 조합이 성립해야 "자격증명 없는 평가자 환경에서도 실행 가능"이 유지된다.

## Open Questions

- **다음 change의 캐시 키에 무엇이 들어가는가.** 이 change가 그 재료를 전부 만든다 — 질문 문자열, `top_k`, 인용된 문서의 `(document_id, revision)`, `PROMPT_VERSION`, 모델 식별자. 어느 조합을 키로 삼고 어느 것을 무효화 태그로 삼을지는 캐싱 change의 설계 결정이며, 여기서 미리 정하면 아직 없는 캐시를 가정한 구조가 남는다. **이 change가 넘기는 미해결 항목이 하나 더 있다** — `add-qa-retrieval`이 명시적으로 넘긴 것, 즉 결과에 실린 `revision`은 *결과 조립 시점*까지만 현재이므로 그것을 영속화(캐시)하는 쪽이 현재성을 다시 확인해야 한다는 계약이다. `/qa`는 영속화하지 않으므로 이 change에서는 성립하고, 캐싱 change의 design이 다시 다뤄야 한다.
- **오래 사는 세션이 자격증명 갱신을 만나면 어떻게 되는가.** `docs/SPIKES.md` S-3이 묻는 것과 같은 질문이지만, 세션이 요청 사이에 살아 있으므로 만날 확률이 일회성 프로세스보다 높다. 갱신이 세션 안에서 조용히 되는지, 아니면 턴 하나가 실패하고 다음 턴부터 복구되는지 모른다. 후자라도 그 실패는 `LlmGenerationFailed`가 되어 재시도가 흡수하므로 이 change의 구조를 바꾸지 않는다. S-3에 이 사실을 덧붙인다.
- **문맥 총량 상한이 필요한가.** `top_k` 상한 50 × 청크 600자 ≈ 30KB가 최악의 프롬프트 크기다. 모델 입력 창을 넘으면 CLI가 어떻게 반응하는지(오류인가 절단인가)를 아직 모른다. 실측 결과에 따라 상한을 두는 설정이 필요할 수 있으나, 기본 `top_k`가 5라 정상 경로에서는 닿지 않으므로 이 change의 스펙·구조를 바꾸지 않는다. 실측 태스크의 결과를 `ARCHITECTURE.md`에 적고, 필요하면 설정 항목 하나를 더하는 것으로 끝난다.
