## Context

백지 상태에서 시작한다. 동기는 proposal.md — Why 참조. 요구사항은 specs/service-health/spec.md 참조.

이 change의 설계를 좌우하는 제약은 세 가지다.

1. **항상 실행 가능해야 한다.** 어느 시점에 체크아웃해도 한 줄 명령으로 뜨고 한 줄 명령으로 테스트가 돈다.
2. **`claude-code-sdk`는 로컬 CLI를 호출하는 형태다.** 순수 HTTP 클라이언트가 아니라 별도 런타임과 구독 인증에 의존한다. 이 성질이 컨테이너 이미지 구성에까지 번진다.
3. **이후 change가 이 골격 위에 얹힌다.** 지금 정한 레이어 경계와 어댑터 계약이 ingestion·retrieval·QA·캐싱의 전제가 된다. 여기서 잘못 그으면 네 번 고쳐야 한다.

## Goals / Non-Goals

**Goals**

- 레이어 경계와 어댑터 계약을 코드로 고정한다. 이후 change는 경계를 새로 협상하지 않고 채우기만 한다.
- 의존성 상태를 한 번의 요청으로 판별 가능하게 한다.
- 외부 인증 부재가 기동 경로 어디에도 스며들지 않게 한다.
- 테스트 픽스처를 만들어, 이후 change의 테스트가 하네스부터 만들지 않게 한다.

**Non-Goals**

- **LLM 호출 설계는 여기서 하지 않는다.** 스트리밍 프로토콜, timeout·retry 정책, 구조화 출력, 프롬프트 조립은 전부 QA change의 설계 대상이다. 이 change는 LLM 어댑터를 호출하지 않으므로 그 계약을 지금 확정하면 근거 없는 추측이 된다. 단 이미지 구성만은 예외다(아래 결정 5).
  - **인증이 없을 때 LLM 기능 요청이 어떤 오류를 반환하는가**도 여기 포함된다. 호출할 기능 자체가 없는 상태에서 그 오류 형태를 규정하면 검증할 수단이 없는 요구사항이 된다. 이 change가 책임지는 것은 "인증이 없어도 기동과 헬스가 성립한다"는 성질까지다.
- **캐시 설계도 여기서 하지 않는다.** 키 구성, 유사도 판정, 무효화 시 캐시-문서 의존 관계 추적은 캐싱 change의 대상이다. 이 change는 캐시 저장소에 ping만 보낸다.
- 벡터 스토어의 컬렉션 스키마, 청킹 전략, 임베딩 모델 로딩 시점. 전부 ingestion change로 미룬다.
- 인증·인가, 레이트 리밋, 관측성 백엔드 연동.

## Decisions

### 1. 레이어는 디렉터리로 강제하고, 어댑터는 프로토콜 뒤에 둔다

```
src/app/
  api/         라우터. HTTP 관심사만 — 검증, 상태 코드, 응답 직렬화
    routes/health.py
    errors.py           도메인 예외 → HTTP 응답 변환 (이 계층에서만)
  services/    유스케이스 오케스트레이션
    health.py           프로브들을 모아 전체 상태를 판정
  core/        도메인 — 프레임워크·외부 라이브러리를 import 하지 않는다
    exceptions.py       도메인 예외 기반 클래스
    models.py           상태 값 객체
  adapters/    외부 경계
    protocols.py        Protocol 정의
    vector_store/       임베디드 벡터 스토어 어댑터
    cache/              캐시 저장소 어댑터
  config.py    환경변수 → 설정 객체
  main.py      앱 팩토리, 의존성 배선, 수명주기 훅
```

`core/`가 프레임워크를 import 하지 않는다는 규칙 하나가 레이어 역전을 실제로 막는다. 컨벤션 문서가 아니라 import 그래프로 강제되므로 어겼을 때 눈에 띈다.

의존성 배선은 앱 팩토리에서 한 번 하고 FastAPI 의존성 주입으로 내려보낸다. 모듈 전역 싱글턴을 두지 않는 이유는 테스트에서 교체가 어려워지기 때문이다.

**대안 — 단일 모듈로 시작하고 나중에 쪼갠다**: 지금은 파일이 몇 개 안 되니 과해 보인다. 그러나 이후 네 개의 change가 각자 어디에 코드를 놓을지 매번 판단하게 되고, 그 판단이 엇갈리면 나중에 옮기는 비용이 지금 디렉터리를 만드는 비용보다 크다. 기각.

### 2. 어댑터 계약은 지금 필요한 만큼만 정의한다

이 change가 어댑터에 요구하는 동작은 "너 살아 있냐" 하나다. 따라서 좁은 프로토콜 하나만 정의한다.

```
HealthProbe
  name  -> str            보고에 쓰일 의존성 이름
  check() -> ProbeResult  도달 가능 여부 + 실패 시 요약 사유
```

벡터 스토어 어댑터와 캐시 어댑터가 각각 이걸 구현한다. `VectorStore`(upsert/query/delete)나 `CacheStore`(get/set/invalidate) 같은 넓은 프로토콜은 **정의하지 않는다.** 소비자가 없는 상태에서 정한 인터페이스는 실제 사용처가 생기는 순간 거의 반드시 틀린 것으로 드러나고, 그때는 이미 문서에 적혀 있어서 고치는 데 설명이 붙는다. 각 프로토콜은 그것을 실제로 쓰는 change에서 그 change의 요구에 맞춰 정의한다.

**대안 — 전체 어댑터 인터페이스를 지금 다 설계한다**: "나중에 흔들리지 않는다"는 이점이 있어 보이지만, 흔들리지 않는 게 아니라 틀린 채로 굳는다. 기각.

### 3. 임베디드 벡터 스토어의 "도달 가능"은 네트워크가 아니라 저장소 접근이다

벡터 스토어를 임베디드 퍼시스턴트 모드로 쓰기로 이미 정해져 있다(별도 컨테이너 없이 볼륨 하나로 영속화 — 한 줄 실행이 단순해진다). 그래서 캐시 저장소와 헬스 점검의 의미가 다르다.

| | 캐시 저장소 | 벡터 스토어 |
|---|---|---|
| 배치 | 별도 컨테이너 | 프로세스 내부 + 마운트된 볼륨 |
| 불능의 의미 | 네트워크 도달 불가, 인증 실패 | 볼륨 미마운트, 권한 없음, 디스크 꽉 참 |
| 점검 방법 | 연결 후 ping | 클라이언트 초기화 + 퍼시스턴스 경로 쓰기 가능 확인 |

둘 다 `HealthProbe`로 추상화되므로 서비스 계층은 이 차이를 모른다. 다만 **벡터 스토어 프로브가 진짜로 볼륨을 건드려야 한다**는 점이 중요하다. 클라이언트 객체 존재 여부만 보면 볼륨이 안 붙은 채로 "정상"이 나오고, 그 상태로 ingestion change를 시작하면 첫 업로드에서 터진다.

부수 효과로, 임베디드 모드는 파일 락을 쓰므로 **워커 프로세스는 1개로 시작한다.** 다중 워커가 필요해지면 벡터 스토어를 별도 서비스로 분리해야 하고, 그건 그때의 결정이다.

### 4. 헬스 실패는 503으로 낸다

전체 정상이면 200, 필수 의존성 중 하나라도 불능이면 503. 본문은 두 경우 모두 같은 구조로 각 의존성 상태를 개별 보고한다.

**503일 때도 공통 오류 봉투(결정 6)를 쓰지 않는다.** 헬스는 오류를 알리는 엔드포인트가 아니라 상태를 보고하는 엔드포인트다. 503과 200의 본문 구조가 갈리면 소비자가 두 파서를 들고 있어야 하고, 정작 "어느 의존성이 문제인가"라는 정보가 오류 메시지 문자열 안으로 뭉개진다. 의존성 목록은 정상 여부와 무관하게 항상 같은 집합으로 내보내, 키가 사라지는 것과 값이 비정상인 것을 구분할 필요가 없게 한다.

프로브가 도달 불가가 아닌 **예상치 못한 예외**를 던지는 경우도 불능과 동일하게 취급한다. 서비스 계층이 예외를 잡아 해당 프로브만 비정상으로 기록하고 나머지 프로브 결과는 그대로 보고한다. 프로브 하나의 버그가 헬스 엔드포인트 전체를 500으로 만들면, 정작 진단해야 할 때 아무것도 못 본다.

**대안 — 항상 200을 주고 본문의 상태 필드로만 구분한다**: 사람이 읽기엔 차이 없지만, compose 헬스체크나 오케스트레이터 같은 자동 소비자가 상태 코드만 보고는 판단할 수 없다. 기각.

프로브는 병렬로 실행하고 **각각에 개별 타임아웃**, 전체에도 상한을 둔다. 하나가 매달려도 나머지 결과는 나와야 어느 의존성이 문제인지 식별할 수 있다. 벡터 스토어 프로브는 파일 I/O라 블로킹이므로 스레드풀로 오프로드한다 — 이벤트 루프를 막지 않는다는 규약이 여기서 처음 적용된다.

compose 헬스체크를 이 엔드포인트에 걸 때는 주의한다. 캐시가 늦게 뜨는 동안 API가 503을 내면 재시작 루프에 빠질 수 있으므로, 기동 유예(start period)를 충분히 준다.

### 5. 컨테이너 이미지에 LLM CLI 런타임을 지금 포함한다

**이 change의 Non-Goals를 의도적으로 한 칸 넘는 결정이다.** 근거를 남긴다.

`claude-code-sdk`는 로컬 CLI를 실행한다. 즉 컨테이너 안에서 답변을 생성하려면 파이썬만으로 부족하고 별도 런타임과 CLI 바이너리, 그리고 인증 상태가 필요하다. 이걸 QA change까지 미루면 그 시점에 베이스 이미지와 설치 계층을 다시 짜야 하고, 최악의 경우 "컨테이너 안에서는 SDK가 동작하지 않는다"는 사실을 마감에 가까워서 발견하게 된다.

그래서 지금 결정한다.

- 런타임 이미지에 CLI 실행에 필요한 런타임과 CLI를 함께 설치한다.
- 인증 상태는 이미지에 굽지 않고 **호스트의 기존 자격증명을 파일로 주입**한다(방식은 결정 5-1). 자격증명을 이미지에 넣으면 리포에 남고, 평가자 환경마다 인증 주체가 다르다.
- 자격증명이 없어도 기동은 성공해야 한다(specs의 요구사항). 즉 **부팅 경로에서 CLI를 실행하지 않는다.** LLM 어댑터는 지연 초기화하고, 첫 호출 시점에만 CLI를 건드린다.
- 이 change에서는 CLI를 **호출하지 않는다.** 설치와 주입 경로만 준비하고, 실제 동작 검증은 QA change의 첫 태스크로 남긴다.

대가는 이미지 크기와 빌드 시간이다. 베이스 이미지를 나중에 갈아엎는 비용보다 싸다고 판단했다.

### 5-1. 자격증명은 호스트의 기존 것을 꺼내 파일로 마운트한다 (새로 발급하지 않는다)

**제약**: 호스트(macOS)와 컨테이너 어느 쪽에서도 토큰을 새로 발급하지 않는다. 호스트에 이미 있는 인증 상태를 재사용한다.

이 제약이 방식을 거의 결정한다. 실측한 사실 두 가지가 근거다.

```
자격증명 저장 위치
  macOS   Keychain 항목 "Claude Code-credentials"   ← 파일 아님. 볼륨 마운트 불가
  Linux   ~/.claude/.credentials.json               ← 파일

Keychain 블롭의 구조
  claudeAiOauth: { accessToken, refreshToken, expiresAt,
                   refreshTokenExpiresAt, scopes,
                   subscriptionType, rateLimitTier }
  → Linux가 읽는 .credentials.json 포맷과 동일하다. 꺼내서 그대로 쓰면 된다.

토큰 수명 (실측)
  accessToken   약 8시간
  refreshToken  약 5.7일
```

**access token이 8시간짜리라는 사실이 핵심이다.** 컨테이너는 살아 있는 동안 반드시 갱신을 하게 되므로, 토큰 한 개를 꺼내 환경변수로 박아두는 방식은 그날 안에 죽는다. 갱신 가능한 형태로 넣어야 한다.

**결정**

- 호스트에서 기존 자격증명을 꺼내 프로젝트 하위의 비밀 디렉터리에 파일로 쓴다. macOS면 Keychain에서 읽고, 이미 파일로 있는 환경(Linux)이면 그대로 복사한다. **OS를 분기하되 평가자가 실행하는 명령은 하나다.**
- 그 파일을 컨테이너의 자격증명 경로에 **쓰기 가능하게** 마운트한다. 읽기 전용으로 붙이면 갱신에 실패해 8시간 뒤 죽는다.
- 추출은 기동할 때마다 수행한다. 컨테이너가 항상 호스트의 최신 상태로 시작하므로, 사본이 오래 묵는 창을 컨테이너 수명으로 제한한다.
- 비밀 디렉터리는 형상관리에서 제외한다.

**대안 1 — `claude setup-token`으로 장기 토큰 발급**: 컨테이너 친화적이고 OS 무관하다. 그러나 **새 토큰을 발급하므로 제약 위반**이다. 기각.

**대안 2 — 기존 access token만 꺼내 환경변수로 전달**: 재발급은 아니지만 갱신 경로가 없다. 실측 수명 8시간이라 평가자가 다음 날 실행하면 동작하지 않는다. 기각.

**대안 3 — Codex CLI로 전환**: 자격증명이 처음부터 평문 파일이라 추출 없이 그대로 마운트되고, 호스트와 컨테이너가 **같은 파일을 공유**하므로 갱신이 양쪽에 반영되어 사본 발산 자체가 없다. 이 문제만 놓고 보면 더 깨끗하다. 그러나 파이썬 SDK가 없어 스트리밍 파싱·timeout·retry·프로세스 수명 관리를 직접 구현해야 하고, 그것이 LLM 호출 설계의 본체다. 인증 편의 하나와 교환하기에는 손실이 크다. 기각하되, 컨테이너 안에서 CLI가 끝내 동작하지 않는 것으로 판명되면 재검토 대상 1순위로 남긴다.

**감수하는 것** — macOS에서는 Keychain을 공유할 수 없으므로 컨테이너가 가진 것은 사본이다. 컨테이너가 갱신하면 그 결과는 호스트 Keychain으로 돌아가지 않는다. 역방향 동기화까지 스크립트로 짤 수는 있으나 호스트의 인증 저장소를 직접 쓰는 행위라 호스트 CLI를 망가뜨릴 위험이 더 크다. 하지 않는다.

### 6. 오류 응답은 단순 봉투 하나로 통일한다

모든 오류가 `{"error": {"code": ..., "message": ...}}` 형태를 갖는다. 도메인 예외 기반 클래스를 `core/`에 두고, API 계층의 핸들러가 그것을 상태 코드와 봉투로 변환한다. 처리되지 않은 예외는 최종 핸들러가 받아 내부 정보를 지운 500으로 만들고, 원인은 로그에만 남긴다. 프레임워크가 기본 제공하는 오류 응답(경로 없음, 메서드 불허, 요청 검증 실패)도 이 봉투로 덮어써야 한다 — 기본 응답을 그대로 두면 형식이 두 가지가 된다.

**적용 대상에서 빠지는 것은 헬스 엔드포인트뿐이다**(결정 4). 상태 보고와 오류 통지는 다른 일이다.

**대안 — RFC 9457 Problem Details**: 표준이라는 장점이 있으나, 이 API의 소비자는 평가자와 자체 테스트뿐이고 `type` URI 같은 필드가 실제로 쓰일 곳이 없다. 규격을 절반만 지킨 Problem Details는 자체 봉투보다 나을 게 없다. 기각.

`code`는 문자열 열거값으로 둔다. 이후 change가 여기에 항목을 추가하는 식으로 확장한다 — 이것도 지금 남기는 계약 중 하나다.

### 7. 헬스 테스트는 프로브를 대역으로 바꿔 상태를 만든다

specs가 요구하는 시나리오는 정상·캐시 불능·벡터 스토어 불능·무응답 네 가지다. 실제 컨테이너를 죽여가며 이 상태를 만들면 테스트가 느리고 불안정해진다. `HealthProbe`가 프로토콜이므로 대역 구현을 주입해 네 상태를 결정론적으로 만든다 — 결정 2의 프로토콜 경계가 여기서 값을 낸다.

실물 의존성과의 통합 확인은 compose로 띄운 상태에서 사람이 1회 수행한다. 자동화 스위트는 외부 서비스 없이 돌아야 한다.

픽스처는 두 가지를 제공한다: 앱 테스트 클라이언트, 그리고 격리된 임시 데이터 디렉터리. 후자는 지금은 벡터 스토어 프로브만 쓰지만 ingestion change부터 본격적으로 쓰인다.

### 8. 설정은 환경변수 단일 소스

접속 정보와 데이터 경로를 환경변수로 받아 설정 객체 하나로 검증한다. compose가 값을 주입하고, 로컬 실행은 기본값으로 돈다. 설정 객체를 거치지 않은 `os.environ` 직접 조회는 두지 않는다 — 어디서 무엇을 읽는지 흩어지면 문서화가 불가능해진다.

## Risks / Trade-offs

**컨테이너 안에서 LLM CLI가 동작하지 않을 수 있다** → 이 프로젝트에서 가장 큰 미검증 가정이다. 결정 5로 설치 경로와 인증 주입 경로를 미리 뚫어두되, 실제 검증은 QA change의 **첫 번째** 태스크로 배치한다. 만약 컨테이너 안에서 불가능한 것으로 드러나면 대안은 호스트 실행 모드를 문서화된 실행 경로로 두는 것이며, 그때 `README.md`·`ARCHITECTURE.md`를 함께 고친다.

**마운트한 자격증명 파일을 컨테이너 안의 CLI가 실제로 읽는지 미검증** → 포맷이 동일하다는 것까지만 확인했고, CLI가 그 경로에서 읽어 동작하는지는 호출해 봐야 안다. 위 스파이크에서 함께 확인한다.

**refresh token 회전 시 한쪽이 무효화될 수 있다** → 컨테이너가 가진 것은 사본이다(결정 5-1). 갱신 시 refresh token이 회전하는 방식이면 호스트 Keychain의 값이 무효가 되어 호스트 CLI가 로그아웃될 수 있다. 회전 여부는 미검증. 완화책은 두 가지다. 하나, access token 수명이 약 8시간이라 한 번의 실행 세션 안에서는 갱신이 일어나지 않을 가능성이 높다. 둘, 기동할 때마다 재추출하므로 사본이 묵는 창이 짧다. 그래도 발생하면 호스트에서 다시 로그인해야 하며, 이 사실을 `README.md`에 경고로 남긴다.

**임베디드 벡터 스토어 + 다중 워커 = 파일 락 충돌** → 워커 1개로 고정하고 그 이유를 설정에 주석으로 남긴다. 성능이 문제가 되는 규모가 아니다.

**503 헬스체크와 compose 의존성 순서가 얽혀 재시작 루프** → 기동 유예를 충분히 주고, 캐시 컨테이너에 자체 헬스체크를 걸어 API가 그 뒤에 뜨게 한다.

**골격만 있고 기능이 없는 커밋** → 평가 관점에서 첫 change가 도메인 기능을 하나도 내놓지 못한다. 다만 이후 모든 change가 여기서 정한 경계를 재사용하므로 총 비용은 줄어들고, 무엇보다 "실행 불가"라는 불합격 경로를 첫날에 닫는다. 감수한다.

**지금 정한 계약이 이후 change에서 어색해질 수 있다** → 프로토콜을 좁게 정의한 것(결정 2)이 이 위험의 완화책이다. 그래도 어긋나면 해당 change에서 고치고 이유를 남긴다.

## Open Questions

- 벡터 스토어 프로브의 쓰기 가능 확인을 어느 정도까지 할 것인가. 디렉터리 접근성 확인으로 충분한지, 실제 소규모 쓰기까지 해야 하는지는 구현하며 정한다. 어느 쪽이든 specs의 시나리오와 태스크 분해는 바뀌지 않는다.
- 로그 형식을 JSON으로 고정할지 개발 환경에서만 사람이 읽는 형식을 쓸지. 관측성 백엔드 연동이 Non-Goal이라 지금 정하지 않아도 무방하다.
