## Context

동기와 범위는 `proposal.md` 를 본다. 여기서는 **지금 코드가 어떤 모양이라서 이 설계가 이렇게 나왔는지**만 적는다.

지금 `RetrievalService.search` 는 다섯 단계다 — 질의 임베딩 → 대상 집합 계산 → 저장소 질의 → 현재성 재검증 → 하한 필터. 이 중 **가운데 하나(저장소 질의)만** retriever다. 나머지 넷은 retriever가 몇 개든 요청당 한 번씩만 일어나야 하는 일이다. 팬아웃은 그 가운데 자리에만 들어간다.

제약 셋이 설계를 좁힌다.

- **컨테이너를 늘릴 수 없다.** 평가자가 `docker compose up` 한 줄로 띄운다. 이미 API·Chroma·Redis 셋이고, 어휘 검색 하나를 위해 검색 엔진 컨테이너를 더하면 기동 시간과 메모리가 과제의 실행 가능성을 위협한다(불합격 기준 1번).
- **Redis 는 아직 클라이언트가 없다.** 헬스 프로브(`adapters/cache/probe.py`)까지만 쓴다. LLM 응답 캐시 change 가 Redis 클라이언트의 주인이 되어야 하며, 이 change 가 먼저 만들면 소유권이 갈린다.
- **`score` 를 읽는 하위 계층이 사실상 없다.** `grep` 결과 `api/queries.py` 의 응답 뷰 한 곳뿐이고, `core/prompting.py` 도 `services/qa.py` 도 점수를 보지 않는다. 점수 의미 변경의 파급이 API 표면 한 줄에 갇혀 있다 — 이 사실이 "하한을 융합 앞으로 옮긴다"는 결정을 감당 가능하게 만든다.

## Goals / Non-Goals

**Goals**

- 팬아웃·융합을 **기존 다섯 단계의 순서를 바꾸지 않고** 가운데 한 자리에 끼워 넣는다. 대상 집합 계산과 현재성 재검증은 지금 코드 그대로 남는다.
- 융합 계층이 retriever의 존재를 모르게 한다 — 입력은 `(이름, 가중치, 항목 목록)` 뿐이고, `core/fusion.py` 는 표준 라이브러리만 쓴다.
- retriever를 하나만 켠 구성이 **지금과 완전히 같은 순서**를 내게 한다. 회귀 여부를 판정할 수 있는 기준선이 없으면 "좋아졌다"고 말할 수 없다.
- 어휘 색인의 수명을 벡터와 **같은 코드 경로**에 얹는다. 두 색인을 따로 관리하는 순간 어긋남은 시간 문제다.

**Non-Goals**

- 형태소 분석. `konlpy`·`mecab` 계열은 JVM 또는 C 확장과 사전 데이터를 요구해 이미지가 수백 MB 늘고 빌드가 플랫폼을 탄다.
- 재순위(cross-encoder). 융합 뒤 상위 K를 다시 채점하는 단계는 LLM/모델 호출을 하나 더 만든다 — 이 change 가 감당할 범위가 아니고, 융합의 효과를 측정하기 전에 얹으면 둘 중 무엇이 기여했는지 알 수 없다.
- 가중치·하한의 자동 튜닝. 값은 손으로 정하고 근거를 `ARCHITECTURE.md` 에 적는다.
- 분산 캐시. 아래 결정 7 참조.

## Decisions

### 1. 어휘 색인 저장소는 SQLite FTS5 — 파일 하나, 컨테이너 0개

FTS5 는 파이썬 표준 `sqlite3` 에 컴파일되어 들어 있고 `bm25()` 순위 함수를 내장한다. 저장소는 `./data/lexical.sqlite3` 파일 하나이며, 이미 레지스트리(`./data/registry.sqlite3`)가 같은 방식으로 붙어 있어 볼륨·백업·삭제 절차가 늘지 않는다.

| 대안 | 왜 아닌가 |
|------|-----------|
| Chroma 의 `where_document` | `$contains` 부분 문자열 필터일 뿐 순위가 없다. 어휘 **검색**이 아니라 어휘 **필터**다 |
| Elasticsearch / OpenSearch | 컨테이너 + JVM 힙. 이 규모(샘플 문서 2건)에 대한 과잉이고 기동 시간이 평가 절차를 위협한다 |
| `rank_bm25` 인메모리 | 영속성이 없어 기동마다 전 청크 본문을 Chroma 에서 끌어와 재구축해야 한다. 워커마다 사본이 생기고 메모리가 코퍼스 크기에 비례한다 |
| 레지스트리와 **같은** SQLite 파일 | 한 트랜잭션으로 묶을 수 있을 것 같지만 착시다 — 벡터 쓰기는 다른 프로세스라 어차피 원자성이 성립하지 않는다. 얻는 것 없이 레지스트리 파일에 검색용 테이블이 섞인다 |

**`bm25()` 의 부호는 어댑터가 뒤집는다.** FTS5 의 `bm25()` 는 관련도가 높을수록 더 작은 **음수**를 돌려준다(내부 BM25 값에 -1 을 곱한 값). 정렬은 `ORDER BY bm25(...) ASC`, 노출 점수는 `-bm25(...)` 다 — `lexical-index` 가 요구하는 "점수 `0` 이상, 내림차순"은 이 변환 **뒤에** 성립한다. 원값을 그대로 실으면 스펙 위반이고, 원값에 `DESC` 를 걸면 가장 안 맞는 청크가 1 위가 된다. 오류가 나지 않고 순위만 뒤집히는 종류라 테스트로만 잡힌다. 뒤집은 값이 음수가 되지 않는 것은 fts5 가 `idf <= 0` 을 `1e-6` 으로 눌러 두기 때문이며, 이 사실은 태스크에서 실측으로 확인한다.

FTS5 를 **외부 콘텐츠 없는 독립 테이블**로 만들고, 삼중항·`chunk_index` 는 색인되지 않는 일반 컬럼(`UNINDEXED`)으로 둔다. 대상 집합 필터는 `WHERE` 절의 `(document_id, revision, index_signature)` 튜플 IN 조건이다. 동기 API 라 `asyncio.to_thread` 로 내보낸다 — Chroma 어댑터와 같은 규약이다.

### 2. 토큰화는 우리가 한다 — 원 토큰과 어근을 **둘 다** 색인한다

FTS5 기본 토크나이저(`unicode61`)는 공백·기호로만 자른다. 한국어에서 이것은 어절 단위 색인을 뜻하고, `"교육비는"` 으로 물으면 `"교육비"` 를 담은 청크에 닿지 않는다. 오류 없이 그냥 안 찾는다.

**결정: 쓰기와 읽기 양쪽에서 같은 순수 파이썬 토크나이저를 돌려 공백으로 이어 붙인 토큰 문자열을 FTS5 에 넣고, 질의도 같은 토큰들의 `OR` 로 만든다.** 규칙은 넷이다.

1. **정규화** — NFKC 후 소문자화. 전각·반각과 대소문자 차이가 여기서 사라진다.
2. **경계 분할** — 한글 / 라틴·숫자 / 그 외의 경계에서 자른다. 단 라틴·숫자 연속(`P1`, `v2`)은 쪼개지 않는다.
3. **혼합 토큰 보존** — `200만원` 처럼 숫자와 한글이 붙은 토큰은 **원형(`200만원`)과 조각(`200`, `만원`)을 모두** 색인한다. 원형만 넣으면 `"200만원"` 으로만 찾히고, 조각만 넣으면 `200` 의 변별력이 사라진다.
4. **접미 벗기기** — 한글 토큰에서 조사·어미 목록(`는·은·이·가·을·를·에·에서·으로·로·와·과·의·도·만·까지·부터·보다·입니다·합니다·하는·한다` …)을 최장 일치로 한 번 벗겨, **원 토큰과 어근 토큰을 함께** 색인한다. 남는 어근이 2글자 미만이면 벗기지 않는다.

원형과 어근을 둘 다 넣는 것이 요점이다. 어근만 넣으면 벗기기가 과하게 동작한 경우(`"수도"` → `"수"`)에 원문이 사라지고, 원형만 넣으면 조사 붙은 질의가 닿지 않는다. 둘 다 있으면 **잘못 벗겨도 원형이 살아 있어 최악이 "재현율이 조금 는다"** 로 끝난다.

`TOKENIZER_VERSION` 상수를 두고 `derive_index_signature` 의 재료에 넣는다. 규칙을 고치면 서명이 달라지고 기존 문서는 `stale` 이 되어 재업로드를 요구한다 — 이미 있는 기동 정리 경로가 그대로 처리한다.

**대안: FTS5 `trigram` 토크나이저.** 한국어 부분 일치는 잘 되지만 3글자 미만 질의어를 아예 검색할 수 없고(`P1` 이 검색 불가), `bm25()` 의 문서 빈도가 3-gram 단위가 되어 "드문 어휘"라는 개념이 우리가 쓰려는 뜻과 어긋난다. 어휘 검색을 넣는 첫 번째 이유가 짧은 식별자라서 탈락.

### 3. 관련성 판정은 융합 **앞**에, 각자의 단위로 — 어휘 쪽은 드문 토큰 겹침

`retrieval` 스펙이 하한의 적용 지점을 옮긴 이유는 스펙의 근거 블록에 있다. 여기서는 **어휘 쪽 하한을 무엇으로 재는가**만 정한다.

BM25 원점수에 하한을 걸 수 없다 — 값이 코퍼스 크기와 질의 길이에 따라 몇 배씩 움직여서 고정 임계값이 의미를 갖지 않는다. 대신 **토큰 하나하나의 희소도**를 재고, 스펙이 적은 그대로 "충분히 드문 토큰이 하나라도 겹치는가"를 묻는다.

    idf(t)    = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))       # BM25 표준, df=0 에서도 유한
    rarity(t) = idf(t) / idf(df=0)                              # 같은 코퍼스의 최대 IDF 로 정규화, (0, 1]
    통과 조건  = max{ rarity(t) : t 가 이 청크에 있는 질의 토큰 } >= 하한(기본 0.3)

정규화가 하한을 코퍼스 크기에서 뗀다 — `idf` 원값은 `N` 이 커지면 같은 비율의 `df` 에서도 함께 커져 고정 임계값이 뜻을 잃는다. `df` 는 FTS5 의 `fts5vocab` 가상 테이블에서 읽고, 질의당 토큰 수만큼만 조회한다.

**처음에는 커버리지 비율**(매칭된 토큰의 IDF 합 / 전체 질의 토큰의 IDF 합)**로 적었고, 구현 중 실측에서 두 군데가 깨져 위 규칙으로 바꿨다.**

- **비율은 토큰 하나짜리 질의를 원리적으로 걸러내지 못한다.** 분자와 분모가 같아 항상 `1.0` 이다. `"승인"` 하나로 물으면 그 토큰이 아무리 흔해도 통과하므로, 스펙의 「흔한 토큰만 겹치는 청크는 오르지 않는다」가 성립하지 않는다.
- **없는 토큰이 분모를 부풀려 정상 질의를 죽인다.** 결정 2 의 토크나이저는 원형과 어근을 **둘 다** 내므로 질의 하나가 토큰 여럿이 되고, 그중 색인에 없는 것(`교육비는`·`얼마인가요` 같은 표층형·의문사)이 `df=0` 이라 최대 IDF 를 받는다. `sample-docs/` 두 건(200자 청킹, `N=10`)에서 `"교육비는 얼마인가요"` 의 커버리지가 **0.244** 로 하한 `0.3` 에 못 미쳐, 스펙의 「조사가 붙은 질의어가 어근을 찾는다」가 빈 목록이 됐다.

바꾼 규칙으로 같은 코퍼스를 다시 재면 네 회귀 질의와 `"교육비는 얼마인가요"` 가 모두 통과하고 두 무관 질의는 빈 목록이다. 하한 `0.3` 은 `N=10` 에서 `df >= 4`(청크의 40%)를 "흔하다"로 판정하는 지점이고, `0.4` 로 올리면 `승인`·`pr`(`df=3`)이 잘려 코드리뷰 회귀 질의가 빈 목록이 된다. 실측표는 `ARCHITECTURE.md` 「어휘 색인」에 있다.

- `"오늘 서울 날씨 어때?"` — 네 토큰 모두 색인에 없어 `MATCH` 자체가 0 건이다 → 빈 목록.
- `"P1 장애가 나면 몇 분 안에"` — `P1`(`df=1`, 희소도 `0.645`)이 하한을 넘어 그 토큰을 담은 청크가 통과한다.

### 4. RRF 상수는 60, 정규화는 이론 최댓값으로 나눈다

`RRF_K=60` 은 RRF 원 논문(Cormack et al., 2009)이 실험적으로 고른 값이고 업계 관례다. 우리 코퍼스로 다시 재려면 정답 라벨이 필요한데 그 라벨이 없다 — 근거 없이 다른 값을 쓰는 것보다 관례값을 쓰고 그 사실을 적는 편이 정직하다.

**상수의 이름을 `RRF_K` 로 못 박는다.** 이 change 에는 `K` 로 불릴 뻔한 값이 셋이다 — RRF 상수(60), 응답의 `top_k`, 그리고 retriever가 길어 오는 후보 깊이. 아래 수식과 스펙에서 `K` 는 **오직 `top_k`** 를 뜻하고, 융합 상수는 `RRF_K`, 목록 길이는 `candidate_depth` 다. 융합 함수가 받는 절단 개수도 `top_k` 자리의 값이지만, 서비스는 캐시에 담을 목록을 만들 때 절단하지 않고 부른 뒤 응답 직전에 자른다(결정 7).

    raw(d)  = Σ_r  w_r / (RRF_K + rank_r(d))    # r 은 이름표 정렬 순서
    max     = Σ_r  w_r / (RRF_K + 1)            # 같은 항 형태, 같은 순서
    score(d) = raw(d) / max                     # (0, 1]

`max` 를 `(Σ w_r) / (RRF_K + 1)` 로 접지 않는다. 두 식은 실수에서는 같지만 부동소수점에서는 다르고(가중치 `1.0`·`2.0` 에서 `fl(1/61)+fl(2/61) ≠ fl(3/61)`), 그 차이가 만장일치 1위를 `0.9999999999999999` 로 만든다. 누적 순서를 이름표 정렬로 고정하는 것도 같은 이유다 — 전달 순서로 더하면 순서가 마지막 비트를 바꿔 스펙의 "전달 순서 무관"이 깨진다.

양의 상수로 나누므로 순서는 보존된다. `max` 는 **융합에 전달된 입력 목록 전체**의 가중치로 계산한다 — 빈 목록도 포함이고, 전달되지 않은 목록은 제외다.

경계가 하나 있다. 어휘 retriever가 하한에서 전부 걸러 **빈 목록**을 내면 그 가중치는 분모에 남고(한쪽만 찾은 청크는 `0.5`), 선택 retriever가 **실패해 목록에서 빠지면**(결정 6) 분모에서도 빠져 살아남은 retriever 기준으로 척도가 다시 잡힌다. 앞은 "못 찾았다"는 판정이고 뒤는 판정 자체가 없는 상태라, 어휘 색인이 죽어 있는 동안 점수가 통째로 절반이 되는 일은 생기지 않는다. 실제로 기여한 retriever만으로 나누는 셋째 선택지는 쓰지 않는다 — 그러면 한쪽만 찾은 청크가 `1.0` 을 받아 "모두가 1위로 꼽았다"는 척도의 의미가 무너진다.

타이브레이크는 `(-score, document_id, chunk_index)` 다. 한 대상 집합 안에서 문서마다 삼중항이 하나뿐이므로 `(document_id, chunk_index)` 는 후보를 유일하게 식별한다 — 전순서가 성립한다.

### 5. retriever 구성은 JSON 설정 항목 + 이름→팩토리 등록부

    APP_RETRIEVERS='[{"name":"dense","weight":1.0,"candidate_depth":30,"required":true},
                     {"name":"lexical","weight":1.0,"candidate_depth":30,"required":false}]'

pydantic-settings 가 환경변수의 JSON 을 모델 목록으로 파싱한다. 배선(`main.py`)은 이름을 `adapters/retrievers/registry.py` 의 팩토리 표에서 찾아 인스턴스를 만들고, 없는 이름이면 `ConfigurationError` 로 기동을 세운다.

**후보 깊이는 retriever마다 따로 두고, 기동에서 `top_k` 상한과 비교한다.** 깊이가 상한보다 작으면 `ConfigurationError` 다 — 기본값이 아니라 상한과 비교하는 이유는 `retrieval` 스펙의 근거 블록에 적었다. 깊이를 retriever별로 두는 것은 두 retriever의 후보 분포가 다르기 때문이고(어휘 쪽은 하한에서 대부분 잘려 나간다), 그래서 캐시 키에도 단일 값이 아니라 `(이름, 깊이)` 쌍 전체가 들어간다.

**"코드 변경 없이 config 로 확장"의 정직한 범위**를 여기 적어 둔다. 이미 등록된 retriever의 **조합·가중치·후보 깊이·필수 여부**는 설정만으로 바뀐다. 진짜 새 알고리즘을 더할 때 손대는 곳은 **어댑터 모듈 하나와 등록부 한 줄**이며, `core/fusion.py`·`services/retrieval.py`·`api/` 와 이 change 의 스펙은 그대로다. "어떤 코드도 안 바뀐다"는 플러그인 로딩(엔트리포인트·동적 import)으로만 가능한데, 그것은 등록되지 않은 이름이 런타임에 나타날 수 있다는 뜻이라 **기동 시 검증**을 포기하는 것과 같다. 설정 오타가 기동을 세우는 쪽이 이 과제에서 더 값지다.

`Retriever` 프로토콜은 한 메서드다.

    async def retrieve(query: str, *, depth: int,
                       versions: Sequence[StoredIndexVersion]) -> list[RetrievedChunk]

`RetrievedChunk` 는 `ScoredChunk` 의 필드에 `native_score` 를 더한 값 객체다 — 척도가 다른 점수를 `score` 자리에 담으면 `[0,1]` 불변식이 깨진다.

### 6. 팬아웃은 `asyncio.gather(return_exceptions=True)`, 실패 분류는 서비스가

밀집 retriever는 임베딩 계산(스레드풀) + Chroma 왕복, 어휘 retriever는 SQLite 왕복이다. 둘 다 이미 블로킹을 스레드로 내보내고 있어 `gather` 로 겹치면 지연이 **합이 아니라 최댓값**에 가까워진다 — 이것이 팬아웃이 응답 시간을 크게 해치지 않는 이유다.

`return_exceptions=True` 로 받아 서비스가 분류한다. 필수 retriever의 예외는 그대로 올려 `503` 이 되고, 선택 retriever의 예외는 `logger.warning` 후 목록에서 제외한다. 전부 실패면 `StorageUnavailable` 을 다시 던진다.

### 7. 검색 결과 캐시는 프로세스 안의 LRU — Redis 가 아니다

키는 `sha256(query ‖ fingerprint ‖ search_signature ‖ candidate_depths)` 이고, `fingerprint` 는 정렬된 삼중항 전체의 해시, `candidate_depths` 는 이름순으로 정렬한 `(retriever 이름, 깊이)` 쌍 전체다. **저장하는 값은 상위 K 로 자르기 전의 융합 목록**이라 `top_k` 가 키에 들어가지 않는다 — `top_k=3` 요청이 채운 항목을 `top_k=5` 요청이 재사용한다.

Redis 가 아닌 이유가 셋이다. (1) Redis 클라이언트의 주인은 LLM 응답 캐시 change 여야 한다 — 두 change 가 같은 어댑터를 각자 만들면 나중 것이 앞의 것을 뜯는다. (2) 이 캐시는 **정확성이 아니라 지연**만 다룬다. 워커가 여럿이면 히트율이 떨어질 뿐 결과는 같다(같은 키는 같은 값을 만든다). (3) 캐시가 없어도 검색은 완전히 동작해야 하고, 그 사실은 `retrieval` 스펙의 "캐시를 꺼도 결과가 같다" 시나리오가 강제한다.

**캐시는 융합 결과만 담는다.** 현재성 재검증(`_drop_superseded`)과 상위 K 절단은 적중·미적중과 무관하게 매 요청 실행된다. 캐시가 스펙의 보증을 우회하지 못하게 만드는 유일한 방법이 이 순서다.

관련성 하한은 여기서 다시 걸지 **않는다.** 하한은 retriever가 융합 **앞**에서 자기 단위로 거는 것이고(`retrieval`), 캐시된 목록은 이미 그것을 통과한 결과다. 융합 뒤에 다시 거는 것은 그 스펙이 금지한 바로 그 동작이며, 하한값이 `search_signature` 에 들어 있어 값을 바꾸면 키가 달라지므로 재적용할 이유도 없다.

무효화 코드는 없다. 문서가 바뀌면 `fingerprint` 가 달라져 키가 달라지고, 옛 항목은 조회되지 않다가 LRU 상한에 밀려 사라진다.

### 8. 하나의 서명이 두 색인을 함께 지배한다

토큰화 구성을 별도 서명으로 두지 않고 `index_signature` 에 합치는 근거는 `document-ingestion` 델타의 요구사항 블록에 적었다 — 요약하면 검색 가능성이 두 축으로 쪼개지는 것을 막기 위해서다. 대가는 임베딩 모델을 바꿀 때 어휘 색인도 함께 다시 만들어야 한다는 것이고, 그 비용은 재업로드 한 번이다.

수집 순서는 지금 그대로 두고 어휘 색인을 **벡터 쓰기 바로 뒤, 레지스트리 커밋 앞**에 끼운다.

    새 벡터 쓰기 → 새 어휘 색인 쓰기 → 레지스트리 커밋 → 이전 세대 정리(양쪽)
                 ↑ 여기까지 어느 단계가 실패하든 되돌리기는 양쪽 모두를 지운다

되돌리기가 닿지 못한 실패가 남긴 잔여물은 기동 정리가 처리한다 — 이미 벡터 쪽에 있는 그 경로에 어휘 색인 인자를 하나 더 넘긴다.

## Risks / Trade-offs

**[접미 벗기기가 형태소 분석이 아니다]** → 규칙 기반이라 `"수도권"` 을 `"수도"` 로 잘못 벗기는 사례가 나온다. **원 토큰을 함께 색인**하므로 결과는 "없는 매칭이 는다"(정밀도 하락)이지 "있는 매칭이 사라진다"(재현율 하락)가 아니다. 그리고 희소도 하한이 잘못 벗긴 흔한 토큰만으로는 청크가 오르지 못하게 막는다. 정밀도 손실은 융합이 흡수한다 — 어휘 목록에서만 상위인 청크는 밀집 목록의 지지를 못 받아 융합 상위로 오르기 어렵다.

**[FTS5 가 없는 파이썬 빌드]** → 대부분의 배포판은 켜져 있지만 보장은 아니다. 기동 시 `SELECT sqlite_compileoption_used('ENABLE_FTS5')` 로 확인하고, 없으면 **기동을 세우지 않고** 어휘 retriever를 실패 상태로 둔다(선택 retriever라 밀집만으로 계속 동작한다). 이 상태는 응답의 기여 목록에서 즉시 드러난다. Dockerfile 의 베이스 이미지에서 실제로 켜져 있는지는 태스크에서 확인한다.

**[융합이 기존 품질을 떨어뜨린다]** → 어휘 목록이 엉뚱한 청크를 1위로 올리면 융합이 그것을 상위로 끌어올려, 지금 맞히던 네 질의를 틀릴 수 있다. `retrieval` 스펙이 그 네 시나리오를 **회귀 기준**으로 못 박았고, 실패하면 가중치를 조정하거나(설정) 어휘 retriever를 끈다(설정) — 둘 다 코드 변경이 아니다.

**[점수 의미 변경이 데모 UI 를 깨뜨린다]** → `demo-ui` 가 점수를 유사도로 표시하고 있으면 `0.016`… 이 아니라 `1.0` 근처의 값이 나와 오해를 부른다. 정규화가 그 오해의 폭을 줄이지만 근본 해결은 표기 변경이다 — 태스크에 UI 문구 수정과 `README.md` 갱신을 넣는다.

**[요청당 저장소 왕복이 는다]** → 밀집 1회 + 어휘 1회 + 레지스트리 재검증. 병렬이라 지연은 최댓값에 가깝고, 반복 질의는 캐시가 흡수한다. 최악은 캐시가 꺼지고 두 저장소가 모두 느린 경우이며, 그때도 헬스 응답이 막히지 않는다는 것은 `retrieval` 의 동시성 요구사항이 이미 강제한다.

**[캐시가 워커별로 따로 산다]** → 히트율이 워커 수만큼 나뉜다. 정확성 문제가 아니므로 감수하고, 필요해지면 같은 키 계산을 그대로 둔 채 저장소만 Redis 로 바꾼다 — 키 설계가 저장소에 의존하지 않게 만든 이유다.

## Migration Plan

기존 데이터에 대한 이주 절차가 필요하다. `TOKENIZER_VERSION` 이 `derive_index_signature` 에 들어가므로 **이 change 를 배포하면 기존에 수집된 모든 문서의 서명이 달라진다.**

1. 배포 후 첫 기동에서 기존 경로가 그대로 동작한다 — 기동 정리가 서명 불일치를 발견해 벡터를 지우고 `index_status: "stale"` 로 표시한다. 기동은 실패하지 않는다.
2. 사용자는 `stale` 문서를 다시 업로드해 복구한다(`reindexed`). 이 절차는 이미 스펙에 있고 테스트가 있다 — 새로 만드는 경로가 아니다.
3. `README.md` 에 "이 버전으로 올리면 기존 문서를 다시 올려야 한다"를 적는다.

롤백은 코드를 되돌리면 된다. 서명이 예전 값으로 돌아가고, 이 change 로 만들어진 청크가 이번엔 `stale` 이 된다 — 대칭이다. `./data/lexical.sqlite3` 는 남지만 아무도 읽지 않는다.

되돌리지 않고 **끄기만** 하려면 설정에서 어휘 retriever를 빼면 된다. 그때도 서명은 토큰화 구성을 포함한 값 그대로이므로 재색인은 일어나지 않는다.
