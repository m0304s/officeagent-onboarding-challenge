## Why

지금 검색은 **밀집 벡터 하나**다. 질의 임베딩과 청크 임베딩의 코사인 유사도만으로 순위가 정해지고, 하한(`0.82`)에 걸리지 않은 것만 나간다. 이 구조가 조용히 실패하는 자리가 둘 있다.

- **고유명사·식별자·숫자.** `"P1"`, `"200만원"`, `"main"` 처럼 의미가 아니라 **글자 그 자체**가 근거인 토큰은 의미 임베딩에서 주변 문맥에 녹아 사라진다. 문서에 그 문자열이 있는데도 검색이 못 찾는다 — 오류가 아니라 근거 0건이고, `answer-generation` 이 그것을 `no_evidence` 로 마감한다. 사용자에게는 문서에 있는 사실이 "없다"고 보인다.
- **단일 신호의 임계값 의존.** `0.82` 는 표본 8건으로 잰 값이다. 문서가 늘어 점수 분포가 이동하면 하한 하나가 검색 품질 전체의 단일 실패 지점이 된다. 신호가 하나뿐이면 그 신호를 신뢰할 수 없을 때 물러설 곳이 없다.

**PRD §2(Query & Answer)의 "관련 내용을 벡터 검색"을 이미 충족한 상태에서 그 위에 얹는 품질 개선**이다. 평가 비중이 가장 큰 항목이 RAG 파이프라인(23%)이고 그 안에 "검색 방식은 자유 선택, 선택 이유를 `ARCHITECTURE.md` 에 설명"이 있다 — 이 change 가 만드는 것은 기능이 아니라 **선택의 근거가 있는 검색 방식**이다.

## What Changes

검색 한 건이 retriever 하나를 부르는 대신, **N개의 retriever를 부르고 그 결과를 하나의 순위로 융합**한다. 융합은 RRF(Reciprocal Rank Fusion) — 각 retriever가 매긴 **순위**만 쓰고 점수 크기는 쓰지 않는다.

    질의
      ├─→ [기존] 밀집 벡터 retriever ──→ ranked list (코사인, 자체 하한 통과분)
      └─→ [신규] BM25 렉시컬 retriever ─→ ranked list (BM25, 자체 하한 통과분)
                                              ↓
                                     [신규] RRF 융합 (결정론적)
                                              ↓
                                    상위 K + retriever별 기여 내역

- **BM25 렉시컬 색인을 신설한다.** 청크 본문을 어휘 색인에 함께 넣고, 질의어와 글자가 겹치는 청크를 BM25로 순위 매긴다. 색인의 수명은 벡터와 **같은 삼중항**(`document_id`, `revision`, `index_signature`)에 매인다 — 수집이 벡터를 쓰는 자리에서 어휘 색인도 함께 쓰고, 되돌릴 때 함께 되돌리고, 기동 정리가 함께 지운다. 한쪽만 남으면 retriever마다 다른 세대를 보게 되고 융합 결과는 그 순간 의미를 잃는다.
- **RRF 융합 계층을 신설한다.** 입력은 "이름표가 붙은 ranked list N개", 출력은 "ranked list 1개". 융합 계층은 retriever가 몇 개인지도 무엇인지도 알지 않는다. **동점은 전순서 타이브레이크로 깬다** — RRF는 구조적으로 동점이 잦고, 동점 처리가 불안정하면 `retrieval` 이 요구하는 "같은 질의는 같은 결과" 가 깨져 캐시 전제까지 무너진다.
- **retriever 구성을 설정으로 연다.** 어떤 retriever를 쓸지, 가중치·후보 깊이·필수 여부를 설정이 정한다. **이미 등록된 retriever의 조합을 바꾸는 데는 코드 변경이 들지 않고**, 새 알고리즘을 더할 때 손대는 곳은 어댑터 한 모듈뿐이다 — 서비스·융합·API 는 그대로다.
- **점수의 의미가 바뀐다 (BREAKING).** 응답의 `score` 는 코사인 유사도가 아니라 **융합 점수**가 된다. 관련성 하한은 융합 뒤가 아니라 **각 retriever가 자기 점수 단위로 융합 전에** 건다 — 서로 단위가 다른 점수에 임계값 하나를 걸 수 없고, RRF 점수는 관련성의 크기가 아니라 순서만 담기 때문이다. 기존 `retrieval_min_score` 는 밀집 retriever의 자체 하한으로 자리를 옮긴다. 각 결과는 **어느 retriever가 몇 위로 올렸는지와 그때의 원래 점수**를 함께 싣는다 — 이것이 없으면 융합 뒤에는 왜 그 순위인지 아무도 설명할 수 없다.
- **검색 결과 캐시를 신설한다.** 융합은 요청당 retriever 호출을 N배로 늘린다. 융합된 후보 목록을 **대상 집합 지문**(현재 유효한 삼중항 전체)과 검색 구성 서명으로 키를 잡아 캐시한다. 문서가 추가·교체·삭제되면 지문이 달라져 **키가 바뀌므로, 무효화를 호출하는 코드가 없다.** 캐시 적중이어도 현재성 재검증과 하한 적용은 그대로 돈다 — 캐시가 `retrieval` 의 보증을 우회하지 않는다.

**범위 밖** — LLM 답변 캐시(Redis)는 이 change 가 만들지 않는다. 형태소 분석기·동의어 사전·재순위(cross-encoder) 도입, retriever별 하한의 자동 조정, SSE 이벤트 어휘 변경, `answer-generation` 의 인용 조립 규칙 변경도 밖이다.

## Capabilities

### New Capabilities

- `lexical-index`: 어휘 색인 하나의 수명. 청크 본문의 색인 등록·삭제, 벡터와 같은 삼중항에 매인 세대 관리, 토크나이저 구성이 바뀔 때의 처분, 색인에 닿지 못할 때의 실패 표현. **검색 순위를 정하지 않는다** — 여기가 정하는 것은 "무엇이 색인되어 있는가"까지다.
- `rank-fusion`: 이름표 붙은 ranked list N개를 하나로 합치는 계약. RRF 공식과 가중치, **동점 타이브레이크의 전순서성**, 입력 목록이 0개·1개일 때의 동작, 융합 결과가 담아야 할 retriever별 기여 내역. retriever가 무엇인지도, 설정이 무엇을 정했는지도 알지 않는다 — 후보 깊이의 설정과 기동 검증은 `retrieval` 의 몫이다.

### Modified Capabilities

- `retrieval`: 검색이 retriever 하나가 아니라 **설정이 정한 retriever 집합의 융합 결과**가 된다. 점수의 의미(유사도 → 융합 점수), 관련성 하한의 적용 지점(융합 후 → retriever별 융합 전), 결과에 실리는 기여 내역, retriever 하나가 실패했을 때의 처분(필수/선택), retriever별 후보 깊이와 상위 K 상한의 관계에 대한 기동 검증, 그리고 결과 캐시의 적중·무효화 동작이 요구사항으로 들어온다. 대상 집합 규칙("지금 유효한 청크뿐")·질의 유효성·출처 구조·동시성 요구사항은 **그대로**이며, 모든 retriever가 **하나의 같은 대상 집합**을 공유한다는 것이 새로 명시된다.
- `document-ingestion`: 수집이 벡터와 어휘 색인 **둘 다** 쓰고, 되돌리기와 이전 세대 정리가 둘 다에 미친다. 색인 서명의 재료에 어휘 토크나이저 구성이 더해진다 — 토크나이저가 바뀌면 기존 색인은 `stale` 이 된다.

## Impact

**신규 코드**

| 경로 | 내용 |
|------|------|
| `core/fusion.py` | RRF 계산과 타이브레이크 (순수 함수, 표준 라이브러리만) |
| `core/lexical.py` | 토크나이저와 어휘 색인 값 객체 |
| `adapters/lexical/` | 어휘 색인 어댑터 — `protocols.py` 의 프로토콜 뒤에 둔다 |
| `adapters/retrievers/` | retriever 어댑터와 이름 → 구현 등록부. 밀집·BM25 둘 다 여기로 들어온다 |
| `adapters/cache/retrieval.py` | 검색 결과 캐시 |

**변경되는 코드**

| 경로 | 변경 |
|------|------|
| `services/retrieval.py` | 단일 호출 → retriever 팬아웃 · 융합 · 캐시. 대상 집합 계산과 현재성 재검증은 그대로 |
| `services/ingestion.py` | 쓰기·되돌리기·정리에 어휘 색인 경로 추가 |
| `core/retrieval.py` | `ScoredChunk` 에 retriever별 기여 내역. `score` 의 의미가 바뀐다 |
| `core/documents.py` | `derive_index_signature` 에 토크나이저 재료 추가 |
| `adapters/protocols.py` | `Retriever`·`LexicalIndex` 프로토콜 |
| `config.py` | retriever 구성(목록·가중치·후보 깊이·필수 여부), RRF 상수, 캐시 크기 |
| `api/queries.py`·`api/routes/search.py` | 결과 뷰에 기여 내역 |

**손대지 않는 코드** — `api/sse.py`, `core/prompting.py`, `adapters/llm/`, `services/qa.py`. 검색 결과가 `ScoredChunk` 목록이라는 사실이 그대로라 생성·스트리밍 계약이 흔들리지 않는다.

**문서** — `ARCHITECTURE.md` 에 하이브리드 검색 파이프라인·RRF 선택 근거·어휘 색인 저장소 선택 근거·점수 의미 변경 이력, `README.md` 에 retriever 설정 방법. `PROMPT_DESIGN.md` 는 바뀌지 않는다.

**테스트** — PRD §5 의 핵심 3경로 중 **ingestion·retrieval 두 경로를 직접 건드린다.** 어휘 색인이 수집 트랜잭션에 들어가므로 수집 실패·되돌리기 테스트가 늘고, 검색은 융합 결정성·타이브레이크·retriever 실패·캐시 무효화가 새 검증 대상이다. 기존 검색 품질 시나리오(`sample-docs/` 4문항)는 **회귀 기준으로 그대로 남는다** — 하이브리드가 기존에 맞히던 것을 틀리면 그 자리에서 드러나야 한다.

**앞으로 지어질 것에 미치는 영향** — LLM 답변 캐시는 **검색 구성 서명을 키에 넣어야 한다.** 가중치나 retriever 목록을 바꾸면 같은 질문이 다른 근거를 받는데, 키가 질문만 보면 예전 근거로 만든 답변이 그대로 나간다. `add-multiturn-qa` 가 "캐시 키는 재작성된 질의 기준" 을 못 박은 것과 같은 자리에 하나를 더 박는다.
