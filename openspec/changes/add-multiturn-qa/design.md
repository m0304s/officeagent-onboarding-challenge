## Context

동기는 `proposal.md` — Why 에, 요구사항은 `specs/` 세 파일에 있다. 여기서는 그 요구사항을 지금 코드 위에 어떻게 얹는지만 적는다.

지금 상태에서 이 설계를 좌우하는 사실 넷:

- **`/qa` 는 `prepare` 와 `stream` 으로 갈려 있다.** 상태 코드는 첫 바이트와 함께 확정되므로 검증·검색은 스트림 밖(`prepare`)에서 끝나고, 그 뒤의 실패만 스트림 안의 `error` 로 나간다. 새 단계는 이 경계 중 어느 쪽에 놓이는지를 각각 정해야 한다.
- **Redis 는 아직 헬스 프로브까지만 쓰인다.** `adapters/cache/probe.py` 가 TCP 도달성만 확인하고, 실제 클라이언트는 없다. `APP_CACHE_URL` 설정 항목과 compose 서비스는 이미 있다.
- **인용 범위 제한은 이미 코드에 있다.** `core/prompting.py` 의 `_validate_markers(body, source_count)` 가 `1..source_count` 밖의 마커를 버리고 개수를 센다. 히스토리를 프롬프트에 넣어도 이번 `sources` 밖을 가리키는 인용은 여기서 걸린다 — 새로 만들 장치가 아니라 이미 있는 장치가 요구사항을 떠받친다.
- **생성 하나가 프로세스 하나다.** Codex CLI 를 `app-server` 로 띄워 stdio JSON-RPC 로 대화하며, `QaService` 가 `anyio.CapacityLimiter(concurrency)` 로 동시 생성 수를 묶는다. 재작성은 생성 호출을 하나 더 만드는 일이라 이 예산을 건드린다.

## Goals / Non-Goals

**Goals**

- 후속 질문의 검색이 성립하게 한다 — 지금은 조용히 `no_evidence` 로 끝난다.
- `services/retrieval.py`·`adapters/embedding/`·`adapters/vector_store/`·`api/sse.py` 를 **한 줄도 고치지 않는다.** 이 넷이 그대로인 것이 "파이프라인 계약 불변"의 검증 가능한 형태다.
- 세션 계층 전체가 없어도 단일 턴 질의응답이 지금과 똑같이 동작하게 한다.

**Non-Goals (설계 수준)**

- 재작성 품질의 정량 평가 지표. 이번에는 `specs/query-rewriting/spec.md` 의 시나리오가 합격선이다.
- 대화 히스토리를 이용한 **답변** 품질 향상. 히스토리는 지시어 해소를 위한 재료이고, 답변은 여전히 이번 검색 결과만으로 만든다.
- LLM 응답 캐싱. 이 change 는 캐시를 만들지 않는다 — 다만 캐시가 나중에 지켜야 할 제약 하나를 아래 결정 6 에 못 박는다.

## Decisions

### 1. 세션 저장소는 Redis, 자료구조는 LIST + EXPIRE

**대안**

| 후보 | 기각 사유 |
|------|-----------|
| SQLite (`adapters/registry/sqlite.py` 재사용) | TTL 이 없다. 만료를 청소 작업으로 직접 돌려야 하는데, 그 작업이 실패하면 세션이 영영 남는다 — `conversation-session` 의 만료 요구사항이 배경 작업의 건강에 매달린다 |
| 프로세스 메모리 | 워커가 둘이면 같은 세션이 워커마다 다른 히스토리를 본다. 재기동마다 전부 사라진다 |

**Redis 를 고르는 이유** — TTL 이 자료구조 자체의 기능이라 만료가 코드가 아니라 저장소의 성질이 된다. compose 서비스와 `APP_CACHE_URL` 이 이미 있어 새 인프라가 늘지 않는다. 그리고 다음에 지을 LLM 응답 캐시가 같은 클라이언트를 쓴다 — 여기서 만드는 어댑터가 그때 재사용된다.

**LIST 를 고르는 이유** — 턴 순서가 곧 삽입 순서라 정렬 키가 필요 없다. `RPUSH` → `LTRIM(-N, -1)` → `EXPIRE` 셋을 파이프라인 한 번에 보내면 상한 유지와 수명 갱신이 한 왕복에 끝난다.

JSON 문자열 하나를 통째로 읽고 쓰는 방식은 기각했다 — 같은 세션에 동시 요청이 둘 오면 읽기-수정-쓰기가 겹쳐 한쪽 턴이 사라진다. `LTRIM` 은 그 경합에서 턴을 잃지 않는다.

키는 `session:{id}`, 값은 턴 하나당 JSON 문자열 하나(`question`, `search_query`, `answer`). **근거 청크 본문·인용·문서 식별자는 담지 않는다** — `conversation-session` 요구사항이며, 담으면 문서를 지운 뒤에도 그 내용이 세션에 남아 삭제를 우회한다.

### 2. 세션 식별자는 `secrets.token_urlsafe`

이 change 에는 인증도 소유권 검증도 없다(범위 밖). 그 상태에서 식별자가 유일한 방벽이므로 순번·UUID1·시각 기반은 쓰지 않는다. UUID4 도 요구사항을 만족하지만 `secrets.token_urlsafe(16)` 쪽이 "추측 불가능성이 목적"이라는 의도가 이름에 드러난다.

### 3. 재작성은 새 어댑터 없이 `AnswerGenerator` 를 재사용한다

재작성은 "프롬프트 문자열 하나 넣고 텍스트 받기"라 `AnswerGenerator.generate` 와 모양이 같다. `QueryRewriter` 프로토콜을 따로 두는 대안은 기각했다 — 실제로 다른 것은 프롬프트뿐인데 프로토콜을 나누면 테스트 스텁이 두 벌이 되고, 두 벌이 어긋나면 어긋난 줄 모른다.

차이는 전부 **서비스 계층의 정책**이라 어댑터에 닿지 않는다.

| 항목 | 답변 생성 | 재작성 |
|------|-----------|--------|
| 스트리밍 | 조각을 그대로 흘려보낸다 | 조각을 모아 문자열 하나로 만든다 — 사용자에게 보이지 않는 중간값이다 |
| timeout | `qa_llm_timeout_seconds` | `qa_rewrite_timeout_seconds` (더 짧게) |
| retry | 지수 백오프로 `max_attempts` 회 | **하지 않는다** — 결정 5 |
| 실패 처분 | `error` 이벤트로 스트림 종료 | 원문 폴백, 요청은 계속 |

동시성 예산은 `QaService` 의 `CapacityLimiter` 를 공유한다. 재작성은 검색보다 앞서고 답변 생성은 검색보다 뒤이므로 **한 요청이 두 슬롯을 동시에 쥐는 구간이 없다** — 순차라서 교착이 생기지 않는다.

### 4. 구조화 출력은 "한 줄" 규약

재작성 프롬프트는 **질의 한 줄만** 출력하도록 지시하고, 파서는 첫 번째 비어 있지 않은 줄을 취한다. 비었거나 `retrieval` 의 상한을 넘으면 결과를 버리고 원문으로 폴백한다.

JSON 출력 대안은 기각했다. Codex CLI 의 출력이 JSON 임을 보장하지 않아 파싱 실패 시 어차피 폴백인데, 필드 이름·중괄호·이스케이프만큼 실패 표면이 넓어진다. 한 줄 규약은 `core/prompting.py` 의 `VERDICT:` 줄 규약과 같은 발상이고, 코드베이스에 이미 있는 패턴이다.

### 5. 재작성은 재시도하지 않는다

재작성은 답변 생성 **앞**에 붙으므로 그 지연이 첫 바이트까지의 시간에 그대로 더해진다. 재시도를 붙이면 최악의 경우가 배로 늘어나는데, 얻는 것은 후속 질문의 검색 품질 하나뿐이고 잃는 것은 모든 후속 질문의 체감 속도다. 한 번 해 보고 안 되면 원문으로 간다.

`qa_rewrite_timeout_seconds` 는 답변 생성 timeout 보다 짧게 기본값을 잡는다 — 재작성은 짧은 문자열 하나를 만드는 일이라 오래 걸린다는 것 자체가 이상 신호다.

### 6. 새 단계가 `prepare`/`stream` 경계 어느 쪽에 놓이는가

```
prepare (스트림 밖 — 여기서 난 예외는 상태 코드가 된다)
  ├─ 히스토리 조회      조회 실패 → 빈 히스토리, 예외를 밖으로 내지 않는다
  ├─ 질의 재작성        실패·초과 → 원문, 예외를 밖으로 내지 않는다
  └─ 검색               실패 → 503 storage_unavailable  (기존 계약 그대로)

stream (스트림 안 — 여기서 난 실패는 error 이벤트가 된다)
  ├─ sources
  ├─ answer*
  ├─ 턴 기록            done 을 내보내기 직전. 실패는 삼키고 degraded 로 표시
  └─ done | error
```

**히스토리 조회와 재작성이 `prepare` 인 이유** — 재작성 결과가 검색 입력이라 검색보다 앞서야 하고, 검색은 `prepare` 에 있어야 저장소 장애가 `503` 으로 나가는 기존 계약이 유지된다. 두 단계 모두 예외를 밖으로 내지 않으므로 `prepare` 의 상태 코드 의미는 달라지지 않는다.

**턴 기록이 `done` 직전인 이유** — 클라이언트는 `done` 을 받자마자 다음 턴을 보낼 수 있다. 기록을 `done` 뒤나 백그라운드 태스크로 미루면 그 다음 요청이 아직 기록되지 않은 히스토리를 읽어 재작성이 폴백한다. 대화가 빠를수록 자주 깨지는, 재현이 어려운 종류의 결함이다. 대가는 마지막 이벤트 앞에 붙는 Redis 왕복 한 번이며, 그것을 받아들인다.

### 7. 히스토리는 프롬프트에서 근거와 다른 구역에 들어간다

`build_prompt` 가 히스토리 인자를 받아 `<대화>` 구역을 `<근거>` 앞에 놓고, 지시문에 "`<대화>` 는 질문을 이해하기 위한 것이며 인용 대상이 아니다"를 더한다. 마커 검증은 손대지 않는다 — `_validate_markers` 가 이미 `1..source_count` 로 자르므로 히스토리를 가리키는 인용은 구조적으로 만들어질 수 없다.

`PROMPT_VERSION` 을 `qa-ko-1` → `qa-ko-2` 로 올린다. 그 상수의 주석이 이미 이유를 적어 두었다 — 캐시 키에 들어갈 값이라, 올리지 않으면 프롬프트 개선이 낡은 캐시에 가려 관측되지 않는다.

### 8. 캐시가 나중에 지켜야 할 제약 (이 change 는 캐시를 만들지 않는다)

LLM 응답 캐시는 아직 없다. 지을 때 **캐시 키는 사용자의 원문 질문이 아니라 재작성된 검색 질의를 기준으로 삼아야 한다.** 원문으로 키를 잡으면 서로 다른 세션의 `"그거 더 자세히"` 가 전부 같은 키에 모여, 사용자가 남의 대화에 대한 답변을 받는다. `done` 이벤트가 검색에 쓰인 질의를 노출하는 것이 이 제약을 지킬 재료를 미리 내놓는 것이기도 하다.

## Risks / Trade-offs

**재작성이 모든 후속 질문의 첫 바이트를 늦춘다** → 첫 턴은 재작성하지 않아 단일 턴 경로의 지연은 0 이다. 후속 턴은 짧은 timeout 과 무재시도로 최악의 경우를 한 번의 대기로 묶는다. 지연이 문제가 되면 재작성을 검색과 겹쳐 돌리는 대신 timeout 을 줄이는 쪽이 먼저다 — 겹치면 원문 검색과 재작성 검색 둘 중 무엇을 쓸지가 다시 정책이 된다.

**Redis 가 죽으면 후속 질문이 조용히 나빠진다** → `503` 대신 축소 동작을 고른 대가다. `done` 의 축소 표시와 헬스 프로브가 그 사실을 드러내며, 축소된 요청은 첫 턴과 정확히 같게 동작하므로 나빠지는 것은 후속 질문의 검색 품질뿐이고 답변의 정확성은 아니다.

**소유권 검증이 없어 식별자를 아는 누구나 그 대화 맥락을 쓴다** → 범위 밖으로 선언된 사항이고, 추측 불가능한 식별자·짧은 TTL·대화 본문 비로깅으로 노출 표면을 줄인다. 히스토리는 인용될 수 없으므로 새어 나갈 수 있는 것은 앞 턴 질문의 맥락이지 문서 내용이 아니다. 인증이 필요한 배포에서는 별도 change 가 필요하다는 사실을 `README.md` 에 적는다.

**히스토리를 넣으면 모델이 근거 없이도 답할 재료를 얻는다** → 이것이 이 change 의 가장 큰 품질 위험이다. 방어는 셋이고 서로 독립이다 — (1) 근거 0 건이면 생성기를 아예 호출하지 않는 기존 경로, (2) 프롬프트의 구역 분리와 명시적 지시, (3) `_validate_markers` 의 범위 밖 마커 폐기. 셋 중 하나가 무너져도 나머지가 남는다.

**Codex 프로세스 수가 요청당 최대 두 배가 된다** → 순차 실행이라 동시 점유는 늘지 않지만, 세션 풀의 회전율은 올라간다. `SessionPool` 의 유휴 세션 재사용이 이 비용을 흡수하는지 확인하고, 흡수하지 못하면 상한을 조정한다.

## Migration Plan

`session_id` 없는 요청이 기존 경로 그대로이므로 **순수 추가**다. 기존 클라이언트는 고칠 것이 없다.

배포 순서 — Redis 는 이미 compose 에 있으므로 인프라 변경이 없다. 설정 항목(세션 TTL, 턴 상한, 재작성 timeout)은 전부 기본값을 가져 환경 변수를 주지 않아도 기동한다.

롤백 — `QaRequest.session_id` 를 빼면 세션 계층 전체가 도달 불가가 된다. Redis 에 남은 세션은 TTL 로 스스로 사라져 정리 작업이 필요 없다.

**아카이브 순서** — `answer-generation` 델타는 `add-answer-generation` change 가 아카이브되어 `openspec/specs/answer-generation/spec.md` 가 생긴 뒤에 얹혀야 한다. 순서가 뒤집히면 이 change 의 델타만으로 반쪽짜리 메인 스펙이 만들어진다.

## Open Questions

- 재작성된 질의를 기준으로 잡은 캐시가 **세션을 넘어 공유되어야 하는가.** 같은 재작성 결과를 얻은 서로 다른 세션은 같은 답변을 받아도 되는 것처럼 보이지만, 재작성이 히스토리의 표현을 옮겨 담으므로 그 문자열 자체가 앞 턴의 내용을 담을 수 있다. 캐시 change 에서 답하면 되며, 이 change 의 스펙·설계·작업 분해를 바꾸지 않는다.
- 재작성 프롬프트를 한국어로만 둘지, 질문 언어를 따라가게 할지. 지금 답변 프롬프트가 한국어 고정이라 일단 맞추고, 다국어 요구가 실제로 생기면 둘을 함께 옮긴다.
