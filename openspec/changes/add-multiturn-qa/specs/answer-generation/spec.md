## ADDED Requirements

### Requirement: 세션을 지정해도 스트림의 모양은 달라지지 않는다

요청은 세션을 **선택적으로** 지정할 수 있어야 한다 (**SHALL**). 세션을 지정한 요청과 지정하지 않은 요청이 내보내는 이벤트의 **종류·순서·횟수는 같아야 한다** (**MUST**) — `sources` 정확히 1회로 시작하고, `answer` 0회 이상이 뒤따르고, `done` 또는 `error` 정확히 하나로 끝난다.

세션 때문에 새로운 이벤트 이름이 생겨서는 안 된다 (**MUST NOT**). 조각을 나누거나 합치는 규칙도 달라져서는 안 된다 (**MUST NOT**).

세션을 지정하지 않은 요청의 동작은 이 change 이전과 같아야 한다 (**MUST**).

> 멀티턴은 검색에 넣을 문자열과 프롬프트에 실을 재료를 바꾸는 것이지 전달 방식을 바꾸는 것이 아니다. 이벤트 어휘가 세션 유무로 갈리면 클라이언트가 두 모드를 각각 구현해야 하고, `sources` 를 먼저 보내 얻은 이득이 분기 뒤로 숨는다.

#### Scenario: 세션을 지정한 요청도 같은 이벤트 순서로 끝난다

- **WHEN** 히스토리가 있는 세션을 지정해 질문한다
- **THEN** 콘텐츠 타입이 `text/event-stream` 이고, 첫 이벤트가 `sources` 이며, 마지막이 `done` 또는 `error` 정확히 하나이고, `sources`·`answer`·`done`·`error` 밖의 이벤트 이름이 없다

#### Scenario: 조각을 이어 붙이면 최종 답변이 된다

- **WHEN** 히스토리가 있는 세션을 지정해 질문한다
- **THEN** `answer` 이벤트의 `text` 를 등장 순서대로 이어 붙인 것이 `done` 이벤트의 `answer` 와 같다

#### Scenario: 세션 없는 요청은 이전과 같다

- **WHEN** 세션을 지정하지 않고 질문한다
- **THEN** 세션 저장소에 접근이 일어나지 않고, 검색에 쓰인 질의가 질문 문자열과 같으며, 응답의 이벤트 순서와 `done` 의 내용이 이 change 이전과 같다

### Requirement: 히스토리는 해석의 재료일 뿐 인용의 대상이 아니다

히스토리가 있는 요청에서 생성 프롬프트는 앞선 턴들을 포함할 수 있다 (**MAY**). 그러나 답변이 인용할 수 있는 근거는 **이번 요청의 검색이 돌려준 청크뿐**이어야 한다 (**MUST**).

인용 번호는 이번 요청의 `sources` 에 실린 근거만 가리켜야 한다 (**MUST**). 히스토리의 앞선 답변이나 앞선 턴의 근거를 가리키는 인용이 `done` 이벤트에 실려서는 안 된다 (**MUST NOT**).

프롬프트는 히스토리와 근거를 **구분 가능한 형태로** 실어야 하며 (**SHALL**), 히스토리 부분이 근거로 취급되지 않는다는 지시를 포함해야 한다 (**MUST**).

> 앞 턴의 답변은 이미 문서에서 나온 문장이니 인용해도 된다고 볼 여지가 있는데, 그 순간 근거의 세대 관리가 무너진다. 그 답변이 인용한 문서는 지워졌을 수도 새 리비전으로 바뀌었을 수도 있고, 히스토리에는 그것을 확인할 `revision` 이 없다 — `conversation-session` 이 근거 본문과 문서 식별자를 세션에 저장하지 않기로 한 이유가 이것이다. 인용 가능한 것을 이번 검색 결과로 못 박는 것이 그 결정의 짝이다.

#### Scenario: 인용은 이번 요청의 근거만 가리킨다

- **WHEN** 히스토리가 있는 세션에서 질문해 답변을 받는다
- **THEN** `done` 이벤트의 모든 인용이 이번 스트림의 `sources` 에 실린 항목을 가리키고, 각 인용에서 문서 식별자·파일명·리비전·원문 위치를 확인할 수 있다

#### Scenario: 앞 턴의 문서가 이번 검색에 없으면 인용되지 않는다

- **WHEN** 앞 턴이 인용한 문서를 삭제한 뒤 같은 세션에서 그 내용을 가리키는 후속 질문을 보낸다
- **THEN** `done` 이벤트에 삭제된 문서를 가리키는 인용이 하나도 없다

#### Scenario: 히스토리와 근거가 프롬프트에서 갈린다

- **WHEN** 히스토리가 있는 세션에서 질문한다
- **THEN** 생성기에 전달된 프롬프트에서 히스토리 구역과 근거 구역이 서로 다른 표시로 구분되고, 히스토리를 인용하지 말라는 지시가 들어 있다

### Requirement: 히스토리가 있어도 근거가 없으면 답을 지어내지 않는다

검색 결과가 비어 있으면 히스토리가 있어도 생성기를 호출해서는 안 되며 (**MUST NOT**), `no_evidence` 로 끝나야 한다 (**SHALL**).

검색 결과가 있어도 그것이 질문을 뒷받침하지 않으면 `insufficient_evidence` 로 끝나야 한다 (**SHALL**). 어느 경우에도 앞선 턴의 답변 내용을 근거 삼아 답변을 만들어서는 안 된다 (**MUST NOT**).

> 히스토리를 프롬프트에 넣는 순간 모델에게는 근거가 0건이어도 쓸 재료가 생긴다. 앞 턴의 답변을 되풀이하면 그럴듯한 문장이 나오지만 그것은 이번 질문의 근거가 아니며, `citations` 가 비어 있어 사용자는 출처 없는 답변을 받는다. 환각 억제가 무너지는 지점이 정확히 여기다.

#### Scenario: 히스토리가 있어도 근거 0건이면 거절한다

- **WHEN** 답변을 받은 세션에서 어느 문서와도 무관한 질문을 보내 검색 결과가 비게 한다
- **THEN** `finish_reason` 이 `no_evidence` 이고, 답변 생성기가 호출되지 않으며, `citations` 가 비어 있다

#### Scenario: 앞 턴의 답변이 되풀이되지 않는다

- **WHEN** 답변을 받은 세션에서 검색 결과가 비는 질문을 보낸다
- **THEN** 이번 요청의 답변 문자열에 앞 턴의 답변 본문이 실리지 않는다

#### Scenario: 근거가 있어도 무관하면 판정이 갈린다

- **WHEN** 히스토리가 있는 세션에서, 근거는 검색되지만 질문을 뒷받침하지 못하는 질문을 보낸다
- **THEN** `finish_reason` 이 `insufficient_evidence` 이고 `sources` 는 그대로 실린다

### Requirement: 종료 이벤트가 세션 정체성과 검색에 쓰인 질의를 알려 준다

`done` 이벤트는 기존 항목에 더해 **세션 식별자**, **이번 요청의 턴 번호**, **검색에 실제로 쓰인 질의**를 포함해야 한다 (**SHALL**). 세션 계층이 축소 동작한 경우 그 사실도 확인 가능해야 한다 (**MUST**).

세션을 지정하지 않은 요청에서도 이 항목들이 같은 자리에 있어야 한다 (**MUST**) — 클라이언트가 필드의 존재 여부로 분기하지 않게 한다.

기존 항목 `finish_reason`·`answer`·`citations`·`elapsed_ms` 는 그대로 실려야 한다 (**MUST**).

#### Scenario: 종료 이벤트에서 세션을 이어 갈 수 있다

- **WHEN** 세션 없이 질문해 답변을 받고, `done` 이벤트의 세션 식별자로 다음 질문을 보낸다
- **THEN** 두 번째 요청의 `done` 이벤트가 같은 세션 식별자를 싣고 턴 번호가 하나 크다

#### Scenario: 실패로 끝난 스트림은 세션을 진전시키지 않는다

- **WHEN** 세션을 지정한 요청이 `error` 로 끝난 뒤 같은 세션으로 다시 질문한다
- **THEN** 두 번째 요청의 턴 번호가 실패한 요청의 것과 같다
