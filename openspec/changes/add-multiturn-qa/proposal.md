## Why

지금 `/qa` 는 요청 하나가 곧 대화 하나다. 질문 문자열이 그대로 질의 임베딩이 되므로 `"그거 더 자세히"`·`"아까 그 문서에서"` 같은 후속 질문은 **지시어만 임베딩된 벡터**로 검색된다. 검색은 오류를 내지 않는다 — 유사도 하한에 걸려 근거 0건이 되고, `retrieval` 계약대로 `200` 과 빈 결과가 나가고, `answer-generation` 이 그것을 `no_evidence` 로 마감한다. 사용자에게는 "근거를 찾지 못했습니다"만 보이고, 무엇이 잘못됐는지는 어디에도 드러나지 않는다.

**이것은 PRD 요구사항이 아니다.** PRD §2(Query & Answer)는 단일 턴 질의응답까지만 요구한다. 이 change 는 그 위에 얹는 확장이며, PRD 가 요구하는 것(스트리밍·출처·환각 억제)을 **하나도 바꾸지 않는 것**이 성립 조건이다. 확장이 기존 계약을 건드리면 얻는 것보다 잃는 것이 크다.

## What Changes

새 계층은 기존 파이프라인의 **앞과 뒤에만** 붙는다. `retrieval` 이 정한 검색 계약과 `answer-generation` 이 정한 이벤트 계약은 그대로다.

    질문 + session_id
        → [신규] 히스토리 조회
        → [신규] 질의 재작성 ─────┐
                                  ↓
                            기존 retrieval (계약 불변)
                                  ↓
        → [신규] 히스토리 주입 ─→ 기존 생성·스트리밍 (계약 불변)
        → [신규] 턴 기록

- **세션 대화 저장소를 신설한다.** Redis 에 세션별 턴 목록을 담고 TTL 로 만료시킨다. 세션당 턴 수와 턴당 문자 수에 상한을 둔다. 지금 Redis 는 compose 서비스와 헬스 프로브(`adapters/cache/probe.py`)로만 존재하므로 **실제 Redis 클라이언트 어댑터를 처음 만든다.**
- **질의 재작성 단계를 신설한다.** 히스토리와 현재 질문을 LLM 에 넣어 앞뒤 맥락 없이 성립하는 독립형 검색 질의 하나를 얻는다. 히스토리가 비면 재작성하지 않고 원문을 그대로 쓴다. 재작성이 실패·지연되면 원문으로 폴백한다 — 재작성은 검색 품질을 **높이는** 단계이지 요청을 **막는** 단계가 아니다.
- **생성 프롬프트에 히스토리를 주입한다.** 단 인용 가능한 근거는 이번 검색이 돌려준 청크뿐이다. 히스토리는 지시어를 해석하기 위한 재료이지 인용처가 아니다 — 이전 턴의 문장에 `[n]` 을 달 수 있게 되면 환각 억제가 뚫린다.
- **`/qa` 요청·응답에 `session_id` 를 더한다.** `session_id` 없는 요청은 지금과 **완전히 동일하게** 동작한다 (**BREAKING 아님**). 재작성이 일어났으면 무엇으로 검색했는지를 응답에서 확인할 수 있어야 한다.

**범위 밖** — 사용자 인증 및 세션 소유권 검증, 대화 영구 보관 및 조회 API, 검색 알고리즘 자체 변경(E5 역할 접두사 규약·유사도 하한 등 기존 계약 유지), SSE 이벤트 어휘·순서 변경.

## Capabilities

### New Capabilities

- `conversation-session`: 세션 하나의 수명과 내용. 세션 식별자 발급, 턴 기록, TTL 기반 만료, 세션당 턴 수·턴당 길이 상한, 저장소에 닿지 못할 때의 처분.
- `query-rewriting`: 히스토리와 현재 질문을 독립형 검색 질의 하나로 바꾸는 계약. 재작성을 하는 조건과 하지 않는 조건, 결과가 만족해야 할 제약(`retrieval` 의 질의 상한), 실패·지연 시의 원문 폴백.

### Modified Capabilities

- `answer-generation`: 요청이 `session_id` 를 받을 수 있게 되고, 생성 프롬프트가 히스토리를 포함하며, **인용 근거는 검색된 청크로만 제한**된다는 것이 요구사항으로 명시된다. 종료 이벤트가 세션 정체성과 실제 검색에 쓰인 질의를 노출한다. 이벤트 종류·순서·조각 전달 규칙은 바뀌지 않는다.

> `answer-generation` 은 아직 `openspec/specs/` 에 없다 — 구현은 끝났으나 `add-answer-generation` change 가 아카이브되지 않은 상태다. 이 change 의 델타는 그 change 가 아카이브된 뒤에 얹힌다.

## Impact

**신규 코드**

| 경로 | 내용 |
|------|------|
| `adapters/cache/redis.py` | Redis 클라이언트 어댑터 — 지금 없는 것을 새로 만든다 |
| `adapters/session/` | 세션 저장소, `protocols.py` 의 프로토콜 뒤에 둔다 |
| `core/rewriting.py` | 재작성 프롬프트 조립과 출력 파싱 (순수 함수) |
| `services/rewriting.py` | 재작성 오케스트레이션 — timeout·폴백 |

**변경되는 코드**

| 경로 | 변경 |
|------|------|
| `api/routes/qa.py` | `QaRequest.session_id` 추가 |
| `services/qa.py` | `prepare` 가 재작성을, `stream` 종료 후 턴 기록을 한다. `QaContext` 가 세션과 재작성 결과를 담는다 |
| `core/prompting.py` | `build_prompt` 에 히스토리 인자. `PROMPT_VERSION` 을 올린다 |
| `config.py` | 세션 TTL·턴 상한·재작성 timeout 설정 항목 |
| `adapters/protocols.py` | 세션 저장소 프로토콜 |

**손대지 않는 코드** — `services/retrieval.py`, `adapters/embedding/`, `adapters/vector_store/`, `api/sse.py`. 이 넷이 그대로인 것이 "파이프라인 계약 불변"의 실물 증거다.

**문서** — `PROMPT_DESIGN.md` 에 재작성 프롬프트와 히스토리 주입 전략, `ARCHITECTURE.md` 에 세션 저장소 선택 근거, `README.md` 에 `session_id` 사용법.

**앞으로 지어질 것에 미치는 영향** — LLM 응답 캐싱은 아직 구현되지 않았다(Redis 는 헬스 프로브까지만 쓰인다). 캐시 change 를 지을 때 **캐시 키는 원문 질문이 아니라 재작성된 질의를 기준으로 삼아야 한다** — 원문으로 키를 잡으면 서로 다른 세션의 `"그거 더 자세히"` 가 같은 키에 모여 남의 답변을 받는다. 이 사실을 캐시 change 가 스스로 발견하도록 두지 않고 여기서 못 박는다.
