## 0. 이월 정리 — 이 change의 **첫 커밋**에 포함

> 세 번째 이월 항목이다. 어려워서 밀린 게 아니라 "다음에"라고 적기만 해서 밀렸다. 그래서 마지막이 아니라 **맨 앞**에 둔다.

- [x] 0.1 `docker-compose.yml` 파일 끝 개행 복구 — `restart: unless-stopped` 로 끝나고 개행이 없었다. POSIX 텍스트 파일 규약이고, 없으면 다음 줄을 추가하는 diff 가 기존 마지막 줄까지 변경으로 잡는다
- [x] 0.2 고아 네임드 볼륨 처분 — `officeagent-onboarding-challenge_registry`(16KB)·`_vector-store`(3.0MB). compose 가 바인드 마운트(`./data/chroma`·`./data/registry`)로 전환하면서 최상위 `volumes:` 선언이 사라져 **다시 마운트될 경로가 없다.** 현행 바인드 마운트 데이터가 9시간 더 최신이고 내용은 `sample-docs` 재업로드로 복원되는 시험 데이터라 **이관 가치가 없다** — 옛 데이터로 새 데이터를 덮게 된다. `docker volume rm` 로 둘 다 제거했고, 현행 바인드 마운트 데이터(`data/chroma` 1.5M · `data/registry` 12K)는 그대로다

## 1. 설정과 도메인 값 객체

- [x] 1.1 설정 항목 4개 추가 — `retrieval_top_k`(기본 5, `gt=0`), `retrieval_max_top_k`(기본 50, `gt=0`), `retrieval_min_score`(범위 `[0, 1]`, **초안 0.75 · 5.3에서 계측으로 확정**), `retrieval_max_query_chars`(기본 1000, `gt=0`). 전부 기본값을 두어 "설정 없이 기동된다"는 기존 요구사항을 깨지 않는다 (design 결정 4·5·6)
- [x] 1.2 **`retrieval_top_k > retrieval_max_top_k` 는 기동을 막는다** — `model_validator`로 검증한다. 기존 `chunk_overlap >= chunk_size` 방어와 같은 자리·같은 방식이다. 그 구성에서는 어떤 요청도 통과할 수 없으므로 조용히 뜨면 안 된다 (design 결정 4)
- [x] 1.3 설정 테스트 — 새 항목 없이도 기동되고 기본값이 적용되는지 / 무효값(`top_k` 0, 상한 0, 하한 음수·1 초과, 질의 상한 0)이면 기동에 실패하는지 / **기본 K가 상한보다 크면 기동에 실패하는지** (spec "기본 K가 상한보다 크면 기동을 막는다")
- [x] 1.4 `core/retrieval.py` — `ScoredChunk` 값 객체. 담는 것은 `document_id`·`revision`·`index_signature`·`chunk_index`·`text`·`location`(`ChunkLocation` 재사용)·`filename`·`format`·`score`. **표준 라이브러리만** 쓴다(`core/`는 pydantic도 금지). 점수 범위(`0 ≤ score ≤ 1`)를 `__post_init__`에서 검증한다 (design 결정 2·3)
- [x] 1.5 `ScoredChunk` 테스트 — 범위를 벗어난 점수·음수 `chunk_index`가 거부되는지. 값 객체가 스스로 지키는 불변식이 있어야 어댑터의 변환 버그가 여기서 걸린다
- [x] 1.6 `core/exceptions.py`에 `EmptyQuery`(`empty_query`)·`QueryTooLong`(`query_too_long`)·`InvalidTopK`(`invalid_top_k`) 추가. `ErrorCode`에는 **추가만** 하고 기존 값을 바꾸지 않는다. `QueryTooLong`은 적용된 **문자 수 상한과 토큰 상한을 함께**(어느 쪽에 걸렸든 응답 모양이 같아야 소비자가 파서를 하나만 든다), `InvalidTopK`는 적용된 K 상한을 각각 `extra`로 나른다 — 설정에 달린 값이라 클라이언트가 미리 알 수 없다. **`InvalidTopK`는 상한 초과에만 쓴다** — 하한은 요청 모델의 정적 검증이 `validation_error`로 끝낸다 (design 결정 8)
- [x] 1.7 `api/errors.py`의 `ErrorCode → HTTP 상태` 표에 세 코드를 422로 등록. 변환은 여전히 이 계층에서만 한다

## 2. 색인 서명 유도를 배선으로 올린다

> 검색과 수집이 **같은 서명**을 봐야 한다. 각자 유도하면 어긋난 순간 "방금 올린 문서가 검색되지 않는데 오류는 없는" 상태가 된다 (design 결정 7). 동작 변경이 아니라 인자 이동이므로, **기존 수집 테스트가 전부 그대로 통과하는 것**이 합격 조건이다.

- [x] 2.1 `IngestionService` 생성자에서 `derive_index_signature` 호출을 걷어내고 `index_signature`를 인자로 받는다. `chunk_strategy`는 여전히 분할 함수 해석에 필요하므로 남긴다
- [x] 2.2 `create_app`이 서명을 한 번 유도해 수집 서비스에 주입한다. 임베더 `signature`·전략 이름·`CHUNK_STRATEGY_VERSION`·청크 크기·겹침이 재료라는 사실은 그대로다
- [x] 2.3 `tests/ingestion_harness.py`의 `make_service`가 서명을 유도해 넘기도록 수정 — 개별 테스트는 건드리지 않는다. "임베더 `signature`를 바꾸면 색인 서명이 달라진다"를 재현하던 기존 테스트가 계속 성립해야 한다
- [x] 2.4 기존 수집 스위트 전체가 통과하는지 확인 — 특히 `index_signature` 관련 테스트(같은 구성/다른 구성, `reindexed`, 기동 정리)
- [x] 2.5 `ARCHITECTURE.md`의 색인 서명 서술에 **유도 위치가 배선으로 올라간 이유**를 덧붙인다. 앞 문서가 "수집 서비스가 기동 시점에 고정한다"고 적고 있으므로 반드시 함께 고친다 — 안 고치면 문서-코드 불일치다. **이 묶음 직후에 적는다**

## 3. 임베더 토큰 계산을 질의 경로까지 넓힌다

> 문자 수 상한만으로는 조용한 절단을 막을 수 없다 — 실측 최악 비율이 5.016 토큰/문자라 안전한 문자 상한이 101자가 되는데, 그러면 정상 질문까지 거부한다 (design 결정 6). 수집은 이미 실제 토크나이저로 세고 있으므로, 검색만 대리 지표를 쓰던 비대칭을 없앤다.

- [x] 3.1 `Embedder` 프로토콜의 `count_tokens` 를 `count_document_tokens` 로 **개명**하고 `count_query_tokens` 를 **추가**한다. `embed_documents`/`embed_query` 와 이름이 짝을 이룬다. 현재 이름은 문서 경로 전용인데 그 사실이 이름에 없어 이미 거짓이다. 접두사 문자열은 여전히 어댑터 밖으로 나가지 않는다 (design 결정 6)
- [x] 3.2 `SentenceTransformerEmbedder` 구현 — 두 메서드가 각자의 역할 접두사를 붙여 세고, **특수 토큰까지 포함한 실제 인코딩 길이**를 돌려준다. 본문만 세면 상한 바로 아래 입력이 조용히 잘린다
- [x] 3.3 호출부 갱신 — `IngestionService._guard_tokens` 와 `FakeEmbedder`, 기존 `test_embedding.py`. **수집의 관측 가능한 동작은 바뀌지 않는다**(같은 값을 같은 자리에서 센다). 기존 수집 스위트가 전부 통과하는 것이 합격 조건이다
- [x] 3.4 임베더 테스트 — 두 메서드가 각자 접두사를 포함해 세는지 / 같은 텍스트에 대해 두 값이 접두사 길이만큼 다른지 / 실물 모델로 `count_query_tokens("query: " 포함 인코딩)` 이 실제 `encode` 길이와 일치하는지(가중치 없으면 스킵). **이 일치가 깨지면 가드가 통과시킨 질의가 잘린다**
- [x] 3.5 `ARCHITECTURE.md` 에 토큰 예산 역산 기록 — 실측표(입력 창 512 / 특수 토큰 2 / `query: ` 3 / 본문 가용 507 / 최악 5.016 토큰·문자 / 한국어 평문 0.55), **최악 문자가 CJK 호환 정사각 문자이고 정규화에서 펼쳐지기 때문이라는 사실**, 절대 안전 상한 101자와 그 값이 문자 상한 단독 설계를 기각하는 근거가 된 경위, 두 상한의 역할 분담, 토큰 상한을 설정 항목으로 두지 않는 이유. **구현 직후에 적는다**

## 4. 저장소 질의 — 프로토콜과 어댑터

- [x] 4.1 `VectorStore` 프로토콜에 `query(embedding, *, top_k, versions) -> list[ScoredChunk]` 추가. 프로토콜 docstring의 "`query`가 없다 — retrieval change가 붙인다"를 **실제로 붙인 내용으로 교체한다**. 질의를 문자열이 아니라 벡터로 받는 이유(어댑터가 임베더를 알면 안 된다)를 남긴다 (design 결정 2)
- [x] 4.2 Chroma 어댑터에 질의 구현 — `versions` 삼중항 목록을 `$or`/`$and` 필터로 조립하고, `n_results=top_k`로 질의한다. 기존 `_offload`를 그대로 써서 오프로드와 `StorageUnavailable` 변환 규약을 하나로 유지한다
- [x] 4.3 **빈 `versions`는 "대상 없음"이다** — 저장소를 건드리지 않고 빈 목록을 돌려준다. "조건 없음 = 전체"로 뒤집히면 지워진 문서가 검색된다. 코드에 주석으로 남기고 4.6에서 테스트로 고정한다 (design 결정 1)
- [x] 4.4 거리 → 유사도 변환 — `1 - 거리`, `[0, 1]` 클램프. **클램프가 실제로 발동하면 경고 로그**를 남긴다(분포 이동 신호를 지우지 않기 위해). 변환은 어댑터 안에만 있다 (design 결정 3)
- [x] 4.5 응답 메타데이터 → `ScoredChunk` 조립 — `page` 키가 없는 경우(txt·md)를 처리한다. 수집이 값 없는 키를 넣지 않는다는 규약의 반대편이다
- [x] 4.6 벡터 스토어 질의 테스트 (**실물 Chroma**, 서버 없으면 스킵) — 저장한 청크가 질의로 돌아오는지 / 점수가 내림차순인지 / `versions`에 없는 삼중항의 청크가 결과에 없는지 / **빈 `versions`가 빈 결과이고 전체 검색으로 뒤집히지 않는지** / 같은 `revision`·다른 서명 청크가 섞이지 않는지 / 메타데이터 왕복(위치·파일명·포맷) / 접근 실패가 `StorageUnavailable`인지
- [x] 4.7 `tests/stubs.py`의 `StubVectorStore`에 질의 구현 — **완전 탐색 코사인**. 근사 검색의 흔들림을 없애 임베딩 품질만 남긴다(7장 품질 테스트의 전제). 지연 주입(`delay`)과 실패 주입도 질의 경로에 적용되게 한다 (design 결정 10)
- [x] 4.8 `ARCHITECTURE.md`에 검색 대상 필터 기록 — 삼중항 필터를 **질의 이전에** 거는 이유, 기각한 대안(사후 필터·서명만 필터·필터 없음), 빈 목록이 전체 검색이 아닌 이유, 거리를 유사도로 바꾸는 이유와 클램프의 대가. **구현 직후에 적는다**

## 5. 검색 서비스

- [x] 5.1 `services/retrieval.py` — `RetrievalService(embedder, vector_store, registry, *, index_signature, top_k, min_score)`. 순서는 **질의 임베딩 → 대상 집합 확정 → 저장소 질의 → 현재성 재검증 → 하한 적용 → 조립**. 질의 벡터는 **`embed_query`로** 계산한다 — `embed_documents([query])[0]` 도 벡터를 내지만 오류 없이 점수 분포만 이동한다 (design 결정 11·12)
- [x] 5.2 대상 집합 확정 — 레지스트리 전체를 읽어 `index_status == indexed` 이고 `index_signature`가 현재 값인 문서만 골라 `(document_id, revision, index_signature)` 삼중항으로 만든다. 비면 저장소를 건드리지 않는다 (design 결정 1)
- [x] 5.3 **유사도 하한 기본값 계측** — `sample-docs` 두 문서를 색인하고 스펙의 관련 질의 4개와 무관 질의의 점수를 실제로 재서, 두 분포 사이에 기본값을 놓는다. 잰 숫자를 그대로 5.13에 옮겨 적는다. **감으로 상수를 적지 않는다** (design 결정 5)
- [x] 5.4 **질의 뒤 현재성 재검증** — 결과에 실제로 기여한 문서만 레지스트리에서 다시 읽어(`get`, 보통 한두 건) 현재 `(revision, index_signature)`가 필터에 쓴 삼중항과 같은지 본다. 다르면 **그 문서의 결과를 버린다**(재시도하지 않는다). 레지스트리 읽기와 저장소 질의 사이는 잠겨 있지 않아, 교체 커밋이 그 사이에 끼면 방금 밀려난 리비전이 결과가 된다 (design 결정 13)
- [x] 5.5 하한 적용 — 서비스에서 거른다(어댑터가 아니라). 하한이 정책이고 저장소는 정책을 모른다
- [x] 5.6 `FakeEmbedder`에 **질의 경로 호출 기록** 추가 — `embed_documents`가 `batches`를 남기듯 `embed_query`도 호출된 질의를 남긴다. **두 경로가 같은 벡터를 낸다는 성질은 그대로 둔다** — 비대칭으로 바꾸면 해시 기반 벡터에 유사도 구조가 없어져 5.10의 순위 단언이 임의값이 된다. 비대칭성은 페이크가 아니라 실물 모델의 성질이라 7.7에서 확인한다 (design 결정 12)
- [x] 5.7 서비스 테스트 (임베딩 경로) — 질의 한 건을 처리하는 동안 **질의용 경로가 정확히 한 번**, **문서용 경로가 0번** 호출되는지. 경로를 바꿔 써도 결과 형식은 멀쩡하므로, 이 단언이 없으면 그 실수가 검출되지 않는다 (spec "질의는 질의용 임베딩 경로로 계산된다")
- [x] 5.8 서비스 테스트 (대상 집합) — 문서 없음 → 빈 결과이고 **저장소 질의가 호출되지 않음** / 삭제된 문서가 결과에 없음 / 이전 리비전 청크가 저장소에 남아 있어도 결과에 없음 / `stale` 문서가 결과에 없음 (spec "검색 대상은 지금 유효한 청크뿐이다")
- [x] 5.9 서비스 테스트 (동시 변경) — `StubDocumentRegistry`에 **조회 사이 변경을 주입**할 수 있게 하고(대상 집합 확정 뒤 / 저장소 질의 뒤 각각), 세 가지를 단언한다: 대상 집합 확정 뒤 교체가 커밋되면 그 문서의 결과가 없거나 전부 새 리비전 / 저장소 질의 뒤 삭제가 완료되면 그 문서의 결과가 0개 / 한 `document_id`의 결과들이 모두 같은 `revision`. **낡은 `revision`이 결과에 실려 나가면 다음 change의 캐시가 무효화에 걸리지 않는 항목을 만든다** (spec "검색 도중 교체가 확정되면…", "검색 도중 삭제가 완료되면…", "한 문서의 결과는 전부 같은 리비전이다")
- [x] 5.10 서비스 테스트 (순서·K) — 점수 내림차순 / `top_k` 지정이 설정 기본값을 이김 / 대상이 K보다 적으면 있는 만큼만이고 채우지 않음 / 같은 질의 두 번이 같은 결과. 페이크 임베더로 **질의를 특정 청크 본문과 똑같이 두어** 1위를 확정적으로 만든다 (design 결정 10)

## 6. API 계층

- [ ] 6.1 `POST /search` — 요청 `{"query", "top_k"?}`, 응답 `{"query", "top_k", "results", "count"}`. 결과 항목에 `document_id`·`filename`·`format`·`revision`·`chunk_index`·`text`·`score`와 위치(PDF는 `page`, 텍스트는 `char_start`/`char_end`)를 싣는다 (spec "모든 검색 결과는 원문 출처를 특정한다")
- [ ] 6.2 요청 검증 (문자 수) — 공백 제거 후 비면 `EmptyQuery`, **문자 수** 상한 초과면 `QueryTooLong`(두 상한을 `extra`로). 토크나이저에 닿기 전에 판정한다 — 이 상한의 목적은 절단 방지가 아니라 임의 길이 입력을 막는 것이다 (design 결정 6·8)
- [ ] 6.3 요청 검증 (토큰 수) — 문자 수를 통과한 질의를 `count_query_tokens`(3.1)로 세어 임베더의 `max_input_tokens` 를 넘으면 `QueryTooLong`. **질의 벡터 계산 이전에** 판정한다. 토큰 계산은 블로킹이므로 스레드풀로 오프로드한다 — 수집이 `_guard_tokens` 를 오프로드하는 것과 같은 이유다. **이쪽이 조용한 절단을 막는 진짜 가드다** (spec "문자 수는 상한 이내이지만 토큰이 입력 창을 넘는 질의")
- [ ] 6.4 `top_k` 경계 검증 — **하한은 요청 모델에** (`Field(ge=1)`, 프레임워크가 `validation_error`로 끝낸다. 스키마에 있으므로 OpenAPI 문서에 그대로 드러난다), **상한은 라우터에서 설정과 대조**해 `InvalidTopK`(적용 상한을 `extra`로). 상한은 기동 시점에야 정해지는 값이라 스키마에 넣을 수 없다 (design 결정 8)
- [ ] 6.5 라우터 등록과 로깅 — 질의 한 건이 무엇을 했는지 한 줄로(요청 id·결과 수·최고 점수·대상 문서 수). **질의 문자열과 청크 본문은 로그에 싣지 않는다** — 수집이 문서 내용을 로그에 남기지 않는 것과 같은 이유다
- [ ] 6.6 API 테스트 (성공 경로) — 200과 봉투 4필드 / 결과 개수와 `count` 일치 / 점수 범위와 내림차순 / `top_k` 지정 (spec "질의에 대해 관련 청크를 유사도 순으로 돌려준다")
- [ ] 6.7 API 테스트 (출처) — 텍스트 결과의 오프셋이 시작 < 끝이고 본문이 원문의 부분 문자열 / PDF 결과의 페이지 번호가 1 이상 총 쪽 수 이하 / 결과의 `filename`·`format`·`revision`이 문서 상세와 일치하고 `chunk_index`가 `[0, chunk_count)` 안 (spec "모든 검색 결과는 원문 출처를 특정한다")
- [ ] 6.8 API 테스트 (오류 경로) — 빈 질의 422 `empty_query` / 공백만 422 `empty_query` / **문자 수 상한 초과 422 `query_too_long` + 두 상한 노출** / **문자 수는 이내지만 인코딩하면 입력 창을 넘는 질의 422 `query_too_long`** / **문자 수 상한 이내의 평범한 질문은 200**(토큰 가드가 정상 질문을 거부하지 않는지) / **`top_k` 0·음수 422 `validation_error`** / **`top_k` 상한 초과 422 `invalid_top_k` + 상한 노출**. **거부된 모든 경우에 질의 벡터가 계산되지 않고 저장소 질의가 호출되지 않았는지 단언**한다(대역이 호출을 기록해야 한다 — 5.6). 하한 쪽은 프레임워크가 핸들러 진입 전에 끝내므로 자동으로 성립하지만, **그 사실을 테스트가 고정해 두지 않으면** 검증이 핸들러 안으로 옮겨졌을 때 조용히 깨진다 (spec "유효하지 않은 질의는 검색 없이 거부된다")
- [ ] 6.9 API 테스트 (저장소 장애) — 질의 실패 주입 시 503 `storage_unavailable`이고 내부 예외 메시지가 응답에 없음. **빈 결과로 위장되지 않는지**가 핵심 단언이다 (spec "저장소에 접근할 수 없으면 검색은 명확하게 실패한다")
- [ ] 6.10 `README.md` 갱신 — `POST /search` 요청·응답 예시(한국어 질의), 새 설정 항목 4개(이름·의미·기본값. **기본 K와 K 상한이 함께 검증된다는 사실 포함**), **질의 길이 제한이 문자 수와 토큰 수 두 겹이고 토큰 상한은 모델이 정한다는 사실**, **검색이 답변을 만들지 않는다는 사실과 그래서 무엇을 진단할 수 있는지**. **API가 완성된 직후에 적는다**

- [ ] 7.3 질의-기대 문서 쌍 4건 테스트 — `"교육비는 얼마까지 지원되나요?"` → `company-policy.txt` · `"200만원"` / `"재택근무는 일주일에 몇 번 할 수 있나요?"` → `company-policy.txt` · `"주 2회"` / `"PR을 머지하려면 승인이 몇 명 필요한가요?"` → `development-guide.md` · `"최소 1명"` / `"P1 장애가 나면 몇 분 안에 원인을 파악해야 하나요?"` → `development-guide.md` · `"30분"`. **1위 결과**로 단언한다 (spec "기대한 문서의 청크가 상위에 온다")
- [ ] 7.4 무관 질의 테스트 — `"오늘 서울 날씨 어때?"`의 결과가 비었거나, 최고 점수가 6.3 네 질의의 최고 점수 중 최솟값보다 작은지

- [ ] 7.7 `tests/test_embedding.py`에 **두 경로가 실제로 다른 벡터를 낸다**는 단언 추가 — 실물 모델로, 같은 문자열을 `embed_query`·`embed_documents`로 각각 인코딩해 결과가 다른지. 기존 "접두사 규약이 실제로 붙는지" 테스트 옆이 제자리다. **retrieval 스펙에 넣지 않는 이유**: 비대칭은 이 모델의 성질이지 모든 임베더의 계약이 아니고(대칭 모델도 정당하다), 계약으로 걸면 페이크까지 비대칭이 되어 4.8이 무너진다 (design 결정 12)
